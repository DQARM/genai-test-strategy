# GenAI 測試審查 Skill 使用手冊

版本：1.5.1。更新日期：2026-11-13（Asia/Taipei）。

此 Skill 用於審查已存在的 Test Case（測試案例），支援純軟體、系統設備與人工測試。需求釐清和案例產生請使用 `genai-test-strategy`；審查使用 `genai-test-review`。

## 安裝

審查涵蓋規格問題單、風險對應測試深度、跨領域風險及執行安排的審查界線。問題單不代表問題已回答；非需求風險不強迫新增假需求。檢查轉移序列、組合強度及決策表縮減的依據，仍只用已確認規則判 Expected。排程標籤／時間與設計版本分開，不能用 smoke／回歸建議清單縮小原設計審查範圍。

安裝本資料夾的 SKILL.md、agents 與 references，保留相對結構；不要覆蓋原本的測試策略 Skill。
GitHub 入口：[skills/genai-test-review](https://github.com/DQARM/genai-test-strategy/tree/dev/skills/genai-test-review)。
可單獨使用本 Skill 審查其他工具製作的文件，不必先安裝測試策略 Skill 或建立 Git 專案。

## 已有測試策略專案時

1. 設計端交付案例時會自動準備並驗證交接包，提供實際位置；特殊審查重點保存為 qa/review-focus.md。
2. 開新對話／工作階段，貼實際 HANDOFF.md 內容；也可只指定可存取的專案，如下。
3. 取得發現後回到設計端決定修正、待釐清或其他處置；修正後以新版本再審查。

```text
請使用 genai-test-review，審查「填入可存取的專案根目錄」目前的案例。
自動查找適用交接包；沒有時直接審目前專案，說明實際版本與限制。
沿用已選範圍，重新讀取規格、決策與操作文件。
請留下具體發現、依據與建議，不修改產品規則或案例。
```

REV 取自 Review（審查），數字是流水號。輸入包在 qa/review-packs，完成的審查紀錄在 qa/reviews；審查結果存在不代表輸入包存在。若明確指定某個包／歷史版本，找不到時會列阻塞，不悄悄換成目前資料。一般審查不需要自己填示例包名。

## 換另一個 AI 模型獨立審查

1. 請設計端「準備可攜審查包，包含特殊重點、原始來源、四輪準則與回傳格式，驗證後提供實際 ZIP」。設計端使用 prepare-review --portable；以其工具 --help 確認能力。
2. 在另一模型開新對話，提供 ZIP 或已解壓內容，請它「從 PROMPT.md 開始，依 REVIEW_GUIDE.md 審查，按 REVIEW_TEMPLATE.json 回傳結果」。接手模型不需要安裝本 Skill。
3. 來源依 manifest.json 的 bundle_path 讀 payload 副本；原機器的路徑不用可讀。包內 verify_pack.py 可驗證完整性；無法解壓、讀來源或執行驗證時須列限制。
4. 拿回 JSON 與摘要，讓設計端核對版本、編號與發現，再依人的處置修正。原包與審查保留，新設計用新版本再審。

reference 包仍需要原專案；portable 包才有來源副本及 ZIP。兩者都有獨立可讀的準則、回傳模板與特殊重點；verified-with-gaps 表示設計或來源仍有缺口，不代表通過。只有包時無法重算完整原專案 digest，回傳需保留此限制。不同模型也可能共享偏誤，必須實際閱讀原文。同一對話換模型仍屬 same-session。

交接包會帶入來源閱讀紀錄、具體摘錄引用及閱讀範圍摘要。審查會回到原檔核對摘錄是否忠於正文／圖表、上下文及適用版本，而非只看 SRC（Source，資料來源）已登錄或標為已讀。只讀目錄、來源缺失、摘錄誤解或更新後未重讀，會列為具體發現與限制。舊資料沒有閱讀紀錄時不假造歷史；仍可審查可讀內容，缺口交回設計端補齊。

兩個 Skill 共用同一個 qa/、編號字典與專案工具。審查不重新初始化、不重問版控；累計題數、本批額度及續問／先產出選擇都沿用。訪談節奏由設計端原 session 決定，審查保持該狀態。審查的四輪不套用訪談批次。
舊包缺 handoff／閱讀欄位時仍可人工交接可讀內容，保留版本與限制；需要升級時交設計端處理，審查不重建原專案。

## 只有規格與案例文件時

```text
請使用 genai-test-review，依附件中的規格與已選範圍，審查這份案例。
先在對話交付發現；來源不足的部分列限制，不新增產品規則。
```

沒有已確認規格仍可先檢查步驟與一致性；規格追溯與覆蓋可能受阻。報告會如實說明，不能把未檢部分算成通過。沒有原專案工具時，不偽造可供正式基線使用的完整設計 digest。

## 四輪會檢查什麼

| 輪次 | 內容 |
| --- | --- |
| 規格追溯 | 每個 Expected（預期結果）是否有已確認規則與版本支持？ |
| 可執行與可判定 | 初態、資料、操作、判定時機、觀測、證據與重置是否明確可行？ |
| 已選範圍覆蓋 | 方法、覆蓋項目及本輪需求的風險評估是否完整，保留項目是否有案例與斷言，暫緩是否有依據？ |
| 一致性 | 有沒有重複、矛盾、過期依據、單位錯誤或依賴其他案例？ |

風險評估會檢查需求直接關聯、評估版次與狀態，以及危害嚴重度、發生可能性、測試優先序各自的準則與理由。未評估或 unknown 不算低風險；缺資料只列發現，不替使用者評分或接受剩餘風險。舊資料沒有欄位時列限制，不要求整個專案重做訪談。

可依相關 QA（Question and Answer，問答紀錄；數字後綴為流水號）核對原始問題／選項／回答及更正鏈，找出摘要遺漏條件或沿用舊答案的問題。AI 解讀不是使用者原話，缺原文如實列限制；不要求重新回答全部問題。

四輪是四種檢查，可一次交付，不是四輪訪談；只有實際完成的輪次才列為完成。
詳細準則見 [criteria.md](references/criteria.md)，交接與記錄格式見 [handoff.md](references/handoff.md)。

## 你會拿到什麼

- 審查對象、版本、工作階段與完成／受阻的檢查。
- 每項 Finding（發現）的案例、規則或原文位置、具體差異、證據與修正建議。
- 需設計端處理的規格／操作缺口與待人決定的事項。
- 已初始化專案中新增的 qa/reviews/REV-*.json，必要時附同名 Markdown；只在對話模式則直接交付文字。

F 取自 Finding（審查發現），TC＝Test Case（測試案例），AC＝Acceptance Criterion（驗收條件）。新增或引用其他編號時也會說明其英文來源、中文用途與後綴意義。機器資料中的 ID（Identifier，識別碼）保持原樣，以免破壞追溯。

## 如何處理發現

```text
請使用 genai-test-strategy，接回這份審查，沿用原焦點與已問題數。
先列出受影響的規則與案例；依我已確認的處置修正。
若仍需新的產品決策，沿用原本的批次與選擇；等待選擇時先取得續問選擇，已選先產出或明訂總上限已到時只列待辦，不因修正重新訪談。
修改後建立新版本，再交 genai-test-review 重審。
```

審查端不擅自修正產品答案，也不代替人接受剩餘風險。原始審查保留，修正後重新審查，不把舊紀錄的 digest 改成新版。
審查檔保存沿用既有版控方式，只提交本次審查檔；既有 staged 內容或同步阻塞會如實說明。設計端後續更新原進度與 HTML 閱讀網頁。

同一對話換 Skill 仍是 same-session（同工作階段自查），不能稱獨立審查。新工作階段重新讀取指定依據才是 fresh-session；人實際審查才是 human。四輪審查不等於人已核可案例，更不代表產品已實測或通過。
