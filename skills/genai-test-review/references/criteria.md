# 四輪審查準則

從已確認規格、AC、選定風險／情境／範圍、候選案例、已驗證的操作介面與準則建立審查上下文。來源可以共享，但判準不得來自受測程式；不能因程式、案例、Expected 都由同個假設產生且相互一致，就宣稱已獨立驗證。

## 1. Traceability

逐一檢查每個 Expected 對應已確認規則、適用條件、revision、原文。找出推測的持久化、重啟、等於邊界、時間／容差、錯誤處理等。缺規則記為待釐清 Finding，交回設計端登錄 Q，不由審查端修改問題清單或加入產品承諾。來源的顯示值、保存值、設備輸出及物理效果不得互相代換。

`source_citations` 指向來源的 `reading_seq`（此來源的閱讀紀錄序號）與 `finding_index`（該紀錄內的摘錄序號）。逐一實際開啟對應原檔的定位與必要上下文，核對版本、引文／轉述、數字、單位、比較運算子及圖表語意。readings 是設計端的閱讀紀錄，不能充當審查已讀的證明；檔案 hash 也只驗證版本。來源 confirmed、readings.status=scoped 或工具檢查通過，不保證摘錄支持這個 Expected。

只有目錄、讀取輸出截斷、抽樣未涵蓋條件、圖表未看、摘錄不支持規則、引用已過期／已被更正時，列出具體來源位置、受影響規則／案例、缺口及修正建議。原檔不可得時標限制，不以別人的摘要完成該檢查。舊資料缺 readings，仍可核對現有原文並留下發現，不推論過去一定沒讀；由設計端補結構化證據，審查端不回寫設計資料。

有問答依據時，核對原始提問、選項與回答是否支持決策中每個適用條件；「第二個」須對照當時選項。AI interpretation 不是原話，answered 不是 confirmed。檢查 supersedes 更正鏈，不能忽略新答案或以舊摘要消除分歧；partial／summary_only 記原文缺失限制。缺原文不等於產品規則一定錯誤，也不能當成已驗證無誤。

## 2. Executable and verifiable

如有 qa/questions.md，它只是 registry.questions 的衍生交接單。核對 open／deferred 對規則或操作的實際影響；排序、建議選項、建議轉交人及空白填答不是決策證據。已知衝突未解卻採一邊為 Expected 時列具體發現，不替 PM 選答案。審查端不以修問題單為由修改設計輸入。

實際讀每一步確認：可取得環境與權限、可建立及驗證初態、可重建資料、操作路徑存在、輸入具體、觀測點可取用、判定時機可控制、預期可判定、證據可保存、可清理重跑。只有標題或 Gherkin 時列具體欠缺欄位。

例如「輸入異常資料，確認處理正確」缺輸入、初態、操作、時機與觀測；不要直接補入猜測的值。介面文件沒有提供的查詢或重置能力，不能自行杜撰；要提出可觀測性缺口或已確認的黑箱驗證方法。

## 3. In-scope coverage

先檢查方法和項目清單本身：分區是否合理、邊界的等號與鄰值是否有依據、決策表是否漏可行組合、轉移是否綁定初態；成對組合是否漏掉已知高階交互作用。再逐項查保留 COV（取自 Coverage，覆蓋項目）對應的已選案例、具體資料、操作與斷言；不是有 COV 連結就算充分。

第三輪以已選 AC 的保留 COV 檢查設計承接，同時保留原有 AC／風險／情境的完整性檢查。暫緩項目查人的取捨與剩餘風險；不可清空 COV 或全標 defer 來消除已選 AC 的責任。EXP（取自 Exploration，探索任務）不能代替正式案例。分開表達設計承接與有實際結果支持的執行覆蓋。

只用本輪已選 AC、風險、情境、邊界、狀態、異常作分母。逐條看斷言，不能只數 TC ID。若已確認要求涵蓋畫面、保存、重啟，但 TC 只看畫面，列後兩者缺口。若規格尚未要求重啟持久化，不能以審查名義新增這個 Expected。

檢查所有比較邊界及初始狀態。只有明確的資料型別、單位與解析度時才採 adjacent value；不可沿用教材的步進或門檻。缺少某個已選風險的案例是缺口；未選項目放剩餘風險清單並沿用已決定取捨。

需求風險評估另查：本輪需求是否有實際初評／確認依據，requirement_revision 是否對應需求版次；risks.requirement_ids 是否直接連結，是否漏評或把未評估當成無風險。severity（危害嚴重度）、likelihood（發生可能性）、priority（測試優先序）應分開且有專案等級定義及理由；unknown 不能當最低等級，低機率不能降低後果嚴重度。確認記錄須支持實際評估內容，不能只掛一個無關決策編號。

一個需求可有多個風險，共通風險可跨需求；查已選風險是否由案例真正承接，其他本輪相關風險是否有暫緩理由、剩餘風險與決策。未選需求可以未評估，不自行擴張訪談或測試範圍。缺資料列 Finding，交回設計端；審查端不補評分、不改取捨、不把沒有 RISK 記錄當成零風險。舊版無新欄位時清楚列限制，不追溯改寫舊基線。

### 假想缺陷與斷言辨識力

對每個保留 COV，設想一個與已確認規則相關、合理而可觀測的實作錯誤，對照案例的初態、資料、操作及斷言；同一反例可承接多個項目但保留映射。這是設計推演，不是已執行 mutation testing 或產品結果。

在報告留：COV／規則｜假想錯誤｜正確與錯誤行為差異｜案例步驟／斷言｜可辨識、無法辨識、無法評估或不適用及理由。例如規則為距離 ≤ 2 m 允許授權，錯誤為 < 2 m；只輸入 1.9 m 的案例無法辨識等號錯誤，應核對已選等號項目是否有 2 m 的可用輸入及授權斷言。

已有具體反例、但所有承接案例仍可能通過時，列 coverage Finding，指出輸入、觀測或斷言缺口；建議只用已確認判準。若規則未決、反例不適用、量測不可得或想不出合理反例，記具體限制／待釐清，不僅因 AI 答不出來就判定斷言弱。等價錯誤不應硬要求案例分辨；不為反例發明規則或增加未選範圍。

需要評估審查者檢出能力時按 [calibration.md](calibration.md) 使用隔離副本，不能在正式審查包埋瑕疵。

### 方法深度與跨領域風險

風險與方法的關聯須有失效機制及證據理由；不能看到高危害就固定要求三值邊界。狀態準則區分狀態、單一有效轉移、有效及無效轉移、連續轉移對；核對序列可行性、初態與中間狀態。組合測試查強度 t、限制及可延伸為完整合法配置的元組；刪除不合法列後不能直接宣稱覆蓋不變。決策表合併要保留原列映射及不影響結果的依據，未知不等於不可行。

error-guessing、data-lifecycle 或 experience 提供情境／失效假說；仍查每個 Expected 的規則依據。團隊經驗與既有 bug 修法不能直接當新規格，資料生命週期也不可無依據加上刪除傳播或還原承諾。

風險 origin 可能為 integration、change、architecture、environment、omission、experience；可沒有 requirement_ids，但須明列 affected_areas、來源／決策、assessment_status、三維分級理由及取捨，遺漏規則另有 question_ids。不能為了需求關聯要求新增假需求；也不能只改 origin 就放過無依據風險。缺省 origin 的舊孤立風險仍是缺口。

qa/execution-profile.json 與 qa/selections 是執行安排，與原設計 digest 分開；若只審設計，不因標籤或時間更動否定原審查。原 cases／registry／strategy／plan 等設計欄位變更仍依新 digest 重審，不把它們移出來規避。執行清單使用前另核對版本；不能用 smoke 或預算裁減後的清單取代原已選範圍。未執行不標產品通過。

## 4. Consistency

找重複、矛盾、過期來源、單位混用、案例間依賴、初態互相污染、先後順序隱藏要求、失效的版本與不一致的判準。合併重複案例需保留原 ID 與追溯；不能直接刪掉唯一覆蓋某風險的案例。

每筆正式案例須自行建立並確認前置狀態，能單獨重跑。即使前一筆案例收尾會重置，仍不能依賴其成功執行來滿足本案例前置；這是可執行性／一致性 Finding，不能只註明執行順序就視為解決。業務上必須連續的操作應放在同一案例的明確步驟內，並讓該案例自行準備初態。

## 輸出與獨立性

共用／推導判準另查：AC 採納決策、適用條件、比較關係、觀察時機及限制是否足以支持這個 Expected。經驗來源只供情境線索；審查包中的 comparison_reference_ids 只供已確認比較關係，不能把參考版本行為一律當作正確。規格沒有的期望仍列待釐清。

每項 finding 留：ID、round、case_ids、rule_refs、具體問題、證據、修正建議；交人處置為修正、合併、暫緩、待釐清、接受剩餘風險或有依據駁回。修正後重審對應新 digest。

新對話／新 agent 實際重新載入來源才標 fresh-session，另記 session／reviewer／model。相同 agent 在原對話重讀只能標 same-session；不得改標以通過檢查。fresh-session 可減少上下文污染但不能保證沒有同模型偏誤。能使用不同模型／人員時做交叉審查，仍保留可追溯判準。

獨立代理不可用或未獲允許時，不擅自建立；提供新對話提示，沿用指定審查版本。人員審查可標 human 並記實際審查證據。基線需要四輪完成、finding 有處置，以及人對目前內容的明確核可；不要求為每筆例行保存再問一次同意。

記錄格式、版本核對與回到設計端的方式見 [handoff.md](handoff.md)。rounds 只記真正完成的輪次；有來源或範圍缺口時明列限制，不以空 findings 冒充通過。
