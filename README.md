這是一個通用的 GenAI 輔助測試策略 Skill，讓每個人使用自己的專案資料，
逐步釐清需求、補完可驗證規格、選出優先風險，並產生有具體步驟的 Test Case。
可用於 Web、App、API、資料處理、Linux／網路、設備或 AI 產品等專案。
「GenAI」指用 AI 協助工作流程；被測產品不必使用 AI。
所有規則、數值、操作介面與預期結果，都以本專案的資料及確認決策為準。
教材中的溫控系統只是例子；新專案不會預先建立任何教材規則或案例。

本手冊可以放在專案根目錄，檔名保留 `README.md`。
一般操作以對 AI 下指令為主；進階使用者可使用後面的命令列流程。
本手冊說明已安裝 Skill 的使用方式；工具程式隨 Skill 提供，初始化後會複製進專案。
日常閱讀可開啟 `qa/report.html`：來源資料與完整測試案例有雙向超連結；原有文件與紀錄全部保留。
需求釐清先聚焦一個可交付流程，每批最多五題、一次一題；統整後選擇「先產出」或「再釐清最多五題」。取消預設十題總上限，使用者明訂限制仍優先；初始化及續問選擇不計需求題數，資料足夠就提早產出。
每題成對保存原始提問、選項與回答，將 AI 解讀分開；依實際確認保存決策與進度；案例及閱讀報告在輪末集中更新。接續時按需讀取相關規則與來源，完整依據仍保留在專案內；API 成本限制另見 11.3。
每批案例開始撰寫前，AI 會先列出目前已知條件、狀態與來源；已有足夠依據就接續產生案例，不必重新核可整張摘要。
AI 再依規則選擇測試方法，列出要涵蓋的邊界、條件組合或轉移，形成案例；共用判準確認一次後可重用，部分規則未定時也能先交付探索計畫。這些分析沿用本輪範圍與提問額度。

## 00. 兩個 Skill 如何配合

本專案提供兩個可個別安裝的 Skill；既有 `genai-test-strategy` 名稱與入口保留。

| Skill | 負責工作 | 安裝入口 |
| --- | --- | --- |
| `genai-test-strategy`：GenAI 測試策略 | 需求釐清、規格、風險、方法、完整案例；接回發現後修正，依人核可建立基線 | 本儲存庫根目錄的 [SKILL.md](SKILL.md) 及原有 agents／assets／references／scripts／README.md |
| `genai-test-review`：GenAI 測試審查 | 審查既有案例的追溯、可執行性、覆蓋與一致性，留下具體發現與建議 | [skills/genai-test-review](https://github.com/DQARM/genai-test-strategy/tree/dev/skills/genai-test-review) 整個資料夾 |

原本已安裝測試策略者，只需更新它，並依使用平台支援的 Skill 安裝方式新增測試審查。
不要用審查 Skill 覆蓋原本的測試策略。平台要求選擇子資料夾時，審查入口選 `skills/genai-test-review`；只安裝儲存庫根目錄不能假定第二個 Skill 也已安裝。
兩者共用同一個專案 `qa/`、編號字典及 `qa/tools/qa_project.py`；不建立第二套專案，也不把審查檔當新的需求來源。
只有規格與案例文件時，審查 Skill 也可單獨使用，不必先初始化專案。

日常使用：

1. 用 `genai-test-strategy` 讀稿、釐清、選重點並產生案例；每批最多五題，統整後由你選擇續問或先產出，足夠就提早交付。
2. 要審查時，由設計端產生 `review-pack`；在新工作階段用 `genai-test-review`，提供同一專案與指定交接包。
3. 審查端只新增發現紀錄，規格／案例不改；回到設計端依人的處置修正，對新版本再審查。原焦點、已問數及有效答案沿用。

同一對話換 Skill 仍是 same-session（同工作階段自查）；真實新工作階段重新載入依據才是 fresh-session（新工作階段審查）。四輪審查是四種檢查，可一次交付，不是要求你再回答四輪問題。
審查的產品決策缺口交回設計端，保留原本批次與續問／先產出選擇，不能藉切換 Skill 自動重啟訪談。實際測試執行與證據整理能力仍保留在既有流程中，依任務啟用。

## 01. 五分鐘開始使用

### 步驟 1：啟動 Skill，先回答有沒有已知規格

```text
請使用 $genai-test-strategy 協助我釐清需求並產生 Test Case。
請先問我有沒有已知規格或需求草稿。
再協助我建立或選定專案資料夾，讓我選擇本機或 Git server 版控；選 server 時協助登入。
有文件時詢問文件位置，沒有文件時逐題訪談。
```

AI 的第一題應是：

> 你目前有沒有已知規格或需求草稿？

- 有規格文件或需求草稿。
- 有一些口頭規則，還沒有文件。
- 目前沒有已知規格，需要從頭釐清。

這一回合只回答規格狀況，也可以自由描述；AI 先不詢問或建立專案資料夾，
也不把文件路徑與產品需求問題一起塞進來。
已有零散草稿或口頭規則就能開始，不要求先有完整文件。
如果你已提供規格、草稿、來源位置或說明規格概況，AI 應直接沿用，不重問。
只有提供專案資料夾路徑，還不能推定是否有已知規格。

### 步驟 2：選擇新建或沿用專案資料夾

已取得規格概況後，若你尚未選擇資料夾，AI 才接著問：

> 這次要由我建立新的專案資料夾，還是使用你現有的專案資料夾？

- A. 建立新的專案資料夾。
- B. 使用現有的專案資料夾。

這一回合先選 A 或 B；選擇及路徑已提供時，AI 應直接沿用，不重問。

### 步驟 3：提供專案資料夾路徑，由 AI 建立或接手

選 A 時可回覆：

```text
請幫我建立「D:\Projects\Product-A」。
```

選 B 時可回覆：

```text
使用現有的「D:\Projects\Product-A」，請保留裡面的資料。
```

以上只是路徑示例，請換成自己的位置。若新建時明確說「由你選位置」，
AI 可在能寫入的工作區建立不衝突名稱，並回報實際位置。
現有資料夾若不存在，應先核對路徑，不會默默建立一個空資料夾冒充找到原資料。

AI 必須先確認資料夾存取能力，取得下一步的版控選擇後，再建立或沿用 qa/ 與 Git。
在瀏覽器輸入 D:\Projects\Product-A，不會自動讓 AI 存取你電腦的磁碟。
請使用已開啟／掛載該資料夾的環境，或提供 AI 可存取的工作區。
若要將歷史留在自己電腦，工作完成後須保存整個專案及 `.git`。

### 步驟 4：選擇本機或 Git server 版控

版控方式還沒決定時，AI 接著只問：

> 這個專案的版本要只保存在本機，還是同步到 Git server？

| 選擇 | 保存方式 | 接著會做什麼 |
| --- | --- | --- |
| A. 本機 Git | 歷史保存在專案資料夾內 | 建立或沿用本機版本，不需登入或連線。 |
| B. 本機 Git＋Git server | 本機保留歷史，另同步到指定儲存庫 | 協助登入 GitHub、GitLab 或你的 Git server，確認儲存庫及權限。 |

選 B 後，還不知道服務時才問「你要使用哪個 Git server？可提供服務或儲存庫網址」。
AI 會逐步處理登入及儲存庫；帳號已連線且權限足夠時直接沿用。
需要你登入時，由 AI 引導到官方授權流程；密碼、驗證碼或安全金鑰操作由你在官方頁面完成。
完整操作見 [14.5 Git server 登入與同步](#145-git-server-登入與同步)。

選擇會記在專案的 `qa/session.md`，下次續作不重問。
這只是文件與成果的版本保存方式，兩種都可搭配手動測試，不要求建置
CI/CD（Continuous Integration／Continuous Delivery，持續整合／持續交付）。

### 步驟 5：有文件時，指出規格或草稿位置

只有一開始回答有文件、但尚未提供位置時，AI 才問：

> 規格或需求草稿放在哪個資料夾？也可以回答「就在這個專案資料夾」，或提供可讀取的附件。

**你可以擇一回覆：**

- 就在這個專案資料夾，請先盤點相關檔案。
- 草稿在「D:\Documents\Product-A-Drafts」，與專案資料夾不同。
- 我已提供附件，請先閱讀。

若一開始已說沒有文件，直接跳過這一步，不再要求文件路徑。
如果只回答「有規格」而未說明形式，AI 會先釐清是文件還是口頭規則。

可提供需求草稿、規格、會議記錄、圖片、操作手冊、API 文件、舊案例或缺陷。
只有零散草稿也能開始，不需要完整規格或原始碼。
已提供可讀取的附件或檔案時直接沿用，不必再重複提供。

### 步驟 6：依有無文件，展開需求釐清

**有草稿：**

AI 先讀取內容、整理已知事項與缺口，再提出最重要的一個問題。
草稿若在專案外，會保留原檔，將本輪需要的版本複製進專案
`inputs/requirements/`，記錄原位置及版本；不會搬移或覆寫原草稿。
草稿內容與 AI 整理稿不會自動變成已確認規格。

**沒有文件：**

AI 先記錄「目前無文件版需求」，不再追問文件路徑。
已有口頭規則時，先沿用你說過的內容，再逐題補齊；尚無規格時從目的與重要行為開始。
「沒有文件」不會被解讀為「沒有已知規則」，已知內容也不會自動被當成正式規格。
若還不知道專案內容，下一題才問「你要測試的專案或功能是什麼？」
已知道專案內容時則直接問下一個重要分歧。
回答會逐步整理成 `inputs/requirements/initial-notes.md`，
區分使用者原意、AI 草稿、已確認決策及待確認事項。

範圍很大時，AI 會先協助選定本輪流程，按「每批最多五題，統整後選擇續問或先產出」推進。
你可指定更短時間或更少題數；10–15 分鐘只是預設進度檢視目標，不必把整個專案釐清完才開始產出案例。操作方式見第 05 節。

### 步驟 7：選測試重點，產生完整案例並保存

```text
請依已確認需求找出最重要的測試風險，再把已選情境展開為完整 Test Case。
開始寫這批案例前，先列出目前已知條件、確認狀態、來源及待確認缺口。
每筆要有前置條件、資料、具體操作步驟、Expected 及依據、判定時機與證據。
未確認事項請保留，不要替產品補答案；這一輪先不執行產品測試。
請保存進度，說明本輪交付什麼、還缺什麼，以及下一個動作與責任人。
```

操作介面、環境或產品規則不明時，案例會保留 draft／blocked。
你可以先完成需求釐清和案例設計，再依需要進入審查、核可及實際執行。
只有當你明確要求「先在對話討論，暫不建資料夾」時，才跳過預設的資料夾步驟；
此時 AI 不會宣稱已保存檔案或本機版本。

## 02. 分工與重要觀念

**編號一定附說明：**

AI 每次新增或展示資料編號，必須讓你知道英文來源、中文意思與用途。
每則回覆或每份文件第一次使用某前綴時，展開說明或附簡短圖例。
例如 `REQ-01`（REQ＝Requirement，需求；01 是本類別的流水號，用來追蹤這筆需求）。
同一輸出重複引用可用短標籤；換一則回覆或一份文件時仍要有說明。
ID＝Identifier，意思是識別碼。流水號不代表優先度、版本、確認狀態或測試結果。
舊編號原樣保留；不會為補零而把 `REQ-01` 擅改成 `REQ-001`。

本 Skill 的預設編號慣例（不是所有團隊必須使用的標準）：

| 前綴 | 英文來源 | 中文意思 | 用途 |
| --- | --- | --- | --- |
| `SRC` | Source | 資料來源 | 追蹤文件、操作指南或其他依據。 |
| `REQ` | Requirement | 需求 | 追蹤單一產品需求。 |
| `AC` | Acceptance Criterion | 驗收條件 | 定義可觀測且可判定的產品條件。 |
| `Q` | Question | 待釐清問題 | 追蹤未決事項、責任人與確認時點。 |
| `QA` | Question and Answer | 問答紀錄 | 保存原始問題、選項與回答；不是品質保證的縮寫。 |
| `DEC` | Decision | 決策 | 記錄人的決定與依據。 |
| `RISK` | Risk | 風險 | 追蹤失敗情境、影響與取捨。 |
| `SC` | Scenario | 測試情境 | 表示待選或已選的測試情境。 |
| `TC` | Test Case | 測試案例 | 保存完整前置、步驟、判準與證據要求。 |
| `REV` | Review | 審查紀錄 | 記錄特定版本的案例審查。 |
| `F` | Finding | 審查發現 | 追蹤具體問題與處置。 |
| `APP` | Approval | 核可紀錄 | 記錄人對明確內容與範圍的核可。 |
| `BL` | Baseline | 案例基線 | 凍結已核可的案例版本。 |
| `RUN` | Run | 測試執行紀錄 | 保存某次實際執行的觀察與證據。 |

RISK 與 RUN 本身就是英文單字；AC 的複數寫法為 Acceptance Criteria。
自訂前綴也要解釋；既有前綴含義不明時標待確認，不能猜英文展開。
新的純數字編號也需標明是步驟序號、需求序號等。
JSON 的 id／參照欄位仍只放原編號，說明放在圖例或獨立欄位。

**AI 負責：**

- 讀取與整理資料、辨識衝突和遺漏。
- 一次提出一個重要決策問題，提供選項及各選項的差異。
- 將你的回答整理成需求、驗收條件、決策與待辦。
- 提出風險排序、候選情境與完整測試步驟。
- 執行結構檢查、建立追溯關係、整理審查發現與版本紀錄。
- 在你要求且具備執行環境時，協助執行並記錄實際觀察。

**人負責：**

- 確認產品應有的行為與哪份資料具決策效力。
- 決定本輪測試範圍、資源投入及可接受的剩餘風險。
- 確認審查發現的處置，核可正式案例基線。
- 決定是否執行、是否接受例外，以及產品是否放行。

三個需要分開的動作：

| 項目 | 說明 |
| --- | --- |
| 保存版本 | 記錄目前文件狀態，草稿也可以保存。 |
| 核可案例 | 人接受某一個明確版本的案例集，建立 baseline。 |
| 執行測試 | 在指定產品與環境實際操作，取得 Actual 和證據。 |

「check 通過」表示工具未發現它所檢查的結構問題。
「ready」表示案例設計已具備要求的欄位及依據，仍需審查與適用性確認。
這兩個狀態都不能直接當成產品測試 PASS。

AI 可以建議答案；只有你已確認的答案或已採納的正式來源能形成產品規則。
你回答「不知道」「待確認」時，問題會保留，不會自動變成同意建議。

## 03. 使用環境與專案資料夾

### 3.1 保存專案與本機版本的必要環境

- 能使用此 Skill，且能讀寫專案根目錄的 AI 工作環境。
- Python 3.10 或以上。
- Git。

本機模式不需要 Git server、GitHub 帳號或 remote（遠端儲存庫連線設定）。
server 模式另需對應服務的連線及儲存庫權限；AI 會協助登入，並確認實際操作環境。
本機 Python 工具與本機 Git 操作可離線執行；遠端同步需要連線，AI 對話是否需要網路取決於使用平台。
只做對話中的需求釐清時可以先不準備這些工具；不能因此宣稱已保存專案或版本。

Windows 可在 PowerShell 檢查：

```powershell
py -3 --version
git --version
```

如果電腦沒有 py 啟動器，但 python 指向 Python 3.10+，改用 python。
macOS／Linux 通常改用 python3。後續範例以 Windows PowerShell 的 py -3 為主。
路徑有空白時請用引號；工具操作需在實際存放專案的環境執行。

### 3.2 建議的起始資料

| 檔案／資料夾 | 用途 |
| --- | --- |
| `README.md` | 本操作手冊。 |
| `inputs/requirements/` | 原始需求、正式規格及歷次版本。 |
| `inputs/decisions/` | 已有會議決議、產品人員確認紀錄。 |
| `inputs/interfaces/` | UI 操作、API、CLI、測試設備或工具文件。 |
| `inputs/existing-tests/` | 已有案例、缺陷與結果。 |
| `src/` | 原始碼；沒有也可以。 |

這是整理建議，不要求你搬動既有檔案。需求草稿資料夾可以與專案資料夾不同；
專案外來源只保存本輪所需的副本，原檔留在原位置。
Skill 會另外建立 qa/ 工作目錄；若你原本已有其他用途的非空 qa/，
請先讓 AI 說明衝突並協調使用方式，不要直接覆寫。

### 3.3 準備資料時的重點

- 清楚標示正式版、草稿、過期版和未決事項。
- 有多個互相衝突的版本時，說明誰有權決定採用哪一份。
- 圖片中的數字、單位及比較符號需要核對；讀不清楚就保留缺口。
- 若要測實際操作，補上操作介面、工具版本與權限條件。
- 純程式碼或目前畫面只能顯示「現在怎麼做」，不自動等於「應該怎麼做」。

## 04. 第一次啟動：盤點與初始化

你可以說：

```text
請使用 GenAI 測試策略初始化這個專案。
尚未知道規格狀況時，先問我有沒有已知規格或需求草稿；已回答的資訊請沿用。
先列出你找到並讀過的資料、版本、來源衝突與缺口。
請區分正式規則、操作介面文件及現況觀察，有需要決策的缺口時才提出下一個最重要問題。
```

**Skill 應完成：**

1. 先確認有沒有已知規格，區分有文件、只有口頭規則與尚無規格；已提供就沿用。
2. 依你的選擇建立新專案資料夾或接手現有資料夾，確認實際讀寫能力。
3. 讀取適用的專案指引及既有進度。
4. 詢問本機或 Git server 版控；已選過就沿用。選 server 時協助登入、確認儲存庫及接手工作副本，再初始化或沿用根目錄的 Git。
5. 建立 qa/、專案標記及 `qa/tools/qa_project.py`，保存規格概況、版控選擇與已回答事項。
6. 有文件且位置未提供時才詢問來源；有文件先讀取，無文件則逐題訪談。
   專案外草稿保存所需副本，再盤點並記錄來源路徑、hash、版本與定位資訊。
7. 整理已知事項與缺口，建立第一個 checkpoint；server 模式在已確定目的地與範圍內同步，讀回驗證。

注意：init 只初始化結構；第一個 Git 版本要另外執行 checkpoint。
再次 init 會保留已有內容，不能用它升級專案工具或重設專案。
初始化只建立空白工作結構，不會載入教材產品、範例數值或預設測試案例。
專案背景隨對話逐步記入 `registry.project`；未知欄位保留，不要求一次填完。

**完成後先看：**

| 檔案／資料夾 | 用途 |
| --- | --- |
| `qa/session.md` | 已知規格概況、專案位置、需求來源或無文件狀態、目前階段、下一步及下一題。 |
| `qa/inventory.json` | 找到的檔案與變更；盤點不代表已讀或已確認。 |
| `qa/registry.json` | 已整理的需求、來源、問題、風險等資料。 |

資料的三種角色：

| 項目 | 說明 |
| --- | --- |
| normative | 產品應有的規則。 |
| harness | 可用的操作與觀測介面。 |
| observation | 目前行為或實測現象。 |

確認規則時需要能追溯到已確認 normative 來源或真實決策。
操作文件可以支持「怎麼按、怎麼呼叫、看哪裡」，但不能替代產品 Expected。

## 05. 逐題釐清需求、形成規格

### 5.1 先定本輪焦點與釐清預算

PM 是 Product Manager（產品經理）。AI 先聚焦一個可交付流程、功能或重要風險，再分批補規格與案例。
已指定的焦點直接沿用；範圍過大且未選定時，第一題只協助選擇本輪焦點。
大型草稿先讀摘要、目錄與相關段落，不把所有文件逐條問完當成開始條件。

「一題」是一次實質需求或範圍決策；「一批」是最多五題的訪談額度；「一輪」是聚焦同一交付目標的工作，可包含多批訪談及後續設計。
**每批最多五題、一次一題；統整後由你選擇續問或先產出。預設不再設十題總上限。**
五題是工作節奏設定，不是人類耐心的科學極限，也不是必須問滿的問卷。

| 問題 | 是否計入需求題數 |
| --- | --- |
| 有沒有已知規格、草稿是文件還是口頭、文件在哪裡 | 不計入 |
| 專案名稱或背景、建立／沿用資料夾及路徑 | 不計入；要求選擇本輪功能則計入 |
| 本機／Git server 版控、登入與儲存庫設定 | 不計入 |
| 統整與選擇續問／先產出 | 不計入；不夾帶產品決策問題 |
| 這輪先處理哪個流程、功能或重要風險 | 計入 |
| 產品行為、例外、驗收條件、衝突規格以哪份為準 | 計入 |

例如前三次往返只確認規格有無、資料夾與版控，需求題數仍是零。
準備完成後可顯示「專案準備：完成；累計 0 題；本批 0／5 題」。提出第一個實質問題才計數；準備期間若已問產品決策，也要照實計入。
追加下一批時本批計數重新起算，**累計題數、原焦點與有效答案持續保留**。題數不表示需求完成百分比，不把多個獨立決策塞成一題。

第一批隨你的需求釐清任務開始，不另外問是否啟動。收到本批最後一答後，AI 用短摘要交代：

1. 這批新增確認的規則。
2. 目前能產出的策略、案例或草稿；尚未撰寫的內容要說清楚。
3. 重要缺口，以及再問能補足什麼。

若資料已足夠，AI 直接產出，不等問滿五題。若還有必要決策，會讓你選擇，例如：

> 已確認主要操作流程與成功條件，目前可開始設計正常流程案例。
> 斷線與重新啟動的行為仍未決，會影響異常案例的預期結果。
> 是否再釐清最多五題，以補足這些異常情境？
> 是：再釐清最多五題。否：先產出目前的測試策略與案例。

這段只是工作節奏示例，不是任何新專案的預設需求。

| 你的選擇或目前狀況 | AI 接下來怎麼做 |
| --- | --- |
| 是／再釐清最多五題 | 明確記錄本次選擇，再逐題問最多五題；只適用這一批，下一批仍需選擇。 |
| 否／先產出／先這樣 | 停止訪談，列已知條件，進入測試策略及案例設計；有缺口的部分保留草稿或受阻。 |
| 資料已足夠、未滿五題 | 直接產出，不為湊題數而追問。 |
| 尚未回答續問選擇 | 保存進度並等待，不直接提出第六題、不把沉默或換對話當成續問同意。 |
| 已到你指定的總題數或時間上限 | 統整並產出，不再邀請續問；已確認內容與缺口都保留。 |

若你在最後一答已明確說「再問五題」，不必重複選擇；只願再答兩題，就只追加兩題。
你說「否」只表示停止訪談，**不表示規格完整、接受未知風險或核可案例**。
AI 不能換到案例設計後又繼續問同一批產品問題，也不能為了結案偷偷縮減已選範圍。

你可以直接說：

```text
這輪只處理「填入本輪要交付的流程」。
每批最多五個需求決策問題，一次一題；先查文件，只問會影響本輪成果的缺口。
每批統整已確認內容、目前能產出的案例與重要缺口，再讓我選續問或先產出。
我選續問才開始下一批；選先產出就做測試策略與案例，未知部分保留待確認，不再追問。
資料足夠時直接產出，不必問滿五題。
```

你指定的總限制仍優先。例如「總共最多八題」，第一批五題後最多只能追加三題，第八題後直接產出。
「這次最多三題」就在第三題後產出；一般的「是／繼續」不自動取消你明訂的總上限，只有明確調整才改記錄。
預設 10–15 分鐘仍只是進度檢視目標；若說「整場只有十分鐘」，則包含初始化，不重開計時。無法可靠計時會明說，不假稱已自動計時。

舊專案只轉換可確認為舊預設的三題／十題設定，保留累計與決策；你明訂或來源不明的總上限仍保留。
舊預設尚在進行且累計三題時，可補至第一批五題；舊記錄已問 5／10 題且沒有續問選擇時，先統整等選擇，不直接問第六題。
若已超過五題且無法重建批次界線，就保留累計，現在統整一次，不補發多次舊摘要。已收尾的工作不因升級自動重啟；泛稱續作專案也不等於同意重新訪談。

| 遇到的問題 | 怎麼處理 |
| --- | --- |
| 影響預期結果、驗收或重要風險的產品分歧 | 有本批額度且尚在訪談時交有權決策的人確認；已選先產出時列待辦。 |
| 操作路徑、設備介面、環境或證據取得方法 | AI 先查文件，再記錄工程／測試負責人需要補充的內容。 |
| 本輪未選範圍的細節 | 保留待辦、責任人或未指派、回訪日期或觸發條件。 |

每題先保存決策、規則與進度，標記受影響案例；選先產出、資料足夠或總上限已到時，實際寫出可完成的策略與案例。
已知規則但缺操作介面、初態建立或觀測方法時，寫出有依據的案例內容，缺欄位標待補，保留 draft／blocked。
若產品判準也不足，就交付已有內容與阻塞清單，不硬湊案例數量。未選情境只列候選；未知 Expected 不由 AI 補答案。
未決事項只阻塞實際受影響的案例與階段；涉及共用前置時保留跨流程影響。原基線及實測紀錄不改寫。

交付時回報新增確認、實際產出的案例／草稿與仍缺欄位，以及下一個動作與責任人；明確區分草稿、可執行與已實測。
下一步可以是查文件、補操作資訊或審查，不能一律又安排訪談。

這次只是流程與文件更新，不增加工具必填欄位；既有專案不需升級 qa_project.py 或重新初始化。
AI 在原 qa/session.md 記錄累計題數、本批起算點與已問／可問數、明訂總上限、最近統整、續問狀態與選擇依據；換對話或 Skill 都沿用。
審查 Skill 的四輪是四項檢查，不套用五題批次，也不因交回修正就重啟訪談。工具 1.4.0 與舊交接包的用法不變，工具升級方式見 Q15。
提問設計參考 [GOV.UK Question pages](https://design-system.service.gov.uk/patterns/question-pages/) 的必要性、說明目的與避免重問原則；五題批次及續問選擇是本 Skill 的設計選擇。

### 5.2 一次確認一個產品分歧

你可以說：

```text
請從會造成不同產品行為或不同 Expected 的分歧開始，一次問一題。
只問會影響本輪案例或驗收的缺口；先查文件與已確認答案，跳過不適用的分支。
問題用白話；必要時說明影響，有明確方向才給中性選項，也允許待確認或自由回答。
把我已確認的答案記成決策，再更新需求與驗收條件。
```

把 GOV.UK 的表單提問原則用在需求訪談，重點是讓每題更必要、更容易回答：

| 原則 | 本 Skill 的具體做法 |
| --- | --- |
| 只問有用途的問題 | AI 先判斷答案會改變哪個案例、判準或風險取捨；不影響本輪的細節先列待辦。 |
| 已有答案只用一次 | 先查相關文件與有效決策，直接沿用已確認答案；未確認草稿不會自動變成規格。 |
| 每次聚焦一個問題 | 問題先用白話說清楚，需要時才補短說明；不把錯誤處理、提示、等待時間與重試一起問。 |
| 只展開適用分支 | 例如已確認不支援離線作業，就跳過離線操作的細節；不能自行假定功能不適用。 |
| 提供容易回答的方式 | 有明確方向才給中性選項；接受不知道、適用時的不適用及自由回答，保留真正未決的內容。 |
| 可檢查與修正答案 | 統整時可直接指出哪項要改，保留修訂記錄；只重檢受影響規則與案例，其他答案繼續沿用。 |
| 如實呈現進度 | 說明新增規則、已有成果與阻塞；題數只顯示已用額度，不冒充需求完成百分比。 |

以上是對本流程的應用，不是 GOV.UK 對 AI 訪談的認證。官方來源包括
[Question pages](https://design-system.service.gov.uk/patterns/question-pages/)、
[Designing good questions](https://www.gov.uk/service-manual/design/designing-good-questions) 與
[Check answers](https://design-system.service.gov.uk/patterns/check-answers/)。
五題統整不能代替改善問題本身；實際使用時觀察是否重問、是否因措辭而答不出來，以及答完能否形成案例，再調整題目順序與內容。

AI 會依專案需要，檢查觸發、邊界、時機、狀態、例外、持久化、
恢復、資料、權限或併發等問題，不必每個專案都問完整套問卷。

提問依你的專案而定。例如，只有當你的專案涉及批次匯入，且資料尚未說明
錯誤處理時，才可能問：「一筆資料不合法時，整批拒絕，還是只跳過該筆？」
必要時補一句：「這會決定要檢查整批未寫入，或合法資料仍被保留。」允許回答待確認或提出其他行為。
不能直接推定交易範圍、可否部分寫入或錯誤訊息內容，也不在同一題再追問等待時間與重試。這不是所有專案的第一題。

有答案時可這樣回覆：

```text
Q-001 確認採用「填入我決定的產品行為」。
這次決策只涵蓋「填入適用條件」；其他未決事項仍保留待確認。
請記錄決策依據，更新受影響的需求與 AC。
```

尚無答案時可這樣回覆：

```text
Q-002 暫時不知道，責任人是產品負責人，需在案例核可前確認。
請保留 open，列出影響，先繼續與它無關的項目。
```

**預期產出：**

- 穩定的 REQ ID：需求。
- AC ID：可驗證的驗收條件。
- DEC ID 與決策原文／摘要：誰在何時決定了什麼。
- Q ID：未決問題、責任人、確認時點、影響及阻塞階段。

確認 AC 時至少讀懂：前提是什麼、輸入是什麼、何時看哪裡、
結果應是什麼、容差是否適用、依據是哪一份已確認內容。
不要只批准「功能正常」「操作成功」等無法判定的句子。

### 5.3 原始問答如何保存與查閱

專案工具 1.6.0 起，AI 提問時先記問題及選項，收到回答後補原話與獨立的 AI 解讀。
資料保存在 `qa/registry.json` 的 interactions；你可在 `qa/report.html` 點「問答紀錄」，或閱讀生成的 `qa/interview.md`。
QA＝Question and Answer（問答紀錄），如 QA-001 的 001 是流水號，不代表答案已確認。Q＝Question（待釐清問題）、DEC＝Decision（決策）；一個問題可以有多次問答，一次回答也可能支持多項決策。

| 紀錄內容 | 用途 |
| --- | --- |
| 原始提問、必要情境及完整選項 | 讓「是」「第二個」等短答仍可解讀 |
| 使用者原始回答 | 保留原話，不用 AI 摘要替代 |
| AI 解讀與回答狀態 | 區分已答、部分回答、不知道、暫緩及缺原文；不自動核可規則 |
| 更正與關聯 | 保留舊答案，可點到決策、需求、風險及測試案例 |
| 已知時間、回答者及登錄時間 | 不知道原對話時間就留空，不用登錄時間冒充 |

改答案時可以直接說：「更正剛才的回答……」。AI 會新增更正紀錄，留下原答案，再評估受影響內容。
舊資料若只有摘要，會標示「僅剩摘要／原文缺失」，不補寫成逐字稿，也不為補紀錄重問整輪。
五題統整仍以新增或變更條件、重要解讀及未決事項為主，不增加確認題數。

平常接續只讀進度與相關決策；有需要才讀指定問答，避免每輪攜帶整段歷史。完整聊天匯出是選配。
僅在對話中草擬時不建立檔案；此功能需要 AI 實際保存，不是宿主聊天的自動備份器。
既有專案須先升級 `qa/tools/qa_project.py`；重新 init 不會替換舊工具。欄位與命令見 [成對問答紀錄](references/interview-records.md)。

## 06. 排定風險與本輪測試範圍

你可以說：

```text
請逐筆盤點已登錄需求的風險評估狀態，再聚焦本輪範圍。
連結每項需求的失敗情境與後果，分開說明危害嚴重度、發生可能性與測試優先序及依據。
先依文件完成初評，只詢問會改變本輪取捨的重要分歧；未知明列，不逐需求重問。
提出一批最小但有價值的候選情境，讓我決定保留、合併、暫緩或待澄清。
```

REQ 來自 Requirement（需求），RISK 是 Risk（風險）；如 REQ-001／RISK-001，001 是各類流水號。需求與風險採多對多關聯，不要求每個需求都硬湊一個風險。

| 項目 | 你會看到什麼 |
| --- | --- |
| 需求評估狀態 | 未評估／已有初評（待確認）／已確認；需求已確認不自動確認其風險評估。 |
| 危害嚴重度 | 失敗發生後的後果，含影響對象、範圍與恢復難度。 |
| 發生可能性 | 在使用條件下多容易發生，以及資料不足之處。 |
| 測試優先序 | 這次先測哪些項目及理由，不與嚴重度混用。 |
| 評估依據 | 分級定義、文件／決策、推論與待確認事項。 |
| 版本與追溯 | 需求版次、對應風險、相關案例與暫緩處置。 |

有公司分級標準便沿用；沒有時 AI 先提出精簡建議，取得適用確認依據前保留初評。unknown 表示資料不足，不是低風險。若暫未辨識風險，仍保留檢視範圍與理由，不宣稱零風險。

AI 先批次整理，再集中確認重要分歧；已有有效決策直接沿用。風險問題仍計入五題批次，選「先產出」後交付初評與缺口，不重啟訪談。未選需求可以保留未評估，先完成本輪能交付的案例。

工具 1.5.0 的 `check` 會提示缺評估、缺嚴重度／理由、缺需求關聯或評估版次過期。`render` 產生 `qa/risks.md` 與 HTML「需求風險評估」表，點需求、風險與案例可互相查閱。

舊專案先保存版本並明確升級專案內工具；缺新欄位仍可整理草稿和閱讀。建立新基線前補齊本輪需求評估與真實確認依據；舊 priority 不會自動變成 severity，既有基線及實測紀錄不改寫。詳細規則見 [需求風險評估](references/risk-assessment.md)。

你的取捨可以直接記錄：

```text
本輪保留 SC-001、SC-002；SC-003 暫緩。
請記錄暫緩原因與剩餘風險，更新 strategy.md、plan.md 和 scope。
只將已選項目展開成完整案例。
```

三份內容各自回答不同問題：

| 項目 | 說明 |
| --- | --- |
| `strategy.md` | 為何測、優先測哪裡、用什麼層級與方法、需要什麼證據。 |
| `plan.md` | 這一輪誰做、何時做、測哪個版本、用哪些資料與環境。 |
| case | 在什麼前提下，具體怎麼操作並判斷某個規則。 |

時間不足時，請 AI 清楚列出捨棄哪些驗證與留下什麼風險。
案例數量多、通過率高，都不能單獨代表重要風險已被處理。

## 07. 產生完整可執行案例

選定本輪範圍後，AI 應在寫這批案例之前，先向你呈現一張「目前已知條件」摘要：

| 項目 | 摘要應包含的內容 |
| --- | --- |
| 本輪範圍 | 已選的功能、流程、風險與情境，以及暫不處理的部分。 |
| 規則與驗收條件 | 已確認行為、驗收條件；需求草稿、AI 建議及現況觀察另外標示。 |
| 執行條件 | 設備、軟體、權限、工具、測試資料、前置狀態與重置方式；尚未驗證的可用性要明說。 |
| 判定方式 | 觀察什麼、何時判定、門檻／容差，以及要取得哪些證據。 |
| 待確認事項 | 缺少的規則或操作資訊、相關責任人與確認時點，及受影響案例。 |

每項都保留確認狀態與來源定位，例如文件版本／條款或人的確認決策，有檔案時提供連結。
摘要也須帶入本批適用的共通限制與跨功能依賴；草稿或觀察到的現行行為不會自動成為產品規則。

- 每批開始時整理一次；同批後續只更新變動，不在每筆案例前重印。
- 已有足夠確認依據及操作資訊時，AI 應接續產生案例，不要求你重新確認全部已知內容。
- 缺口只阻塞受影響案例，其他案例繼續產出；不能為了補齊摘要而猜規格或操作。
- 展示摘要不占需求決策題數；需要實質決策的問題沿用本輪剩餘額度，到限就列待辦。

這份摘要供快速核對；每筆案例仍須有完整前置、步驟及預期結果來源，後續審查與核可照常進行。

你可以說：

```text
請把本輪選定的情境轉成完整測試案例，不要只有標題或 Given/When/Then。
先列出本批已知條件、狀態與來源；有足夠依據的案例直接接著產出，有缺口的部分標明受阻原因。
每筆都要有可自行建立的前置狀態、具體資料、編號操作步驟、
觀測點、判定時機、Expected 及規則依據、證據取得方式、清理與重跑方法。
沒有已確認介面的部分列為 blocked，指出需要補什麼。
```

**每筆案例應包含：**

1. ID、revision、目的及設計狀態。
2. 對應的需求／AC、風險、候選情境與來源版本。
3. 測試層級、環境、產品 build 的辨識方式與工具版本。
4. 如何建立並確認初態；不得只寫「接續上一個案例」。
5. 具體輸入值、單位、測試資料與準備方式。
6. 每一步操作位置／命令、輸入、觀察點與觀察時機。
7. 產品斷言的 Expected，以及支持它的已確認 AC。
8. 要保留的 log、畫面、輸出、量測或其他證據。
9. PASS、FAIL、BLOCKED／INCONCLUSIVE 的判讀方式。
10. 清理、重置與獨立重跑方法。

重跑時也要核對會影響本案的殘留狀態，例如快取、去重記錄或待處理事件。
只看到主要資料已清空，不代表所有狀態都已重置；不明部分應列待確認。

**請特別檢查觀測層級：**

畫面顯示新值，只能直接支持畫面顯示的結論。
要證明保存成功，還需要已確認規則與適當保存證據。
要證明下游已處理或端到端效果成立，需要相應層級的證據。
依專案承諾選擇觀測層，不要求每個專案都測相同的層級或使用相同工具。

「可執行」可以是人能照做的操作流程，也可以是完整的自動化程式。
若要自動化，可另外要求：

```text
請檢查已確認介面是否足以自動化，提出適合的框架與腳本。
列出相依套件、執行命令與限制。沒有實際跑過就標示 generated-not-run。
```

**主要產出：**

| 檔案／資料夾 | 用途 |
| --- | --- |
| `qa/cases/TC-*.json` | 案例的結構化來源。 |
| `qa/test-cases.md` | 方便人閱讀的完整案例視圖。 |
| `qa/traceability.md` | 已選 AC／風險／情境與案例的對照。 |
| `qa/risks.md` | 每筆需求的風險評估狀態、嚴重度、可能性、優先序與依據。 |
| `qa/report.html` | 可離線開啟的閱讀報告；來源清單、完整案例與規則可互相點閱。 |

請修改 JSON 來源後重新 render；直接修改生成的 Markdown 或 HTML，內容會在下次
render 被覆蓋。你可以直接告訴 AI 要改哪個案例，由它維持來源與視圖一致。

### 7.1 從規則推導案例，不只掛驗收條件編號

AC＝Acceptance Criterion（驗收條件）；COV 取自 Coverage，表示覆蓋項目；TC＝Test Case（測試案例）。數字後綴是類別流水號。

你可以直接說：

```text
沿用本輪已選範圍，先列目前已知條件，再依規則選適合的測試設計方法。
列出應涵蓋的分區、邊界、條件組合或轉移，說明保留與暫緩理由，再產生有完整步驟的案例。
請自行完成方法分析，不把每個方法都變成新的問題；只釐清會改變產品判準或重要取捨的缺口。
```

| 規則特徵 | AI 可選的方法 | 你會看到的成果 |
|---|---|---|
| 有值域或門檻 | 等價分割、二值／三值邊界 | 明確分區、邊界與有依據的測試值 |
| 多條件共同決定結果 | 決策表、適用時的成對組合 | 要驗證的可行組合與取捨 |
| 行為取決於目前狀態 | 狀態轉移 | 初態、事件、終態及輸出 |
| 跨角色或端到端流程 | 情境式 | 流程與可判定的檢查點 |
| 團隊曾遇到類似缺陷 | 經驗式、探索任務 | 有來源的候選情境；有判準才形成正式案例 |

例如，**僅作示意**：若已確認整數、步距 1，以及「≥50 告警、<50 不告警」，只測 60 不能證明等號正確。二值邊界可選 49、50；三值則為 48、49、50、51。資料型別、解析度或其中一側行為未知時，AI 不會自行補答案。

AI 會將項目寫進 `registry.coverage_items`，案例及產品斷言連到相關項目；生成 `qa/test-design.md` 與網頁的「設計覆蓋」表。暫緩項目留下原因、剩餘風險與實際取捨決策。同一決策可涵蓋多項，不逐項重問。

表中的「有斷言引用」仍需審查輸入與步驟是否真的承接；它不代表已執行或產品已通過。方法細節見 [test-design.md](references/test-design.md)，可照做的本機練習見 [完整門檻示範](references/worked-example.md#d-完整演練項目數量門檻告警)。練習只需 Python，不需設備或 CI/CD。

### 7.2 共用判準確認一次，之後重用

oracle 是判斷實際行為是否符合期望的「測試判準」。判準可來自明確規則、已確認的推導／比較關係，或團隊採納的共用期望。DEC＝Decision（決策），保存人的真實確認。

```text
請先找出本專案已確認、可以重用的共用判準，列出適用條件與限制。
尚未採納的內容標為建議；依需要讓我確認一次，之後適用的案例直接引用，不逐案例重問。
```

例如「在已約定的操作範圍內不得毀損既有資料」，需說明資料範圍、比較方式與例外；不是所有產品都自動具備這個承諾。人確認後記成決策、需求及 AC，案例引用同一 AC。版本比較或蛻變測試要有已確認的比較關係；相同結果不保證絕對正確，也可能共享缺陷。

### 7.3 規則未完整時，先設計探索任務

EXP 取自 Exploration（探索），表示有範圍及時間上限的探索任務。它適合手動測試，與正式案例分開記錄。

```text
這部分判準還不完整，先依已知操作介面設計一份探索任務。
列目的、範圍、時間上限、前置與重置方式、具體操作、觀察與證據，以及停止條件。
未知行為先記錄觀察與待釐清事項；先交付計畫，實際執行沿用我的執行授權。
```

AI 將任務記在 `registry.charters`，可於 `qa/test-design.md` 及網頁「探索任務」閱讀。操作或環境也不清楚時保持 draft，明列負責人與缺口；不虛構操作。

實際探索另存 `qa/evidence/EXP-001/<本次唯一名稱>.md`，保留受測版本、執行人、時間、實際操作與輸入、觀察、證據及發現。已有 AC 支持的違反可登錄缺陷；沒有判準的行為保留問題，不硬判 FAIL。要成為正式回歸案例時，再補齊規則、步驟與審查。

探索任務或觀察不會自動算入正式案例覆蓋、通過率或產品放行。完整模板見 [共用判準與探索任務](references/oracles-exploration.md)。

## 08. 四輪審查與新工作階段交接

### 8.1 先建立待審版本

你可以說：

```text
請使用 genai-test-strategy，先完成結構檢查，固定本輪範圍與案例內容，取得目前 digest。
產生一份供新工作階段使用的 review-pack，列出需要一併提供的來源。
本階段的自查請如實標記 same-session，不代替獨立審查。
```

四輪分別檢查：

| 項目 | 說明 |
| --- | --- |
| 第 1 輪 | 規格追溯。每個 Expected 是否有已確認規則支持？ |
| 第 2 輪 | 可執行與可判定。初態、輸入、操作、時機及觀測是否可落實？ |
| 第 3 輪 | 已選範圍覆蓋。方法與覆蓋項目是否完整、保留項目是否由案例資料及斷言承接，同時檢查已選 AC、風險與情境？ |
| 第 4 輪 | 一致性。是否重複、矛盾、過期、單位混用或依賴其他案例？ |

### 8.2 在新工作階段審查

開啟新的對話／工作階段，或由另一位人員審查。
讓審查者讀取相同專案版本，並貼上：

```text
請使用 genai-test-review，讀取這個專案的
qa/review-packs/REV-001/packet.json 與 PROMPT.md。
重新閱讀已確認規格、已選範圍、操作介面依據與四輪準則。
不得從程式碼、產碼對話或目前 UI 行為推導 Expected。
每個 Finding 請列案例 ID、規則 ID、具體差異、證據及修正建議。
本次只新增審查記錄，不改寫規格、案例或進度；不重新初始化或重設已問題數。
```

請將 `REV-001` 換成實際交接包 ID。
同一對話重新讀一遍只能算 same-session；真實新工作階段才標 fresh-session。
換工作階段可減少上下文污染，但同模型仍可能延續相同偏誤，仍需檢查依據。

工具 1.4.0 的 review-pack 產生 `packet.json` 與 `PROMPT.md`，附 handoff 協定及審查 Skill 名稱。
既有包即使沒有 handoff 欄位，也可以手動指定審查 Skill，核對版本後使用。
packet 包含結構化規格／範圍／案例及來源資訊，不會自動複製所有原始檔，
也不保證自動產生 ZIP。審查者必須能讀取被引用的規格、介面文件、決策證據
與測試審查 Skill 的準則；若換到另一環境，請另外提供所需來源副本與版本資訊。
packet 的 artifact_digest 綁完整設計；review_input 可能過濾來源，不能對該子集重算 digest。
審查紀錄初始 Finding 為 open，讀不到資料或未檢完範圍時，對應輪次不列完成並記 limitations。
審查端只提交自己新增的審查檔，不直接執行會納入整個 qa 的 checkpoint，避免混入尚未交付的設計修改。

### 8.3 處理發現並重審

你可以說：

```text
請使用 genai-test-strategy，接回這份審查紀錄，沿用原專案、焦點及已問數。
F-001 請修正；F-002 請列待澄清；F-003 請保留並記錄我的處置理由。
更新受影響的案例，重新取得 digest，對修正後的版本再做必要審查。
```

正式基線需要目前 digest 對應的四輪獨立審查，以及 Finding 的實際處置。
把舊 Finding 改成 fixed，不代表新版本已經重新審查。
缺少產品規則時回到需求釐清，不為了讓審查過關而新增猜測的 Expected。

## 09. 人工核可與案例基線

### 9.1 核可前先看這些內容

- 本輪已選案例清單與可閱讀的完整內容。
- 來源版本、目前 digest 及相對上一版的差異。
- 四輪獨立審查結果及 Finding 處置。
- 未測範圍、阻塞與剩餘風險。

核可是在接受明確版本，不能只說「你看著辦」就讓 AI 代替簽核。
若你已在前一個回覆清楚核可相同內容，Skill 應沿用，不需要再問一次。

### 9.2 建議的核可說法

```text
我核可目前 digest 對應的 TC-001、TC-002，作為本輪正式案例基線。
請記錄我的核可範圍、時間與依據，建立 APP-001 和 BL-001，保存本機版本。
此次核可只涵蓋案例集；產品放行另行決定。
```

只有確實核可時才使用這段話；ID 與案例清單須換成實際內容。

### 9.3 工具與檔案順序

1. 固定 registry、案例、strategy、plan 及規格決策證據。
2. 確認四輪審查綁定目前 digest。
3. 人核可同一版本；保存真實核可回覆與 APP 記錄。
4. 執行 baseline 建立 `qa/baselines/BL-001.json`。
5. 執行 checkpoint，必要時加上 qa-baseline-BL-001 標籤。

APP 記錄包含 by、at、evidence_ref、artifact_digest、case_ids。
case_ids 必須恰好對應本輪選定的案例，不得漏列或多列。

建議把「純案例核可」的回覆保存在 `qa/approvals/APP-001-confirmation.md`，
由 `qa/approvals/APP-001.json` 引用。核可本身不必改動 registry 的規格決策，
以免核可動作又改變已審查的設計 digest。
若核可時同時要求改規則、範圍或案例，先完成修改，再對新版本重審與核可。

基線 ID 不可重複覆寫；下一版使用 `BL-002` 等新 ID。
基線代表已接受的案例版本；產品放行還需要實際測試證據與風險判斷。

## 10. 執行測試與保存證據

只有要開始實際測試時，才提出執行要求。

你可以說：

```text
請執行已核可基線 BL-001 中的 TC-001。
本次環境是「實際環境名稱」，SUT 是「實際 build 或產物 hash」。
請先核對環境、工具、前置條件及本輪授權範圍，建立新的 RUN 紀錄。
逐步保存 Actual、時間、退出碼／畫面／log 等證據，依規則判定。
無法執行或無法判定時如實記錄，不猜測成功。
```

**執行步驟：**

1. 確認實際受測產品版本。測試文件的 Git commit 不能代替產品 build。
2. 確認案例、規格、工具、資料與環境適用於這個版本。
3. 使用新的 RUN ID 執行 start-run，凍結當時設計與版本資訊。
4. start-run 只建立 NOT_RUN 記錄；接著才由人或適當工具操作產品。
5. 逐步記錄 Actual、status、時間、證據路徑及真實檔案 hash。
6. 記錄執行人、開始／結束時間、總結果與限制。
7. 執行 check-run，再檢視證據是否真的支持結論。
8. 保存 RUN 與證據的本機版本；重跑使用新的 RUN ID。

結果用語：

| 項目 | 說明 |
| --- | --- |
| NOT_RUN | 尚未執行。 |
| PASS | 前提有效，實際結果符合已確認 Expected，且有相應證據。 |
| FAIL | 前提與觀測有效，但實際結果不符合已確認 Expected。 |
| BLOCKED | 環境、權限、前置條件等阻止測試完成。 |
| INCONCLUSIVE | 有執行或觀察，但證據／判準不足以作出可靠判定。 |

工具建立紀錄不代表強制完成了全部流程管制。
例如 start-run 本身不強制核對案例已存在於某個核可基線，也不替你確認
execution／release 類型待辦是否解除；執行前仍須依 SOP 核對。
若是經你同意的探索活動，請明確記錄其目的與限制，不把它混成正式驗收。

產品有尚未提交的修改時，要另存相關差異或可辨識的實際產物。
RUN 會記 Git 狀態，但只記 HEAD 或 dirty 字樣不足以重建未保存的產品內容。
沒有原始碼的黑箱測試，可記安裝包、韌體或供應商 build 與可取得的 hash。

## 11. 每次收尾與下次續作

### 11.1 逐題保存與本輪收尾

每次回答後，AI 會先保存原始問答與獨立解讀，再依實際確認保存決策、相關規則及精簡進度，再依目前條件繼續釐清或產出案例；不必每題重寫完整案例或重產全部報告。
`session.md` 會標記待更新的案例及閱讀報告；舊視圖在重產前不能當成目前適用版本。
一般問答先保存檔案，輪末集中建立 Git 版本並依授權同步；若你已指定每題提交或同步，仍沿用你的設定。
你選先產出、已有可交付成果、明訂總上限已到或要求停止時，再執行下面的完整收尾；批次等待選擇時仍保存進度。

你可以說：

```text
請收尾：更新 registry、策略、計畫與 session.md，列出下一個動作與責任人；需要決策時才列問題。
執行 check、render，保存這輪有關的來源、案例與證據版本。
回報 checkpoint、仍未保存的檔案、阻塞及下次接續事項。
```

`session.md` 應分開記錄專案準備狀態與需求釐清進度，留下本輪焦點與預計交付、釐清預算及起算點、
預算來源與明訂總上限、時間是目標或上限及適用範圍、問題短標籤及是否計入、累計題數、本批起算點與已問／可問數、最近統整、續問狀態與選擇依據、收尾原因、
相關決策與來源版本／位置、完成事項、待更新案例／報告、未決 owner／時點、目前階段、下一題與下一步。
續作保留累計、本批額度及續問／先產出選擇，舊預算轉換依 5.1；你明訂的總限制不自動放寬。若誤計初始化，依已記錄的問題校正並說明原因，無依據的用量標未知。
完整回答與歷史留在原有決策／訪談檔案，摘要用連結定位，不持續追加全文。選先產出或明訂總上限已到時，必要問題只列待辦；等待批次選擇時不直接索答。
草稿可保存；結構檢查失敗時需說明原因，不得把「已保存」說成「已核可」。
本機模式回報本機版本；server 模式另外回報「已同步」或「待同步」、分支與最近確認的遠端版本。
登入或同步失敗時保留成果及具體下一步，不能把本機保存成功當成遠端同步成功。

### 11.2 下次續作

你可以說：

```text
請使用 GenAI 測試策略繼續這個專案。
先確認專案指引、qa/session.md、Git 狀態與來源版本。
依目前階段選取 registry、strategy、plan 與來源中的相關記錄，包含共通限制及跨功能依賴。
不要預設載入全部文件或整段歷史；有變動或摘要不足時回查原文，再從上次的下一個動作接續。
沿用累計題數、本批額度與續問狀態；等待選擇時不要直接問下一題，已選先產出時繼續做策略與案例。
只有我明確要求再釐清才恢復訪談，每批最多五題、不必問滿；舊預算依 5.1 轉換，我明訂的總限制不自動放寬。
```

換對話時務必提供同一專案資料夾及其歷史。
只貼一段舊對話，無法取代目前的專案檔案與版本。

### 11.3 減少重複上下文與 API 用量

API 是 Application Programming Interface（應用程式介面）；token 是模型計量內容的單位。
本版保留一問一答，調整每次讀取與輸出的資料量：

| 階段 | 處理方式 |
| --- | --- |
| 讀取 | 先看進度、目錄、版本與引用，再讀相關原文及必要依賴；大型記錄先篩選，不整份印入對話。 |
| 釐清 | 每題保存決策及規則；回覆新增決策與下一步，有必要決策且額度足夠才提問，編號用簡短圖例解釋。 |
| 交付 | 輪末或提前交付時集中更新完整案例，使用程式產生 Markdown／HTML。 |
| 審查 | 載入對應版本的完整已選範圍、必要規格與案例；不攜帶無關生成對話。 |

摘要保留已確認、AI 建議及未決的區別，並能回查來源編號、版本與原文位置。
跨功能限制、完整測試步驟、判定時機、證據、四輪審查及整份設計 digest 的核可要求仍適用。
來源變動或摘要不足時仍須回查；不能只依短摘要判定產品符合規格。

你可以直接說：

```text
沿用目前專案與本輪額度，只讀取相關條款及必要的共通限制。
每題先保存我的回答與規則，標記待更新案例；輪末再集中交付完整案例及報告。
請維持精簡 session，保留來源定位；如能取得 API 用量就記錄，無法取得請寫未知。
```

Skill 只能指引資料選取及工作節奏，無法自行移除宿主自動附帶的對話歷史。
`qa_project.py` 1.4.0 沒有 token 計量、費用限制或自動裁切上下文功能。拆成兩個 Skill 也不會自動移除宿主攜帶的歷史；只有實際減少載入內容才可能降低用量，不能保證節費。要使用本版的覆蓋檢查與報告，舊專案須依 Q15 更新工具。
若要硬性控制 API 帳單，呼叫程式還須配合選取上下文、取得實際用量及執行預算上限。
沒有實際量測時不宣稱已節省多少；題數上限也不等於 token 或金額上限。

## 12. 規格或產品版本變更

你可以說：

```text
inputs/requirements/ 中的規格已更新。
請比較差異，列出受影響的 REQ、AC、風險、情境、TC 與既有 RUN。
說明哪些要改寫、重審、重跑；舊基線與舊結果保留原樣。
先把無法確定的產品行為列成問題，再更新正式規則。
```

**變更處理順序：**

1. inventory 找出新增、刪除或改變的來源；再實際閱讀差異。
2. 判斷是格式調整、規則改變、來源衝突或操作介面改變。
3. 記錄人的決策、更新來源 hash 與受影響記錄的 revision。
4. 更新案例、策略或計畫並重新檢查／render。
5. 取得新 digest，進行對應版本的審查與核可，建立新基線。
6. 執行必要回歸測試，建立新的 RUN 與證據。

目前版本採保守的整份設計 digest：registry、全部案例、strategy、plan，
以及 registry 所引用的決策／確認證據 hash 都會影響它。
這些內容變動後，舊審查或核可不會自動適用於新版本。

來源實際檔案若與登錄 hash 不一致，即使你尚未更新 registry，基線檢查仍會阻擋。
目前基線檢查會檢查所有已登錄來源，並不只檢查本輪選定案例直接引用的檔案。
請釐清來源變化及保留必要歷史，不要只把 hash 換成新值來消除警告。

舊 RUN 的 case_snapshot、registry_snapshot 和 design_snapshot 代表執行當時版本，
不可回寫成新規格，再將舊的實際結果解釋為新版本已通過。

請保留原有產出，更新來源與測試案例的網頁閱讀報告。
我要看到所有來源、所有案例，以及每個案例引用哪些來源；兩邊都能互相點閱。

不需要部署網站或連上 Git server。SRC＝Source（資料來源），TC＝Test Case（測試案例），
AC＝Acceptance Criterion（驗收條件），REQ＝Requirement（需求）；數字後綴是各類流水號。

| 想看什麼 | 點閱方式 |

| 規則不完整時能做什麼 | 「探索任務」列出有時間上限的計畫、操作與觀察；這不是實測結果。 |
| 案例的完整步驟 | 點案例編號，查看環境、前置、資料、操作、預期結果、判準、證據及清理方式。 |
| 案例參考哪些來源 | 點來源編號；引用路徑會列出 TC → AC → REQ → SRC 等實際已登錄關係。 |
| 某份來源影響哪些案例 | 在來源詳情的「反查引用案例」點選案例。沒有引用的來源也會列出。 |
| 來源原文 | 看登錄摘錄與頁碼／段落，或點來源原檔連結開啟專案內文件。 |

規格依據與操作／觀測指南會標示不同用途；有連結不代表已覆蓋或已測試。
未登錄的引用、遺失的檔案及已變更的來源都會標示，不由 AI 自行補猜關係。
原檔連結須保留專案的相對目錄；只分享 HTML 時，頁內已收錄的資料與雙向連結仍可閱讀，
但不會附帶所有來源原檔。更新資料後請重新 render，網頁只是產生當下的快照。
詳細說明見 [閱讀報告指引](references/report.md)。

## 14. 本機與 Git server 版控、備份與復原

### 14.1 保存版本

**checkpoint 預設會處理：**

- qa/ 內符合追蹤條件的內容。
- `.qa-project.json`。
- 工具新建的 `.gitignore`。
- registry 明確登錄的來源檔案及規格／需求的決策確認證據。

其他未登錄的資料不會因為放進專案就自動加入 Git。
若要保存本 `README.md` 或某個未登錄資料夾，請明確指定 --include。
下列範例先確認檔案存在，再從專案根目錄執行：

```powershell
py -3 qa/tools/qa_project.py checkpoint . -m "加入操作手冊" --include README.md
```

--include 可重複指定。先檢查要納入的檔案，避免整包加入不相關內容。
被 ignore 的未追蹤檔案仍不會自動加入；用 git status 與 git ls-files 確認。

`qa_project.py` 工具本身不設定或使用 remote；選 server 時由 AI 使用連接器或 Git 工具另外同步。
因此 checkpoint 完成只代表本機已保存，遠端同步要另外驗證。
在原有 Git repo 內操作時，沿用設定；若已有 staged 內容，checkpoint 會停止，
由你先決定如何處理原有暫存內容，再繼續本輪保存。

### 14.2 看歷史與差異

在專案根目錄執行：

```powershell
git status --short
git log --oneline --decorate -10
git diff -- qa
git ls-files
```

比較兩個案例基線標籤，可在兩個標籤確實存在後執行：

```powershell
git diff qa-baseline-BL-001 qa-baseline-BL-002 -- qa
```

### 14.3 備份與搬移

最直接方式是備份整個專案，包含 `.git`、工作檔案及必要證據。
只複製目前文件而漏掉 `.git`，會失去該副本的本機 Git 歷史。

也可在專案根目錄，將已提交歷史匯出為 Git bundle：

```powershell
git bundle create "E:\Backups\Product-A-20261109.bundle" --all
git bundle verify "E:\Backups\Product-A-20261109.bundle"
```

這些是示例路徑，請先建立實際備份目錄，並使用不會覆寫舊備份的檔名。
bundle 只包含已提交歷史，不包含尚未提交的工作內容或被忽略的證據。
需要另外備份這些檔案；只有 hash 不能重建遺失的原始證據。

新專案預設 `.gitignore` 排除 `qa/evidence/raw/`，工具也會略過它的未追蹤檔案。
若將大型原始證據放在該處，請安排另外保存，並保留明確位置及 hash。
本機 Git 是版本歷史；要防止整個磁碟或工作區遺失，仍需另外備份。

### 14.4 復原

建議先讓 AI 顯示差異並準備可檢視的復原內容：

```text
請比較目前版本與 BL-001 對應的 checkpoint。
我想取回當時 TC-001 的內容，先輸出到新的比較檔並說明差異。
不要覆寫目前工作或刪除歷史；待我確認後再套用。
```

可用保留歷史的方式還原選定變更。不要為了復原單一案例，直接清除整個工作目錄。
已建立的基線 ID 與標籤保留原指向；改版使用新的 ID／標籤。

### 14.5 Git server 登入與同步

你可以說：

```text
這個專案要使用 Git server 版控，請協助我登入並連到指定儲存庫。
已提供的服務、網址與選擇請沿用；其他資訊一次只問一項。
```

**操作順序：**

1. 提供 Git server 或儲存庫網址，例如你自己的 GitHub、GitLab 或公司服務。
2. AI 檢查可用連線；已登入正確帳號且可存取目標時沿用，未登入才啟動官方連線／授權流程。
3. 你在官方介面完成登入及驗證，再由 AI 查核帳號和儲存庫權限。
4. 若尚無儲存庫，逐步決定新建名稱、所屬帳號／組織及私人或公開；若已有儲存庫則核對網址與分支，保留原內容。
5. AI 列出本次要保存的檔案；已有明確上傳範圍便直接執行，尚未決定來源文件或證據是否上傳時才補問。
6. 保存本機版本並同步，讀回遠端分支及檔案，回報實際完成狀態。後續收尾沿用設定，不反覆要求同一份授權。

**需要在自己電腦登入時：**

如果 AI 無法直接操作你的終端機，它會引導你在實際存放專案的環境執行。
先確認對應命令已安裝；以下範例由 AI 依主機及工具版本選用，不必全部執行。

| 服務 | 檢查登入 | 尚未登入時開啟官方流程 |
| --- | --- | --- |
| GitHub | `gh auth status --hostname github.com` | `gh auth login --hostname github.com --git-protocol https --web` |
| GitLab | `glab auth status --hostname gitlab.com` | `glab auth login --hostname gitlab.com --git-protocol https --web` |

公司自架服務使用自己的主機名稱與登入方式；必要的企業授權由管理員提供。
登入某個連接器或網頁，不代表本機 Git 已登入，AI 會依實際使用方式驗證。
請在官方登入介面完成密碼、驗證碼與安全金鑰操作，不將 token 或私鑰貼到對話。
命令參考及詳細處理見 [Git server 指引](references/git-server.md)。

登入取消、權限不足或網路暫時不可用時，需求與案例工作可以繼續；進度會記為「server 模式／待登入或待同步」。
AI 不會改成假稱同步成功，也不會強制覆蓋遠端歷史。遠端已有內容時先接手正確工作副本，再初始化 qa/。
Git push 會包含相關分支歷史；若只用連接器上傳檔案快照，會明確說明，不能宣稱完整本機歷史已搬過去。
儲存庫只保存實際提交及同步的內容；未提交或排除的原始證據仍須依 14.3 另外備份。

## 15. 進階命令列速查

### 15.1 第一次初始化

通常由 AI 依已安裝 Skill 的實際路徑執行，你不必猜測技能安裝位置。
若你已在本機取得完整 Skill 目錄，可使用以下形式：

C:\Skills\... 是示例，必須替換成實際存在的 `qa_project.py` 路徑。

初始化後，工具副本才會位於專案的 `qa/tools/qa_project.py`。

如果專案位在另一個 Git repo 內，先確認真正要用的根目錄。
只有確實要建立獨立的巢狀 repo 時才明確使用 init 的 --standalone。
不要把這個選項當成所有路徑錯誤的通用解法。

### 15.2 一般命令

先進入實際專案根目錄：

```powershell
Set-Location "D:\Projects\Product-A"
```

```powershell
py -3 qa/tools/qa_project.py --version
py -3 qa/tools/qa_project.py --help
```

```

```

問答紀錄（工具 1.6.0；通常由 AI 代為操作）：

輸入欄位見 [成對問答紀錄](references/interview-records.md)；輸入檔為暫存傳遞副本，成功後刪除代理自己建立的暫存檔。show-qa 不帶編號只列索引，帶編號才讀完整原文；record-qa 不會自動建立產品決策、增加需求題數或核可。

### 15.3 核可基線命令

以下命令的前提是已完成目前版本的獨立審查，並具備真實 APP 核可記錄。
它們不會替你產生人類同意，也不會自動補完審查。

```powershell
py -3 qa/tools/qa_project.py check . --gate baseline
py -3 qa/tools/qa_project.py baseline . --id BL-001 --approval qa/approvals/APP-001.json
py -3 qa/tools/qa_project.py checkpoint . -m "核可 BL-001" --tag qa-baseline-BL-001
```

check --gate baseline 檢查基線前的結構、來源、選定覆蓋及審查條件；
真正 baseline 命令還會讀取 --approval 指定檔案，核對人員、依據、digest 與案例清單。

### 15.4 執行紀錄命令

先將 TC ID、產品版本、環境與 RUN ID 改成真實內容，並完成執行前核對：

```powershell
py -3 qa/tools/qa_project.py start-run . --id RUN-001 --case TC-001 --sut-version "build-5.1.0" --environment "QA-LAB-A / 實際工具版本"
```

這只建立 NOT_RUN。實際執行及填寫紀錄後，再執行：

```powershell
py -3 qa/tools/qa_project.py check-run . --id RUN-001
py -3 qa/tools/qa_project.py checkpoint . -m "保存 RUN-001 與執行證據"
```

所有 ID 都是示例；已存在的 review-pack、BL 或 RUN 請換新 ID，不要覆寫歷史。
命令的 . 表示目前專案根目錄，也可改成加引號的完整根目錄路徑。

### 15.5 各命令實際會做什麼

| 命令 | 作用與限制 |
| --- | --- |
| init | 建立結構及工具副本；不自動建立第一個 commit。 |
| inventory | 記錄來源檔案的盤點變化；不自動讀懂或採納產品規則。 |
| check | 檢查已整理記錄的結構；不執行產品測試。 |
| render | 從 registry 與 cases 產生原有 Markdown 視圖、編號字典與可點閱的 report.html。 |
| digest | 列出目前設計內容的識別值。 |
| checkpoint | 對符合範圍及條件的檔案建立本機 Git commit。 |
| review-pack | 建立審查輸入與提示；不替你完成獨立審查。 |
| baseline | 核對現有記錄後凍結案例基線；不核准產品放行。 |
| start-run | 建立一次執行的快照與空白結果欄位；不呼叫 SUT。 |
| check-run | 檢查 RUN 記錄與證據 hash；不取代證據內容的判讀。 |

## 16. 常見問題與處理方式

### Q1：AI 說讀不到 D:\Projects\Product-A。

確認 AI 實際運行在哪裡。瀏覽器中的對話不會因為看見路徑就取得磁碟權限。
在能讀寫該專案的工作環境使用，或提供可存取的專案資料副本。

### Q2：工具說 Git is required，或 py／python 找不到。

在執行工具的環境準備 Git 與 Python 3.10+，確認命令可用後重試。
自己電腦已安裝，不代表另一個遠端工作區也已安裝。

### Q3：工具說 Not initialized，或 Project root must be the exact Git worktree root。

回到正確的專案根目錄。新專案先由 Skill 的原始工具執行 init。
不要把 qa/ 子目錄當成根目錄，也不要在父 repo 裡不加判斷地另建歷史。

### Q4：已有非空 qa/，初始化停止。

先確認那個目錄的用途。由 AI 比較現況並提出遷移或使用別的專案根目錄方案。
不要直接刪除 qa/ 來讓命令通過。

### Q5：出現 Existing staged changes preserved。

用 git status 與 git diff --cached 查看原有暫存內容。
先由原工作負責人決定提交或取消暫存，再繼續 checkpoint。
Skill 不會把這些原有變更混進自己的提交。

### Q6：source missing or changed。

檢查來源是否搬移、刪除或更新。重新讀取差異，更新決策及引用，再登錄真實 hash。
盤點出變化後，不能只改 hash 而跳過影響分析。

### Q7：案例是 blocked，或工具拒絕 unconfirmed AC。

查看 blockers 對應的 Q：可能缺產品規則、環境、操作介面、權限或觀測方法。
補足後由 AI 更新規格與案例；不要只把 status 改成 ready。

### Q8：Missing current independent review rounds。

目前版本缺少四輪新工作階段／人員審查，或審查的 digest 已過期。
檢查 review 的真實 independence 與 artifact_digest。
不能把 same-session 改成 fresh-session 來跳過審查。

### Q9：Approval is stale，或案例清單不符合。

APP 必須綁定目前 digest，且 case_ids 恰好等於 `scope.selected_case_ids`。
若內容已變，重新審查並取得對新版本的核可；不要竄改舊核可記錄。

### Q10：核可完就出現新的 digest。

檢查是否把純案例核可追加到 registry 或原規格決策檔。
按第 09 節，將純核可記錄放 `qa/approvals/`，避免改動已審查的設計資料。
若實際有產品規則或範圍改變，就應該產生新 digest 並重走審查流程。

### Q11：run PASS 被拒絕，或 evidence hash mismatch。

確認每一步的 Actual、時間、狀態與證據完整且一致。
證據被改動或遺失時保留問題，必要時重新執行；不要改 Expected 或假填證據。

### Q12：review-pack 已存在、baseline 已存在、RUN 已存在或 tag 已存在。

換新的 ID／標籤。歷史紀錄保留，不覆蓋同名舊版本。

### Q13：顯示 No changes to checkpoint。

表示這次範圍內沒有可提交的差異，不會新增 commit。
此版本工具在這種情況也不會因 --tag 而另外建立標籤。
若只是要為既有 commit 加新標籤，請明確要求 AI 核對 commit 後另行處理。

### Q14：資料夾裡有檔案，為什麼 Git 沒有保存？

檢查是否登錄為來源、是否使用 --include、是否被 `.gitignore` 排除。
symlink、常見私密檔名、虛擬環境、`.git` 內容及 raw 證據目錄有排除處理。
這些規則不是完整機密偵測；提交前仍需確認實際清單及應保存的內容。

### Q15：Skill 更新後，專案內工具仍是舊版，沒有網頁報告。

專案工具是初始化時的副本；重跑 init 不會升級它。
1.1.0 新增文件中的編號說明與 `qa/id-glossary.md`；舊版不會自動產生。
1.2.0 新增雙向超連結閱讀報告 `qa/report.html`；需更新專案內工具，再執行 render。
1.3.0 新增方法／覆蓋項目、共用及推導判準欄位、探索任務與報告。新專案採用 `coverage-items-v1` 設計政策。
1.5.0 新增需求風險評估與 severity 等欄位、risks.md 與網頁風險表；舊專案新基線須依 [需求風險評估](references/risk-assessment.md#檢查與舊專案) 補本輪資料，舊快照不改寫。

1.4.0 在審查包新增 handoff 欄位，並將提示交給 `genai-test-review`；schema 1 與原基線要求不變。1.3.0 包仍可手動交接，審查端不另帶一份專案工具。
但 AI 當輪回覆仍應遵守最新的編號解釋規則。
請 AI 比較新舊工具，先保存 checkpoint，再明確安排升級與相容性檢查。

升至 1.3.0 後，舊 schema 1 專案仍能 draft 檢查、編輯、render 及讀取舊執行記錄；未採用覆蓋項目時顯示提醒。**建立新基線前**，由 AI 補齊本輪方法與覆蓋項目、連結案例斷言、呈現差異，再設定 `project.design_policy="coverage-items-v1"`，對新 digest 重審與核可。既有產品決策不重問；只有新增取捨需要決策。舊基線和舊結果保持原樣。

### Q16：Windows 安裝驗證在建立「規格 #1?.md」時錯誤。

舊測試程式使用含 `?` 的檔名建立測試資料；Windows 將 `?` 視為檔名保留字元，
因此在測試準備階段就中斷，尚未驗證到 HTML 連結功能。這是測試資料的跨平台問題。
1.9.1 的測試修正改用 Windows 合法、仍含中文、空白、`#`、`%` 與 `&` 的檔名，
檢查連結編碼、解碼後檔案及 HTML 內容逸出；含 `?` 的額外變體只在非 Windows 執行。
共用的 HTML 測試不會因 Windows 而跳過。此修正不更動專案資料或 `qa_project.py` 的版本。

在更新後的 Skill 資料夾執行：

```powershell
py -3 -m unittest discover -s scripts -p "test_qa_project.py" -v
```

若看到 `Symlinks unavailable`，表示該環境無法建立符號連結，對應測試記為 skipped，
不可算成通過；其他 skip 也須查看實際原因。Linux 通過不代表已完成原生 Windows 驗證。
依既定升級條件處理剩餘錯誤與跳過項目，不刪除測試或把錯誤改成跳過來宣稱通過。

## 17. 通用案例模板與跨專案使用方式

### 17.1 先填自己的內容，不選預設產品

各專案共用的是釐清、追溯與案例完整度要求，不是產品規則。
本 Skill 不要求你使用某種產業、框架、資料模型或測試工具。
[templates.md](references/templates.md) 提供結構化草稿；以下是方便對話使用的通用格式。
「待填」只是提醒，不是可執行內容；關鍵項目缺漏時必須保留 draft／blocked。

**案例 ID／修訂：**

使用本專案的 TC ID 與 revision。

**測試目的：**

指出要發現的具體失敗情境，而非只寫功能名稱。

**規格與風險依據：**

已確認 REQ／AC、來源版本及定位資訊、對應風險與已選情境。

**環境與操作介面：**

真實 SUT build、平台、工具版本，以及已確認的 UI／API／CLI／設備介面。

**前置條件：**

列出建立獨立初態的操作，以及如何確認初態成立。

**測試資料：**

實際值或檔案、格式、單位、建立方式與可核對的內容。

**操作步驟：**

1. 在確切位置執行具體操作，列出輸入及需取得的觀察。
2. 以已確認的完成事件／時機判讀；不可自行猜一個等待秒數。
3. 對每項觀察列出 Expected、AC 依據及要保存的證據。

依真實流程增減步驟，不要把本段概述直接當成完成的測試案例。

**判定：**

何時可判 PASS、何時是 FAIL，以及何種缺口造成 BLOCKED／INCONCLUSIVE。

**清理與重跑：**

清除或恢復本案狀態並驗證；重跑可獨立建立前置，不依賴其他 TC。

**實際執行：**

設計階段不填 Actual、不宣稱 PASS；真的執行後另記在 RUN。

你可以貼上：

```text
請用上述完整度要求，依我的專案資料展開已選情境。
不要把模板欄位名稱當成操作步驟，也不要憑空命名按鈕、API 或命令。
每筆案例都要讓另一位測試人員能獨立照做並判定。
缺少介面或規則時建立 Q／blocker，繼續完成不受影響的案例。
```

### 17.2 不同專案會有不同問題與證據

**Web／App：**

若涉及編輯取消，需確認取消影響哪些狀態，再確認實際按鈕、頁面與觀察時機。
可用操作記錄與重載後畫面作證，但保存承諾需有相應觀測依據。

**API／服務：**

先確認契約、認證與合法資料，再填實際 request、response 及後端效果的判準。
工具退出成功不代表 HTTP 狀態與回應內容符合產品規格。

**資料處理／批次匯入：**

先釐清錯誤資料如何處理、交易範圍及完成時點，再設計具體輸入檔與前後差異。

**Linux／網路／部署：**

從已確認的目標狀態、拓樸與環境出發，設計操作、狀態核對、重跑及復原。

**設備／嵌入式：**

依實際介面及設計承諾，區分輸入、控制輸出與實際設備反應的證據。

**GenAI／agent 產品：**

只有被測產品本身涉及這類能力時，才加入輸出評判準則、資料集、
工具權限、非確定性及執行軌跡等專屬內容；其他專案不用硬套。

這些是選擇提問方向的提示，不是預先核可的風險、範圍或驗收條件。
更多指引見 [domain-adaptation.md](references/domain-adaptation.md)。
需要具體案例示意時，可請 AI 選讀 [worked-example.md](references/worked-example.md) 的相關小節。
各示例獨立且有自己的教學前提，不可匯入新專案當正式規格。

### 17.3 最短的使用順序

先回答有沒有已知規格；再建立或選定專案資料夾；選本機或 Git server 版控，選 server 時協助登入；
有文件時指出位置並讀稿，無文件時逐題訪談；
確定本輪焦點與釐清預算；一次回答一個重要分歧，逐步確認可驗證規則；
選定風險與情境；把真實操作、資料、判準及證據補齊成完整 Test Case。
到限就交付本輪成果與未決清單，未受影響的工作可先完成。
需要正式案例集時再完成四輪審查及人工核可；要驗證產品時另外實際執行。

## 18. 每階段完成檢查表

**開始工作：**

- [ ] 已先確認有沒有已知規格，分清有文件、只有口頭規則及尚無規格，已回答的資訊沒有重問。
- [ ] 已依選擇建立或接手專案資料夾，記錄需求草稿位置或無文件狀態。
- [ ] 已選擇本機或 Git server 版控並保存偏好；server 模式已驗證登入／儲存庫，或明確記錄待處理項目。
- [ ] 已辨識自己的專案與本輪目標，沒有把示例規則當成專案需求。
- [ ] 已分開記錄專案準備狀態與本輪需求題數，初始化不計入；預算來源清楚，同一輪續作沒有歸零，使用者的題數及整場時間限制仍被遵守。
- [ ] 所有展示的編號都有英文來源、中文意思、用途與後綴說明；未知含義未被猜補。
- [ ] 要保存檔案時，AI 能讀寫正確專案根目錄，Python 與 Git 可用。
- [ ] 已閱讀 session、來源與 Git 現況，知道這輪目標。
- [ ] 已分清正式規則、建議、未決事項及現況觀察。

**完成規格與策略：**

- [ ] 已確認規則有來源或真實決策支持。
- [ ] 未決事項有 Q ID、責任人或 unassigned、確認時點與影響。
- [ ] AC 可觀測、可判定；邊界、時機與容差沒有偷偷補假設。
- [ ] 每筆已登錄需求有風險評估狀態；本輪評估、需求關聯、嚴重度／可能性／優先序與理由可追溯，未評估不當成無風險。
- [ ] 本輪風險排序、範圍與暫緩項目已記錄；已選有案例，其他關聯風險有取捨、剩餘風險與決策。
- [ ] 每批最多五題後統整並等待續問／先產出選擇，未自動追加產品問題；選先產出就交付並保留缺口，足夠交付時提早產出；累計、本批狀態與使用者明訂總限制均沿用。
- [ ] 到限已收尾，未決事項按實際影響保留阻塞；未把逾時、沉默或延長當產品決策。

**完成案例設計：**

- [ ] 寫本批案例前已呈現已知條件、狀態、來源與缺口；摘要未把草稿／觀察升格為規格，未要求重複核可。
- [ ] 每筆案例都有具體初態、資料、操作、時機、觀測、斷言與證據要求。
- [ ] 已依規則特徵選方法、列覆蓋項目，案例與斷言有對應；共用判準沿用實際確認，探索計畫與實測觀察分開。
- [ ] 每個 Expected 都能追溯到已確認規則。
- [ ] 案例可獨立重跑；實際介面與引用的輔助檔案都有版本資訊。
- [ ] registry／cases 已更新，生成視圖已 render，結構檢查結果已處理。
- [ ] `qa/report.html` 已更新；來源與案例能雙向點閱，引用缺口及來源異動已如實標示。

**建立正式案例基線：**

- [ ] 新基線採 requirement-risk-v1，本輪需求評估已確認，分級有依據，關聯風險有案例或暫緩決策；未選需求可保留未評估。
- [ ] 本輪已選 AC／風險／情境有案例及具體斷言承接。
- [ ] 新基線採 coverage-items-v1；已選 AC 至少各有保留覆蓋項目，全部保留項目由已選案例斷言承接，暫緩項目有決策與剩餘風險。
- [ ] 目前 digest 的四輪獨立審查已完成，Findings 已有真實處置。
- [ ] 人已核可相同內容與確切案例清單。
- [ ] APP、BL 及 checkpoint 已保存，舊基線未被覆寫。

**完成實際測試：**

- [ ] 實際 SUT build、案例、環境、工具與初態可辨識。
- [ ] RUN 記錄實際觀察及證據，未執行項目沒有假填 PASS。
- [ ] check-run 與證據判讀已完成，阻塞、缺陷與剩餘風險已記錄。
- [ ] session 與本機版本已保存；必要的原始證據與歷史有備份。
- [ ] server 模式已讀回確認同步結果，或清楚標示仍待同步，沒有把本機保存當成遠端成功。

日常最常用的收尾指令：

```text
請保存本次成果，更新 session，說明剩餘風險，並告訴我下次接著做哪一件事。
```
