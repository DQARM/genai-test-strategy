# 效能選案規則

先找出本輪哪個驗收條件或風險需要量測。引用已確認的驗收條件（AC，Acceptance Criterion）或已登錄的風險，摘出影響選案的原句，例如「尖峰時仍須達標」或「佇列累積後可能無法恢復」。用下表選能回答該問題的子類。一般功能規格只有在出現具體效能承諾或失效線索時才展開。子類術語可參考 [ISTQB Performance Testing §1.2](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB-CT-PT_Syllabus_v1.0_2018.pdf)。

| 需求或風險要回答什麼 | 選用的子類 | 模型列與觀測 |
|---|---|---|
| 在約定的典型或尖峰工作量下能否達標？ | 負載 `load` | 每種約定負載一列，維持工作組合，按指定時窗量吞吐、延遲或錯誤率。 |
| 超出預期負載或可用資源減少時，哪裡開始失效？卸載後服務能否恢復？ | 壓力 `stress` | 分開記錄基準、加壓、卸載及恢復觀測。寫出停止條件與復原方式；超載容許行為及恢復門檻各自需要依據。 |
| 持續運作後是否逐漸退化？ | 耐久 `endurance` | 維持指定負載與時長，在可比較的早、中、晚區段觀察退化趨勢及資源使用；保留各段資料。 |
| 隨用戶數、資料量或配置成長，效能是否仍符合成長目標？ | 擴充性 `scalability` | 明列成長維度、比較組、固定條件與預期關係。要主張加節點有效，就比較不同節點配置下相同工作模型的結果。 |
| 固定配置最多能承受多少工作量，仍滿足品質門檻？ | 容量 `capacity` | 逐級調整工作量並記各級指標，界定已證實達標的範圍及最先失守的觀測點。 |
| 流量突然暴增又回落時，能否及時回穩？ | 突波 `spike` | 列突升與回落的幅度、速率、時點，觀察事件期間及回落後的表現。 |
| 特定操作必須同時發生，可能造成爭用或排隊嗎？ | 併發 `concurrency` | 列同時操作的對象、數量及同步點，觀察等候或完成時間。多條連線也可能只是負載配置，依這次要驗證的承諾選案。 |
| 單一操作有量化承諾，且沒有負載變化等特定問題？ | 一般量測 `measurement` | 例如在已指定配置下量啟動時間，明列起訖事件、觀測點及重複方式。 |

## 把選擇落實到案例

1. 在方法選用紀錄（DES，Design）沿用 `technique: measurement`。對新選的效能目標填 `measurement_profile`，其中 `subtype` 取上表代碼，`trigger` 寫觸發原句或風險，`workload` 寫負載形狀與關鍵操作條件，`metric` 寫觀測位置、指標、單位與統計方式，`acceptance_basis` 寫已確認條款或決策及對應門檻。這些欄位均為文字。沿用 DES 的 `ac_ids`、`risk_ids`、`question_ids` 追溯來源。兩種子類回答不同問題時各建一筆 DES；同子類的多個負載點放在同一筆的 `model_rows`。
2. 在模型列及案例補足會改變結論的條件，如流量方向、單流或多流合計、請求組合、配置、取樣端、暖機與量測時窗、重複次數。按約定記錄比較運算、統計量及各條件的門檻。對加壓或長時試驗，列可用的負載來源、工具容量、停止與復原條件。工具飽和、量測缺段或條件不符時，保留原始數據與限制，將受影響判定列為無法判定。
3. 選案與驗收分開處理。知道要驗哪項表現，缺門檻或負載定義時，寫 `applicability: applicable`、`selection: pending`；`acceptance_basis` 可留空，將影響結論的缺口連到真實問題。能否適用也未知時，適用性填 `unknown`。已有可執行探索就記探索任務，結果留作觀察。只有部分規則已確認時，可採用已確認部分，讓其餘模型列保留空預期、空覆蓋清單及問題。已決定延後才填 `defer`，並沿用既有取捨與剩餘風險規則。
4. 策略或對話草稿顯示「觸發依據｜所選子類｜工作負載｜指標｜判準或待釐清」。對採用的模型列，讓報告可從該 DES 查到覆蓋項目、實際案例步驟及其斷言；執行結果沿用實測紀錄。舊量測紀錄可維持原狀，缺少子類時保留未指定。

## 已有量測資料時如何判讀

以下為虛構的 TCP 吞吐量資料。單一連線量得 640 Mbps，16 條同時連線合計 920 Mbps。兩筆觀察分別保留，先核對設備配置、方向、接收端、時窗和統計方式。僅在其餘約定條件均相符時，作以下判定。

| 已確認的規則 | 可採用的觀察 | 判讀 |
|---|---|---|
| 單一連線至少 900 Mbps | 單流 640 Mbps | 單流未通過。 |
| 16 條連線合計至少 900 Mbps | 16 流合計 920 Mbps | 16 流合計通過。單流另有承諾時另判。 |
| 只寫「TCP 吞吐至少 900 Mbps」 | 兩筆保留各自負載標記 | 待確認門檻適用的連線數及彙總方式。驗收暫無法判定。 |

若手上只有數據，先登錄其來源及量測條件；要用舊數據支持本輪結論，再核對版本與步驟證據。兩個流量點可用來比較實測差異；若要宣稱硬體擴充或長時運作達標，另外找出對應的配置或時間序列證據。
