# Git server：登入與同步

只有使用者選擇 server 模式，或明確要求連線／同步時才展開此流程。保留本機 Git；server 用來保存及協作，不要求建立 CI/CD 或自動化產品測試。`qa_project.py` 維持本機工具，登入及同步由代理使用可用連接器或 Git 工具完成。

## 1. 逐題確定服務與儲存庫

- 先沿用對話、session 或使用者指定的儲存庫網址。未知時只問：「你要使用哪個 Git server？可提供 GitHub、GitLab 或公司自架服務的網址。」不要同時索取帳號、密碼、分支及全部設定。
- 只從實際網址辨識主機；不能將所有 server 當 GitHub。只有服務、沒有儲存庫時，下一個決策才是使用現有儲存庫或新建。既有 remote 先比對目的地，不覆寫別人的設定。
- 使用現有儲存庫時取得並驗證網址與實際分支。新建時逐步取得名稱、所屬個人／組織與可見性；已有明確指示則沿用。可建議私人，但不能把私人內容自行公開。
- 選 server 並指定儲存庫，表示要在該目的地保存專案；只對缺少的設定提問。首次同步前整理具體檔案範圍；已有明確上傳範圍就執行，尚未決定哪些來源／證據可上傳時只釐清範圍。不把本機全部歷史、其他專案或 raw 證據默認納入。

## 2. 協助登入，使用者完成身分驗證

依序選擇可用方式，不要求使用者自己摸索整個登入流程：

1. **連接器可完成任務：** 先檢查該服務的現有連線、帳號及目標儲存庫權限。可用就沿用；未連線時啟動平台提供的正式連線／授權流程，讓使用者在官方頁面完成登入。依當下工具及文件引導，不虛構設定選單或授權網址。
2. **需使用本機 Git：** 在真正存放專案的環境檢查命令列工具及登入狀態。未登入才協助開啟官方瀏覽器登入；已登入的正確帳號不重登。工具無法執行時提供下列對應命令，讓使用者在自己的終端機執行；不能假稱遠端環境的登入會自動登入其電腦。
3. **公司自架或其他服務：** 依該主機的官方登入指引及公司的存取方式處理，包含單一登入或已配置的 SSH（Secure Shell，安全殼層）金鑰。缺少必要權限時指出具體缺口與下一步，不猜登入 API，不以關閉憑證驗證繞過失敗。

先查安裝版本及 `--help`，再使用對應參數。下列是常見主機的命令，實際主機須依使用者網址替換：

| 服務 | 先檢查 | 未登入時 |
| --- | --- | --- |
| GitHub | `gh auth status --hostname github.com` | `gh auth login --hostname github.com --git-protocol https --web` |
| GitLab | `glab auth status --hostname gitlab.com` | `glab auth login --hostname gitlab.com --git-protocol https --web` |

CLI 是 Command-Line Interface（命令列介面）。GitHub Enterprise 可使用實際主機的 `--hostname`；GitLab 自架的瀏覽器登入視伺服器設定可能需要管理員先設定 OAuth 應用程式，不能保證所有主機直接適用。

登入過程中，密碼、驗證碼、Passkey、安全金鑰及授權確認由使用者在官方登入介面完成。不要要求貼到對話，不將 token、私鑰或含憑證網址寫進專案、命令參數或紀錄。需要 token 的服務由使用者在官方認證介面／憑證管理工具輸入；不要呼叫顯示 token 的命令或 `--show-token`，不讀出認證檔。

若登入流程需要設定 Git 憑證管理工具，說明作用並沿用現有可用設定；不要改 Git 全域作者姓名／信箱。連接器、瀏覽器與本機 Git 的登入狀態分別確認，不能互相推定。登入完成後重新查帳號，再查指定儲存庫的存取及寫入權限；可讀不等於可寫。沒有權限資訊時標「寫入權限待驗證」，不用建立測試提交來探權限。

## 3. 接手專案並保存

- **遠端有內容、資料夾空白：** 透過可用工具取得正確工作副本；若需本機歷史，clone 到選定根目錄後再跑 init，沿用已有 `qa/` 進度。
- **資料夾已有文件或歷史：** 先檢查目錄、分支及差異。若已指向正確 repo，沿用；遠端也有獨立內容時先在另一個不衝突位置取得它，再準備合併方案。不可 clone 覆蓋、強推或自動合併不相關歷史。原資料完整保留。
- **全新空儲存庫：** 初始化本機專案，建立第一個 checkpoint，再加入使用者指定且不含憑證的 remote 及分支。不得硬設 main 或替換原有 origin；先讀現況再決定。
- 本機和遠端都要核對本輪納入的檔案。Git push 會帶出該分支可達的既有提交，`.gitignore` 不能移除歷史裡已提交的內容；若既有歷史超出已定上傳範圍，先停止該次上傳並說明具體差異，保留歷史與本機成果。
- 例行收尾先 checkpoint，再同步已確定的分支與範圍。Git 使用正常非強制 push；連接器寫入需基於讀到的分支版本，保留其他檔案。標籤只同步明確選定者，不自動推送全部分支或全部標籤。
- 遠端已更新、分支保護或權限不足時，先讀實際狀態；需要時用工作分支與變更請求，不繞過保護或 force push。實質合併衝突整理差異後請人決定；可以繼續不受影響的需求工作。
- 使用連接器只上傳檔案時，記錄本機 checkpoint 與遠端提交的對應及檔案清單；這不等於移轉本機完整歷史。需要保留完整 Git 歷史時使用支援 Git 傳輸的方式，不用快照冒充。
- 同步後讀回目標分支及檔案，核對版本／內容。Git push 應核對遠端與預期 commit；連接器建立新 commit 時核對內容及對應關係。只在有成功回傳及讀回驗證後報「已同步」。

## 4. 保存狀態與失敗後續作

在 `qa/session.md` 維護精簡版控區塊，不新增另一份資料庫、不改產品規則。只保存非機密資訊：

- 模式：`local`（本機）或 `server`（本機＋遠端）。
- server 模式的服務、無憑證儲存庫網址、分支、上傳範圍、所用連線／帳號名稱。
- 登入狀態：已確認／待登入／權限待處理；同步狀態：未同步／已同步／待同步。
- 最近確認的遠端提交、對應本機 checkpoint 或同步檔案清單、確認時間、下一步。這是最近一次驗證結果，不承諾其後遠端未改動。

登入或網路失敗不阻塞需求釐清；明確記 server 模式待處理，在可存取的本機工作區保存成果。若尚未取得遠端工作副本，避免建立混淆的新歷史，可先保留草稿，待接手正確 repo 後整理。使用者取消登入時不重複催促、不默默改其模式。不得把「已開啟登入頁」「本機 commit 完成」或「產生上傳指令」寫成「已連線／已同步」。

下次續作沿用選擇，只有在要連線時重新確認實際認證與權限。不要為了把同步成功的狀態回寫再同步而無限產生提交；session 記最近一次已核實結果，後續版本正常承接即可。
