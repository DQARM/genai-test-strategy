# 共用判準與探索任務

AC＝Acceptance Criterion（驗收條件）；DEC＝Decision（人的決策）；SRC＝Source（資料來源）；EXP 取自 Exploration（探索），表示探索任務；TC＝Test Case（測試案例）。後綴是類別流水號或已說明的專案標籤。

## 重用已確認判準

先查已確認的專案規則與共用期望；同一規則在適用條件不變時直接重用，不逐案例詢問。先列 AI 建議及其理由，由有權決策的人確認一次，記成 DEC、已確認需求與 AC；原回答可支持多項記錄。沒答案就維持 proposed，不把未答清單整批採納。

`oracle.kind` 說明判準如何取得；確認狀態與核可依據是另一件事：

| kind | 用法 | 需要寫清楚 |
|---|---|---|
| `specified` | 明確規則，來自採納文件或人的明確決策 | 條件、觀察點、時機、容差、規則依據。 |
| `derived` | 已確認蛻變關係、參考實作或版本比較 | DEC、適用條件、比較關係、限制；使用參考產物時登錄檔案、版本及 hash。 |
| `implicit` | 團隊採納的共用期望，例如特定操作不得破壞既有資料 | DEC、適用條件、觀察方式及例外／限制；不自動套用到所有專案。 |

人確認後，這些都成為有依據的 AC；每個案例仍引用已確認 AC，不另開一條能繞過確認的路徑。原始觀察、經驗清單或參考程式本身不是產品的正確答案。

隱含式期望也有邊界：例如故障復原可能允許特定重新啟動；不能把「不當機」解讀成任何情況都不能重啟。「不可毀損資料」要界定資料範圍、前後比較與例外，不能只寫口號。

推導式判準的例子是「在本專案已確認無排序語意的輸入集合中，重新排列資料後，總計應保持相同」。排序是否無語意必須有依據。相同輸出只支持這個關係，不證明絕對答案正確。版本比較也須先排除已知預期變更；兩個實作可能共享同一缺陷。

GenAI／agent 產品可考慮輸入重述、無關資料增減等蛻變關係，但關係、評估方式、容差與抽樣／重跑條件都須由本專案確認。這些方法也適用非 AI 產品，不把任意重述都假定等價。

## 沒有完整判準時先形成探索任務

在可用、已授權的環境中，讓測試人員以有時間上限的任務學習產品、收集資訊。設計探索任務不代表已授權或已執行；沿用既有執行授權，缺少時先交付計畫。遇到未知產品行為，不必等所有問題答完才產出任務。

探索仍需要可用的操作、可確認初態及觀察方法。缺少這些資訊時保留 draft，交工程或測試負責人補操作依據，不反覆把工具問題問給 PM。探索時間上限是工作安排，不是產品回應時間門檻。

來源 kind=`experience` 可保存缺陷清單、維修紀錄或團隊經驗，用來找候選情境。候選 `origin` 可為 specification／experience／mixed，並附 source_refs。經驗只回答「值得查什麼」；判定產品是否符合承諾仍依已確認 AC。

## 探索任務模板

寫入 `registry.charters`，另由工具生成閱讀視圖。以下是尚未可執行的空白模板，不當成 ready：

```json
{
  "id": "EXP-001",
  "title": "填入本輪要了解的行為",
  "status": "draft",
  "mission": null,
  "scope": [],
  "timebox_minutes": null,
  "source_refs": [],
  "binding_refs": [],
  "ac_ids": [],
  "question_ids": [],
  "preconditions": [{"action": null, "verify": null}],
  "actions": [{"action": null, "observe": null, "evidence": null}],
  "stop_conditions": [],
  "cleanup": [{"action": null, "verify": null}]
}
```

`ready` 表示探索計畫具備必要操作條件，不代表產品有完整規格或已測試。已知 AC 可用於局部判定；沒有已確認判準的部分只記觀察。任務可沒有 ac_ids，但不能因此替代正式測試案例或滿足其覆蓋。

## 執行紀錄與發現處理

實際探索時另建 `qa/evidence/EXP-001/<本次唯一名稱>.md`，不在任務設計裡填 actual、result 或 findings。每次保留：

- 任務版本／當時設計 digest、受測版本、環境、工具、執行人、開始與結束時間。
- 實際建立的初態、每次操作與具體輸入、時間、觀察、原始證據路徑及 hash。
- 已引用的 AC，以及哪些觀察符合／違反該判準；未定義行為標示「待確認」，不硬判 FAIL。
- 發現、重現步驟、影響、未查範圍、下一個動作與責任人，以及清理結果。

違反已確認規則的發現可登錄缺陷；欠缺規則的發現轉成待釐清問題或改善建議。要成為回歸案例時，再依已確認規則建立獨立前置、步驟與斷言，完成審查。新增發現不自動擴大本輪範圍或重設提問額度。

目前工具只檢查任務設計，不自動執行探索、不檢查探索 Markdown 的實測真實性，也不把探索紀錄彙總成正式通過率；證據仍需人審閱。

參考：[Barr 等人的測試判準綜述](https://philmcminn.com/publications/barr2015.pdf)；[ISTQB CTFL v4.0.1](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf) §4.4。
