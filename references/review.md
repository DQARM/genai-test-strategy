# 四輪審查

從已確認規格、AC、選定風險／情境／範圍、候選案例、已驗證的操作介面與準則建立審查上下文。來源可以共享，但判準不得來自受測程式；不能因程式、案例、Expected 都由同個假設產生且相互一致，就宣稱已獨立驗證。

## 1. Traceability

逐一檢查每個 Expected 對應已確認規則、適用條件、revision、原文。找出推測的持久化、重啟、等於邊界、時間／容差、錯誤處理等。缺規則列 Q，不自動加入產品承諾。來源的顯示值、保存值、設備輸出及物理效果不得互相代換。

## 2. Executable and verifiable

實際讀每一步確認：可取得環境與權限、可建立及驗證初態、可重建資料、操作路徑存在、輸入具體、觀測點可取用、判定時機可控制、預期可判定、證據可保存、可清理重跑。只有標題或 Gherkin 時列具體欠缺欄位。

例如「輸入異常資料，確認處理正確」缺輸入、初態、操作、時機與觀測；不要直接補入猜測的值。介面文件沒有提供的查詢或重置能力，不能自行杜撰；要提出可觀測性缺口或已確認的黑箱驗證方法。

## 3. In-scope coverage

只用本輪已選 AC、風險、情境、邊界、狀態、異常作分母。逐條看斷言，不能只數 TC ID。若已確認要求涵蓋畫面、保存、重啟，但 TC 只看畫面，列後兩者缺口。若規格尚未要求重啟持久化，不能以審查名義新增這個 Expected。

檢查所有比較邊界及初始狀態。只有明確的資料型別、單位與解析度時才採 adjacent value；不可沿用教材的步進或門檻。缺少某個已選風險的案例是缺口；未選項目放剩餘風險清單並沿用已決定取捨。

## 4. Consistency

找重複、矛盾、過期來源、單位混用、案例間依賴、初態互相污染、先後順序隱藏要求、失效的版本與不一致的判準。合併重複案例需保留原 ID 與追溯；不能直接刪掉唯一覆蓋某風險的案例。

## 輸出與獨立性

每項 finding 留：ID、round、case_ids、rule_refs、具體問題、證據、修正建議；交人處置為修正、合併、暫緩、待釐清、接受剩餘風險或有依據駁回。修正後重審對應新 digest。

新對話／新 agent 實際重新載入來源才標 fresh-session，另記 session／reviewer／model。相同 agent 在原對話重讀只能標 same-session；不得改標以通過檢查。fresh-session 可減少上下文污染但不能保證沒有同模型偏誤。能使用不同模型／人員時做交叉審查，仍保留可追溯判準。

獨立代理不可用或未獲允許時，不擅自建立；產生 review-pack 與新對話提示交接。人員審查可標 human 並記實際審查證據。基線需要四輪完成、finding 有處置，以及人對目前內容的明確核可；不要求為每筆例行保存再問一次同意。
