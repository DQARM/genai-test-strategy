## 初始輸入與資料權威

先分辨對話產出或已有保存／續作任務，沿用已提供資訊。未知規格時第一回合仍只問規格概況；已有資料就先處理能做的內容，不讓行政設定阻擋初步分析。

| 何時需要 | 尚缺時的提問 | 取得後的動作 |
|---|---|---|
| 起始概況未知 | 你目前有沒有已知規格或需求草稿？ | 提供有文件／口頭規則／目前沒有及自由回答；本回合等待，不夾帶其他問題 |
| 有文件但位置未知 | 規格或需求草稿放在哪個資料夾？也可以提供附件。 | 沿用附件／已給位置實讀；無文件從已知口頭規則開始 |
| 尚不知要處理什麼 | 這次想先處理哪個產品或使用流程？ | 一句背景不計需求題；真正的範圍取捨照原計數規則 |
| 首次需保存、產生檔案或使用者已要求建專案 | 要建立新專案資料夾，還是使用現有資料夾？ | 補缺的完整路徑；已有指定根目錄就接手，不在來源資料夾擅自初始化 |
| 保存方式尚未選定 | 版本只保存在本機，還是同步到 Git server？ | 保留選擇，選 server 才協助登入；不從 remote 設定猜偏好，也不把未回答當本機同意 |

沒有保存任務時可先做對話草稿並說明未落檔；不主動追問資料夾／版控。需要保存但缺資訊時，先完成可做分析，再一次補一項行政資訊，這不增加需求題數。轉入專案時將現存原話、來源、規則、ID 與續問選擇搬入既有契約，未知原時間照實保留，不重新訪談。審查／核可不必在開始時決定；實際測試不論入口都要保留執行證據。

只有根目錄不能推定有無規格；只有來源位置也不能推定專案根目錄。有規格但未交代載體時，先分清文件或口頭規則。未找到文件與使用者明說無文件分開記錄。

**資料夾與版控：**

- 新建路徑先確認不衝突；已存在就辨識內容，再決定沿用或改名。使用者授權 AI 選位置時，才在可寫工作區用中性不衝突名稱建立並回報。
- 現有路徑確認存在、是目錄且可讀寫，再讀適用指引、Git 狀態及 qa/ 進度。不存在或無權存取時，取得修正／掛載／附件位置，或先做對話草稿；不在別的環境建立同名假路徑冒充成功。
- remote 只是設定，版控偏好以使用者／session 為準。本機模式保留既有 remote；server 登入失敗或暫無網路，記待登入／同步，繼續可做的需求工作。
- 取得正確工作副本後，用技能內 `scripts/qa_project.py init <root> --name <name>` 建立空白結構，再檢查並建立第一個 checkpoint。之後使用 `qa/tools/qa_project.py`。需要 Python 3.10+、Git；已初始化則直接續作。既有遠端先接手再 init；巢狀 repo、暫存變更及保存範圍按 [local-versioning.md](local-versioning.md)。兩種模式均不要求 CI/CD。

**來源整理：**

專案內文件保留原檔；專案外文件只把本輪需要的版本複製到專案內不衝突位置，例如 inputs/requirements/。記原路徑、檔名、取用日、版本及 hash，registry.sources.path 指向副本。使用既有附件，不要求重交；以專案內安全路徑引用，不使用外部絕對路徑、../ 或 symlink 繞過限制，也不在草稿來源目錄另建 Git。

先盤點，再按 [source-reading.md](source-reading.md) 實讀本輪正文／圖表，記閱讀範圍、定位摘錄及未讀部分。OCR 不確定的數字、運算子與單位回看圖片。來源權威依已確認採納關係，不能只憑日期較新決定。衝突保留雙方並交適當決策人。

文件模式記 requirement_input.mode=documents；無文件記 conversation；概況未取得則 pending。known_spec_note 保存起始概況，原始問答依 [interview-records.md](interview-records.md) 保存並連回決策；草稿／摘要保持原確認狀態。逐步補目的、角色、範圍、介面、環境、品質目標及限制。缺專案描述才問一兩句背景；資料完整不是開始的前提。

有草稿時按 [spec-review.md](spec-review.md) 批次分析歧義、衝突與可測試性缺口，記原 questions，按需 export-questions 轉交不在場的 PM／工程。分析與匯出不算已訪談。接回回答時保存原話與版本，再更新實際受影響內容。

## 上下文、保存與用量

### 先選取，再載入

先看專案指引、精簡 session、Git 狀態與版本，再利用目錄、ID／引用及條款定位，讀本輪原文與必要共通限制、前置、術語、跨功能依賴。大型 registry 先用程式篩選再送入上下文；這是選取方式，不是新增工具命令。來源改動、衝突或引用不明時擴大閱讀。

已讀、版本未變且仍在上下文的內容可沿用；換工作階段後重新讀必要依據。session 只保存目前狀態與連結，完整問答／決策保留原檔。規格與機器記錄以 registry、cases 為主；spec.md、test-cases.md、report.html 等由 render 生成。策略、計畫、決策原文及 session 可直接編輯；文獻保留適用版本、副本／摘錄、URL 與取用日。

### 逐題保存，分輪產出

依 interview-records.md 先保存原始問題／選項及 pending，收到回答立即補原文，另存 interpretation；已知人員與時間照實記，未知留 null。若歷史決策缺 records.md 要求的時間等資料，先保存原問答與待補項目；尚未入庫的規則保持 proposed，不造 DEC／confirmation 來取得 confirmed。既有不完整 DEC 不刪改，保留限制；登錄時間與決策時間分開。依真實決策更新規則與精簡 session，每題回覆只列新增決策、必要影響與下一步。

規則變更時，依 records.md 更新 revision、把受影響現行案例改 draft 或 blocked，標記待更新報告及原因。審查、核可與執行前先處理待更新項目；舊基線與執行快照保留。每題保存檔案，通常收尾才集中產生完整案例與視圖；使用者指定逐題 checkpoint／同步時照辦。

**收尾動作：**

1. 更新受影響案例、registry、策略／計畫及 session；欄位依 templates.md。完成有依據的工作，缺口列明影響、owner 或未指派、確認時點／觸發條件。
2. 執行 check、render，交付完整案例與可點閱的 report.html。版本相同的視圖可沿用；結構問題修正或如實列限制。對話模式只交付文字與未保存狀態。
3. 有案例交付時依 [review.md](review.md) prepare-review，讀回驗證與 HANDOFF 實際路徑，記待審版本、digest 及限制；暫不打包、無案例或對話模式記明原因。打包失敗仍保留設計成果。
4. 依 local-versioning.md checkpoint 本輪明確檔案；server 模式依 [git-server.md](git-server.md) 沿用已授權範圍同步並讀回。保留他人 staged 內容，不改全域 identity。區分檔案、本機版本與遠端保存；失敗保留可用成果。
5. 先用三句回報新增確認、實際交付與缺口、下一步及責任人。下一步可查資料、補介面、補案例或審查；依下面的續問狀態決定是否提問。

### 用量

題數與 token／費用分開記錄。宿主有用量才記輸入、輸出、快取與統計範圍；金額需適用費率，估算與帳單分開。可量測／控制時遵守明訂上限，到限保存進度。未知用量記未知。

qa_project.py 不提供 token 計量、費用硬限制或宿主歷史裁切。按需讀檔可減少部分重複輸入，但 Skill 無法保證帳單或節省比例，也不要求使用者先建計費服務。

## 本輪範圍與釐清預算

一題＝一次實質需求／範圍決策；一批＝一次統整前的訪談額度；一輪＝聚焦一個交付目標，可含多批訪談與後續設計。輪次以新增規則、案例與阻塞的變化說明進展。

### 計數與焦點

| 計入需求題數 | 不計入 |
|---|---|
| AI 提出的功能範圍取捨、產品行為、驗收、衝突採納、風險決策、影響判準的追問／再確認 | 規格概況、文件位置、專案名稱／一句話背景、資料夾、版控／登入、查資料、統整、續問選擇、使用者主動提供／更正 |

準備期間若已問實質決策也計入；一題中有多個獨立決策應拆開。提問即記錄，先處理回答才決定下一步。進度表示累計與本批已問，不當需求完成百分比或剩餘缺口數。誤計依原問題校正並記原因；缺資料記未知。

沿用已選焦點。範圍過大又未選定時，依交付目標提出 2–3 個有理由的流程選項；資訊不足先問本次要完成哪個使用流程，算實質決策。已授權依明確準則選取則直接採用。寫明本輪交付與暫不展開事項，保留跨功能影響與回訪條件；只有人或既有明確授權能更動 scope。

### 統整與續問

預設一次一題、每五題統整一次，沒有總題數上限；第一批隨需求釐清任務開始。資料足夠即提早產出，不預排或湊滿問題。10–15 分鐘是進度檢視目標；只有使用者明訂時間才是上限，整場上限含初始化，無計時依據如實註明。

| 事件／狀態 | 下一步 |
|---|---|
| 本批最後一題尚未回答 | 等待回答並保留 pending；收到後先處理，才完成統整 |
| 本批最後一答完成，仍需重要決策 | 至多三句統整新增確認、可產出內容及缺口；提出「繼續釐清」「先產出」，說明續問用途，等待選擇；本回覆不附下一個產品問題 |
| 明確選繼續，或最後一答已明說再問 | 新增一批最多五題，保留累計與原焦點；只同意兩題就追加兩題。同一選擇不重問，也不授權後續所有批次 |
| 選先產出、要求停問或交付 | 立即進入策略／案例設計，未決部分保留草稿與阻塞；只列待辦，直到人明確要求再釐清才恢復訪談 |
| 資料足夠，或同一缺口反覆缺依據／合適決策人 | 直接交付可做成果；缺口列查文件／找負責人的回訪條件 |
| 使用者總題數／時間上限已到 | 統整並交付，不再邀請追加；一般「繼續」不撤銷總上限，明確調整才更新 |
| 等待選擇、選擇不清楚或換對話／Skill | 保留狀態並保存既有資料；必要時只釐清工作方向，不自行續問 |

總上限存在時，每批額度取五題與剩餘額度的較小值，例如總共八題，第一批後只能追加三題。上限及其來源另記，不把限制餘額說成需求只剩幾題。對外說「每五題統整一次」，避免「再釐清最多五題」造成剩餘量誤解；已說明的節奏可用短句指回。停止訪談不是規格完整、風險接受或案例核可；既有選定範圍保持，缺口按實際影響阻塞。

在 session 記累計、本批起算點與已問／可問數、預算來源、明訂上限、最近統整、續問狀態及選擇原文連結。統整、選擇與摘要不占題數。舊預算轉換僅在升級時按 [migration.md](migration.md#舊訪談預算)。

## 需求提問

提問前由 AI 查三件事：答案會改變哪個本輪案例／驗收／重要風險、文件或有效決策是否已有答案、這個分支是否適用且對方有權決定。只把剩餘必要分歧交給人；工程操作先查文件或交工程／測試負責人，範圍外細節保留待辦。

用白話問一件事，必要時一兩句說明用途。有明確方向才給 2–3 個中性選項及影響，接受自由回答、待確認及適用時的不適用；數值缺口直接問數值與單位。建議標明尚未確認，不把選項、沉默或逾時當決策，也不以回答短／慢推測耐心。

例如已確認有批次匯入且錯誤處理缺依據時，問「一筆不合法時，整批拒絕還是只跳過該筆？」說明這決定保留哪些資料；其他錯誤訊息與重試規則另依需要處理。

記錄原始問答與更正鏈，再把真實決策寫入 DEC 並連 interaction_refs，更新相關 REQ、AC、Q 及 revision／supersedes。前綴與既有編號依 [identifiers.md](identifiers.md)。AC 列前提、動作、輸入／單位、可觀測結果、判定時機／容差與依據；按產品適用性檢視觸發、邊界（含等於）、時間、狀態、例外、權限、併發、持久化、恢復及需維持的行為。

不知道的回答記 open；owner 未知記 unassigned，due_or_trigger 記決定時點／條件，impact_ids／blocks 記影響。更正保留原話與修訂鏈，只重看受影響部分。產品取捨交決策人；操作／量測交工程或測試人員。記交接需求不代表已聯絡、已指派或對方承諾期限。

## 風險策略

先按 [quality-characteristics.md](quality-characteristics.md) 由 AI 篩選適用品質特性及系統風險，在策略記理由與未知；不把清單逐項變成訪談，不在已選先產出時重啟追問。

按 [risk-assessment.md](risk-assessment.md) 批次初評每筆需求及跨整合／變更／環境等風險，保留直接關聯、評估狀態、失敗後果、嚴重度、可能性、優先序與各自理由。unknown 與未評估不是低風險。只有影響取捨的重要分歧才依原續問狀態確認，不逐欄訪談。

按 [failure-modes.md](failure-modes.md)、[test-design.md](test-design.md) 選能發現該失效的方法及深度，記成本、取捨與未測部分。經驗清單產生候選，產品判準仍需已確認依據。策略涵蓋品質目標、範圍與優先序、測試層級／類型、方法與自動化取捨、資料與可觀測性、缺陷處理、進入／退出條件、放行證據及剩餘風險；計畫寫本輪人力、時程、環境、build 與工具。任務未包含產品開發時，只提出介面與可測試性需求，保留產品程式原樣。

| 承諾 | 可選層級及證據 |
|---|---|
| 模組判斷 | 單元／元件：輸入、初態、輸出 |
| 指令傳遞與回應 | 整合／系統：輸入、發送、接收的對應紀錄 |
| 使用者可見行為 | 系統／驗收：操作路徑、畫面、約定環境 |
| 真實設備效果 | 實機驗收：校驗量測、曲線、設備運作紀錄 |

選適合成本與風險的層級，不強制全部採用。無內部權限時設計黑箱方法與觀測需求。只有產品本身涉及模型／agent 才展開相應評判、資料集、非確定性及工具權限；通用專案沿用自身品質目標。

## 候選情境與案例

依已確認規則及選定風險，先選方法、列具體 COV，再由資料、初態與斷言承接。候選依人的取捨或既有授權保留、合併、暫緩、待釐清，記理由與剩餘風險。優先交付少量完整案例。

每批撰寫前展示 [templates.md 的已知條件摘要](templates.md#案例撰寫前的已知條件摘要)：範圍、規則狀態、來源版本／實讀定位、操作／環境、判準、方法／覆蓋及缺口，包含共通限制與跨功能依賴。每批一次，後續只列變動；依據足夠就接著寫案例，不要求重新核可全部條件。摘要只供核對，規則與實測狀態保持原樣。

依 templates.md 補完整案例：真實介面操作與資料、獨立初態建立與驗證、逐步觀察／時機／證據、Expected 及規則／覆蓋引用、通過／失敗／無法判定條件、清理與重跑。共用 fixture 須說明建立、隔離及 reset；確認本案相關快取、去重、佇列等殘留，不能只憑主資料清空推定所有狀態清空。

缺產品規則、環境／權限、操作工具或觀測能力，分別列問題與受阻案例；共用缺口按實際影響處理。仍可寫有依據的目的、準備及判準，Actual 留待 runs。資料足夠才標 ready；Gherkin 或概念步驟不等於可執行程序。

先按 [oracles-exploration.md](oracles-exploration.md) 重用適用的已確認共用／比較判準。判準未完整但操作有依據時，可交付有時間上限的探索任務，觀察不當驗收結果。案例自動化僅在框架與介面已知時提供，人工測試同樣有效。

## 版本、進度與變更

接手或收到審查發現時，從原 session 恢復焦點、有效決策、編號、累計及續問選擇；進度欄位依 templates.md。只替換目前狀態，原文留在既有記錄。計數只寫 session，不為計數修改 registry。

來源變更先讀差異，區分規則與措辭／格式，按真實決策更新 revision，追查 AC、案例、審查與執行的影響。現行設計變動依 [local-versioning.md](local-versioning.md#版本綁定) 取得新 digest；正式基線按 [review.md](review.md) 完成對應完整設計的四輪獨立審查、發現處置與人員核可。已審舊版保持原樣；只看局部差異不當整份新版本已完成審查。

需要回歸／smoke 安排時按 [execution-selection.md](execution-selection.md) 提出變更依賴與標籤聯集，保留理由、未知時間、受阻案例與未覆蓋風險。排程檔與設計版次分開；較短的執行清單不縮小設計 scope 或審查分母。執行前 check-selection 並核對隱藏依賴及實際環境。

## 執行與放行

只有使用者要求且環境／操作在授權內時執行產品。依 [records.md](records.md#執行記錄) 建新 RUN，記 SUT build／產物 hash、案例與規格快照、工具／依賴、環境、資料、初態、逐步實際觀察、證據、時間及執行人。

未執行保持 NOT_RUN；環境阻塞與產品 FAIL 分開；Expected 未定或證據不足記 BLOCKED／INCONCLUSIVE。start-run 建立紀錄，不會操作產品，也不代替執行前核對基線與阻塞。

實測缺陷依 [feedback.md](feedback.md) 保存經驗來源並重評相關風險；只有已發生且有證據的事件才當實測回饋。

放行報告列版本、已驗／未測範圍、阻塞與缺陷、證據、剩餘風險、例外與責任人。人明確決定才記核准放行；案例基線或全數 PASS 不自動代替放行決策。
