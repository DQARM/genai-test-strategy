## 初始輸入與資料權威

初次啟動依序處理「有沒有已知規格」「專案資料夾」「本機或 Git server 版控」「文件位置或逐題訪談」，每回合只問下一個缺少的資訊。選 server 才展開登入及儲存庫設定。已提供的規格概況、選擇、路徑或無文件狀態直接沿用；續作先讀 session，不重走開場問卷。

### A. 第一題：有沒有已知規格

尚未得知規格狀況時，第一則回覆只問：「你目前有沒有已知規格或需求草稿？」

- 有規格文件或需求草稿：先記錄此概況；文件內容是否可作為正式規則，仍要閱讀及確認。
- 有一些口頭規則，還沒有文件：保留已有規則的線索，後續透過訪談記錄；不把無文件誤記為無規格。
- 目前沒有已知規格，需要從頭釐清：記錄此狀態，後續從專案目的及重要行為逐題釐清；不代填規則。
- 這一回合等使用者回答，不同時詢問或建立專案資料夾、不索取文件路徑、不展開產品訪談。可自由回答；回答不清楚時只釐清目前缺少的一項資訊。
- 已提供規格／草稿／來源位置或已說明規格概況時，不重問；只有專案路徑時仍須先取得規格概況。

取得答案後再進入 B。建立專案後，將原回答摘要寫入 `registry.project.requirement_input.known_spec_note` 與 session；這個摘要只表示起始資料狀況，不代表規格已被核可。

### B. 建立或選定專案資料夾

規格概況已知、專案資料夾選擇尚未提供時才問：「這次要由我建立新的專案資料夾，還是使用你現有的專案資料夾？」

- 新建：下一題取得完整新資料夾路徑；已提供就直接使用。若人明確交由 AI 選位置，可在可寫工作區以 project-日期時間等中性、不衝突名稱建立，並回報實際路徑。新建路徑已存在時先辨識內容，不能以空白模板覆寫；需要沿用或改名時只問這一個選擇。
- 現有：取得完整路徑，確認它存在、是目錄、可讀寫，再讀適用指引、Git 現況與 qa/ 進度。不存在時回報並問修正路徑或改為新建，不默默建立來假裝找到現有資料。
- 權限／環境：只使用實際可存取位置；例如在 Linux／雲端不能把 Windows 磁碟路徑當成本地相對資料夾建立。無法存取時說明限制，取得掛載／上傳後的可用位置，或由使用者選擇先做對話草稿。
- 完成資料夾檢查後進入 C；新專案先取得版控選擇，再初始化，避免在預計 clone 的目錄先建立不相關歷史。已有 qa/ 的專案先讀取既有進度，不重做初始化。

### C. 選擇版控方式

偏好未知時只問：「這個專案的版本要只保存在本機，還是同步到 Git server？」

- 本機 Git：版本保存在專案內，不需登入或網路；不查連線、不聯絡遠端，也不刪除原有 remote。
- 本機 Git＋Git server：版本保存在本機並同步到指定儲存庫；依 [git-server.md](git-server.md) 協助登入、確認儲存庫及權限，接手工作副本。缺少服務時才問使用哪個服務／網址，逐次補齊資訊。
- 已提供選擇就直接沿用；僅看見 `.git` 或 remote 不能判定模式。舊專案沒有模式紀錄時補問一次，之後從 session 續作。
- 登入失敗、取消或暫無網路時記「server 模式／待登入或待同步」，保留本機檔案並繼續可做的需求工作，不默默改成已完成的本機模式。

選本機或已取得正確工作副本時，用 init 建立或沿用專案結構，將選擇寫進 `qa/session.md`；init 與第一個 checkpoint 分開完成。遠端工作副本尚待取得時，依 git-server.md 先保留草稿，避免先建不相關歷史。只做對話草稿時可暫緩版控並記明未保存。選 server 不要求 CI/CD（Continuous Integration／Continuous Delivery，持續整合／持續交付）或自動化測試。

### D. 有文件時找位置，無文件時逐題訪談

已知有文件且位置尚未提供時才問：「規格或需求草稿放在哪個資料夾？也可以回答『就在這個專案資料夾』，或提供可讀取的附件。」已說沒有文件時跳過此題；只有口頭規則及尚無規格都由訪談開始。若只說有規格但未交代載體，先釐清是否有文件，不猜測路徑。

- 在專案內：先盤點、閱讀相關需求文字、PDF、圖片、會議記錄等；原檔保留。不要把整個程式目錄當作已確認規格。
- 在其他資料夾：確認可讀，先盤點以辨識本輪相關檔案；只複製要使用的版本到專案 inputs/requirements/ 下不衝突的位置。保留原路徑、檔名、版本／取用時間與 hash；原檔不搬移、不改寫。registry.sources 的 path 指向專案內副本，原位置記 note／專案來源資訊。不得用 ../、絕對外部路徑或 symlink 繞過來源必須在專案內的規則，也不要在草稿來源資料夾另建 Git。
- 已提供附件／檔案：若能讀取就沿用，不再要求把同一份內容放一次；需要保存時收進專案並保留來源資訊。無法讀取時記缺口，不聲稱已閱讀。
- 沒有文件：記錄 requirement_input.mode=conversation；不再要求文件路徑。有口頭規則時先沿用使用者已提供的內容；尚無規格時從目的與重要行為開始。若缺專案描述，下一題問要測試什麼專案／功能；已有描述就從最影響本輪結果的分歧開始。逐題將使用者原意及 AI 整理稿保存在 inputs/requirements/initial-notes.md；整理稿標待確認，真實決策另入 DEC，不能把 AI 摘要直接當已確認規格。
- 有文件模式記 requirement_input.mode=documents，來源位置及專案內副本清單都記下；尚未回答則是 pending。未找到檔案不等於使用者說沒有文件，兩者不可混淆。

不要求具備完整規格、原始碼或測試框架；先閱讀已有材料，讓 AI 補問真正的缺口。若使用者明確要求先做對話草稿，暫不建立檔案，但必須區分「對話內容」與「已保存進度」。

逐步記錄目的、角色、產品／流程邊界、介面、環境、品質目標、限制與權威來源；從已給內容提取已知資訊，只詢問目前最有影響的一項未知。用自己的專案背景調整後續提問與測試方法，不複製教材或另一個專案的規則。

先盤點與實際閱讀，對每份來源記錄路徑、hash、版本／頁碼／段落、用途及是否已確認為依據。大範圍先讀摘要、目錄與目前相關段落，按下節選定焦點再深入；記錄已讀範圍與未讀部分，不宣稱已完整審查。不得把「最新日期」當成唯一權威；衝突要問誰有決策權。OCR 不確定數字、比較運算子、單位時要核對圖片；無法讀取就記錄缺口。

原始資料留在原位置，專案外的來源按上述方式保存本輪副本。規格與可機器讀取記錄存 qa/registry.json，案例存 qa/cases/；規格／案例 Markdown 與 report.html 是由 render 生成的人用視圖，避免雙重真相。策略、計畫、決策原文與 session.md 是可直接編輯文件。引用文獻保留適用版本、副本或摘錄、原 URL 與取用日；不能只存會變動的 URL。

## 上下文、保存與用量

### 先選取，再載入

先確認適用的專案指引、精簡 session、Git 狀態與檔案版本／hash，再依目前階段選取資料。利用來源目錄、registry 的 ID／引用與條款定位，讀目前問題所需的原文；同時納入適用的共通限制、術語、前置條件及跨功能依賴。新專案尚無索引時，先盤點及閱讀必要資料並登錄；不能假裝已完成全文分析。

資料量大時，先由程式列出相關記錄、引用與版本，只把必要結果送入模型；不要先輸出完整 registry／文件再請模型摘要。這是代理使用檔案及既有工具的方式，不是新增的 qa_project.py 命令。原始資料改動、來源衝突、摘要缺漏或交叉引用不明時，回查原文並擴大必要閱讀範圍；不可為縮短上下文猜答案。

已讀、版本未變且仍在目前上下文中的內容不重讀；換工作階段後按需重新載入，不能只憑「以前讀過」就省略必要依據。摘要保留已確認／建議／未決的區別及來源 ID、版本、定位；未讀內容不標為已確認。完整記錄仍在專案中，session 不累積全部訪談原文。

### 逐題保存，分輪產出

每次收到回答，立即將使用者原意、決策人與時間保存到既有決策／訪談記錄；依實際確認更新規則及精簡 session，保留已用題數、待辦與下一個動作；仍需人的決策時才記下一題。不用另外發起模型呼叫去反覆摘要整段歷史。每題回覆呈現新增決策、必要影響與下一步，有剩餘額度且需要決策才提問，編號依既有規則提供簡短圖例。

規則變更時立即列出待更新的案例／報告及原因，受影響的現行案例依 records.md 增加 revision 並改為 draft；仍缺規則或操作依據時改為 blocked。原有基線、審查與執行快照保持原樣。舊 Markdown／HTML 在 session 與交付說明中標為待更新；重產前不作為目前可執行案例交付。進入審查、核可或執行前，先處理相關待更新項目並核對版本。

本輪到限、已有可交付成果或使用者要求收尾／提前交付時，集中補齊受影響的完整案例，執行 check、render、checkpoint 及已授權的遠端同步；使用者已指定每題保存 Git 版本或同步時仍照辦。一般問答先保存檔案，不必每題重產全部視圖；區分檔案已保存、Git 版本已保存及已同步。產出期間若尚未交付，只回報實際進度，不說案例已完成。只在對話草擬時如實說明未保存。

完整案例仍包含獨立前置、實際操作與輸入、Expected 及已確認依據、判定時機、觀察點、證據與清理。使用現有程式產生 Markdown／HTML；不讓模型反覆重寫同樣的排版。沒有改動且版本相符的視圖可沿用，不為節省而刪除完整案例欄位。

### 審查與費用界線

獨立審查使用對應版本的規格、完整已選範圍、案例、必要依賴及準則，排除無關生成對話；分批讀取也要保留總體覆蓋分母與跨案例一致性。四輪審查及整份設計 digest 的核可要求不變；只重讀受影響內容不能冒充整份新版本已通過獨立審查。

使用者設定的 token（模型計量內容的單位）／費用預算與釐清題數分開記錄。宿主提供用量時，記錄實際輸入、輸出及可取得的快取用量，註明統計範圍；金額需有適用費率，估算不得冒充實際帳單。可量測與控制時遵守上限，到限保存進度、回報缺口；不為達標截斷判準或自動開新輪。

本 Skill 的規則只約束資料選取及工作節奏；API 呼叫端／宿主才可控制實際攜帶的歷史及硬性費用上限。qa_project.py 1.3.0 沒有 token 計量、費用限制或自動上下文裁切功能；無可用用量就記未知，不要求使用者為開始工作先建計費服務，不宣稱已移除歷史、已限制帳單或已節省特定比例。

## 本輪範圍與釐清預算

完成必要的起始資訊後，將需求討論切成短回合。一般規模也可直接採用，不新增完整問卷或額外核可流程。

「一題」是一次實質需求或範圍決策；「一輪」是聚焦一個交付目標的工作批次，不等於一次訊息往返，也不是固定要做三輪或十輪。每輪記錄目前階段及預計交付，結束時比較新增依據、案例內容與阻塞的變化，不只回報用了幾題。已具備足夠依據就推進案例設計，不把所有細節問完當作交付前提。

### 初始化與需求決策分開計數

題數上限用於本輪實質需求決策，不是整段對話的訊息數。專案準備只補開始工作所需資訊，已有答案直接沿用；不因不計題數就增加問卷或延長初始化。

| 提問內容 | 計入需求釐清額度 |
| --- | --- |
| 有沒有已知規格、文件或口頭規則，以及文件存放位置 | 否 |
| 專案名稱或一句話背景、建立或沿用資料夾、資料夾路徑 | 否；若進一步要求選擇本輪要處理的功能，就計入 |
| 本機或 Git server 版控、登入、儲存庫及連線設定 | 否 |
| 選擇本輪流程、功能範圍或重要風險的取捨 | 是 |
| 確認產品行為、例外、驗收條件，或決定衝突規格以哪份為準 | 是 |

通常在準備完成後，提出第一個實質需求或本輪範圍決策問題時開始計數；若準備期間已問到這類決策，也照實計入。不要把產品問題改稱「初始化」來規避上限。已由使用者主動提供、且不需再問的答案不另占題數。

進度分開表示，例如「專案準備：完成；本輪需求釐清：未開始（0／10 題；不必問滿）」。提出第一題時記為 1／10；使用者另訂上限時顯示實際上限。這是已問題數與額度，不代表需求總數或完成比例；摘要可寫「已問 5 題；本輪上限 10 題」，不能據此宣稱需求完成 50%。準備期間若已有實質決策，就保留實際用量，不能重新歸零；不必每則回覆重印整張進度表。

### 選一個可交付焦點

沿用使用者已選的流程或本輪任務。範圍過大且尚未選定時，依已知的交付目標、影響及不確定性，提出 2–3 個有理由的流程選項，計入本輪決策題數；此前尚未問過實質決策時，這就是第 1 題。不要同時問預算、所有需求或每個子系統。資訊不足時先問這次要完成哪個使用流程，不自行猜產品優先序。使用者已授權依明確準則選取時直接採用並說明理由。

用一句話寫本輪焦點，再列要交付的規則／案例及暫不展開的範圍。焦點可是一段使用流程、一個交付功能或一個重要風險；不要一律切成技術模組而漏掉跨模組行為。暫不展開的事項仍保留影響、責任人與回訪時點。

釐清焦點不等於正式測試範圍已被縮減。只有人或既有明確授權可改變 `scope` 的選定項目；不能為了快速結案移除原本承諾的驗收條件或覆蓋分母。

### 進度檢查點與上限分開

- 使用者已給題數或時間限制就沿用；否則簡短告知：**單一焦點最多 10 個需求決策問題，每完成 5 題顯示進展，不必問滿**。不為預設另問確認。10 題是可調整的流程預算，不宣稱是人類耐心或注意力的科學上限，也不預先排滿十題。
- 一次只問一題。範圍選擇、影響判準的追問與再確認都計入題數；不得把多個獨立決策包成一題，也不能用「補問」繞過上限。提出問題就記入已問數；先取得該題回答再決定後續。已回答的資訊直接採用，不重問。
- 每完成 5 題，用至多三句說明新增規則、能形成的案例或具體草稿、最重要的剩餘缺口。預設第 5 題回答後統整；若仍需必要決策，於同一回覆接續第 6 題。第 10 題回答後將統整併入成果交付並收尾，不先摘要再重複收尾，也不提出第 11 題。自訂上限未滿五題或不是五的倍數時，仍到該上限就收尾；使用者明確延長時按累計題數每五題統整，最後一次併入收尾。
- 進度統整不新增核可關卡，不固定詢問「要不要繼續」，也不重設已問數。摘要不占需求題數；不為摘要反覆產生全文報告或宣稱尚未寫出的案例已完成。由舊節奏改為每五題時保留計數與最近摘要，不補發過去的檢查點；足夠交付時不必等第五題或第十題。
- 10–15 分鐘是預設進度檢視目標，從第一個實質需求／範圍決策起算；有可靠時間資訊時檢視目前是否應交付、改查文件或延後低價值問題，不把目標誤作硬性中止。若使用者說「只有 10 分鐘」或明訂截止時間，那是必須遵守的時間上限；指定整場時間時初始化也占用時間。不能可靠計時就明說，不假稱已自動計時；時間與題數也不代表完成保證。
- 把準備狀態、焦點、預算及來源（使用者設定／預設）、時間的性質（目標／上限）及適用範圍、起算點、已問問題與計數、最近檢查點寫入 `qa/session.md`，無檔案模式則在對話中記錄。續作不因換對話、檢查點或收到回答歸零。舊記錄誤計初始化時依原問題校正；無依據的數量標未知。
- 已足以完成本輪預計交付、使用者要求先看案例／停止，或重複缺口沒有新依據或合適決策人時，提前整理成果並列待辦。連續「不知道」且後續問題依賴相同缺口時，先交付可做內容或改查資料；不能只憑回答短或回覆慢判定不耐煩。範圍與重要取捨仍須由人決定。
- 最後一題得到回答後，或明訂的時間／費用上限已到，就交付並收尾，不自動換輪；預設上限為 10 題時，不再提出第 11 題，使用者自訂時遵守其上限。若只是部分案例已可完成，可先交付該部分，再於原額度內處理仍影響本輪目標的必要問題。延長需使用者明確要求，記錄追加額度及累計題數；延長、沉默或逾時都不代表同意產品答案。

### 舊三題預算續作

新版預設只取代舊預設，不覆蓋使用者明訂的短討論。記錄可確認原本採用舊預設三題時，續作可改為十題但保留已問數，例如 3／3 改成 3／10，而非 0／10；留一句變更原因。若使用者曾明訂最多三題，仍遵守三題，除非使用者明確放寬。預算來源不明時先保留既有上限，不猜是預設。已收尾的工作不自行重啟；使用者要求續作時再依此規則處理。

### 把問題交給合適的人

| 問題類型 | 本輪處理方式 | 留下的記錄 |
| --- | --- | --- |
| 會改變預期結果、驗收或重要風險的產品分歧 | 優先交給有權決策的人，例如 PM（Product Manager，產品經理）；先查已有決策 | 選項、影響、人的決定，或未決的責任人與確認時點 |
| 操作位置、環境、量測與觀測方法 | 先查本專案文件，仍缺就交工程／測試負責人；其中的產品判準仍由產品決策人確認 | 所需介面或證據、責任人、受阻案例 |
| 本輪未選範圍的細節 | 保留待辦，不占用這輪逐題訪談 | 暫緩理由、影響、責任人或未指派、日期或觸發條件 |

使用現有 `questions` 的 owner、due_or_trigger、impact_ids、blocks 記錄責任與影響，風險保留在 risks；不要另建重複的未決清單。沒有明確指派就寫未指派，不能替他人承諾期限。僅記錄交接需求，不代表已聯絡或指派成功。

### 分輪交付，按實際影響阻塞

每得到可用決策就保存並更新規則、標記受影響案例；輪末或使用者提前要求交付時，將有完整已確認依據及真實操作方法的已選情境集中展開為少量完整案例。已有規則但缺操作、初態建立或觀測能力時，先寫出可確定的測試目的、條件與判準，缺少部分明列在 draft／blocked 草稿；未選情境只能列候選，不自行升格為正式範圍。若連產品判準都不足，交付已有依據的內容與具體阻塞清單，不編造 Expected、操作或結果。

未決事項只阻塞受影響的案例／階段，繼續不受影響的工作。若缺口影響共用前置或多個流程，按實際影響標記，不能刻意縮小。到明訂上限不代表風險已接受；關鍵未決問題仍可阻塞核可、執行或放行。只有有效決策才能解除。

操作與觀測缺口先查相關專案文件，再列交由工程／測試負責人補足的資訊；僅列交接需求不代表已聯絡。若同一缺口跨輪沒有新依據或適合的決策人，不反覆問同一個人，改列待辦及回訪條件，繼續不受影響的工作。

收尾先回報三件事：「本輪新增確認了什麼」「本輪實際交付的案例或草稿與仍缺欄位」「下一個動作與責任人」。下一步可以是查文件、取得介面、補案例或交付審查，只有確實需要人的決策才列下一題；題數到限時只列待辦，不再索答，也不自動開始新輪。區分草稿、可執行與已執行；完成正常保存與版本紀錄，不因對話結束就宣稱整個規格完成。使用 templates.md 的短模板即可。

## 需求提問

先找「同一輸入會因不同解讀導致不同 Expected」的分歧；每次只問一題。優先順序通常是：阻止驗收／重要風險判斷 → 本輪會實作的行為 → 操作與觀測缺口 → 未納入本輪的細節。

提問前由 AI 自行篩選，不把以下檢查變成給使用者的問卷：

- 答案是否會改變本輪案例、驗收或重要風險取捨？不能說明用途就暫不問，保留必要的範圍外待辦。
- 專案文件或先前決策是否已有有效答案？先讀相關依據；已有明確決策就沿用。未確認草稿仍是草稿，只釐清會影響本輪的分歧，不要求重新回答全部內容。
- 這個分支是否適用、目前對象是否能決定？依已確認條件跳過不適用分支；工程操作先查文件或列交接需求，不要求 PM 猜測。適用性未知時才釐清，不能自行判為不適用。

用白話先呈現要決定的一件事；情境及用途不明顯時，再用一兩句說明「這會決定哪個預期結果或測試」。有明確方向才提供 2–3 個中性選項及各自影響；允許「不知道／待確認」、適用時的「不適用」及自由回答，不強迫把答案塞進選項。只有數值缺口時可直接詢問該數值與必要單位，不造出選項讓人猜。需要建議時說明取捨與依據並標「AI 建議、尚未確認」，不把推薦當規則或用誘導措辭取代人的決策；不將一題塞入多個獨立問題。

例如只有在專案真的包含批次匯入、且錯誤處理仍缺依據時，才問「一筆資料不合法時，整批拒絕，還是只跳過該筆？」補一句「這會決定測試要檢查整批未寫入，或合法資料仍被保留」。不在同題再追問錯誤訊息、等待時間與重試規則。

統整及案例撰寫前的已知條件摘要應讓人能直接指出哪項要改；有既有 ID 就沿用並說明含義。收到修正時保留原決策與修訂關係，更新相關規則，將受影響的現行案例標為 draft／blocked，再處理由修正產生的必要分支。沿用其他有效答案與原題數，不從頭訪談或要求重核所有內容。使用者主動修正不另占題數；AI 另提實質決策問題則照常計入。摘要可供修正，不表示內容已全部核可。

使用者只說「不知道」：記錄 open，owner 若未知寫 unassigned，確認時點寫明本輪何處前需決定。繼續處理與該缺口無關的內容，不把整個專案卡死。要記錄但暫緩的風險由人承擔，不能把 unresolved 改成 resolved。

形成 AC 時由 AI 檢查：何種前提、誰做何事、何值與單位、在什麼時間、從哪個觀測點判斷、如何區分成功與失敗。只把其中尚缺且影響本輪交付的一項交給使用者決定，不整串逐項詢問。時間、容差、重試次數或品質門檻都必須有本專案依據，不能為了寫完整案例而自行填值。

## 風險策略

將風險寫成可失敗的情境，如「畫面更新但資料未保存，重新啟動回到舊值」，而非泛稱「功能風險」。評估影響範圍、嚴重程度、發生可能性／曝露、近期變動、不確定性及已有獨立證據。用 P0/P1/P2 等少量優先級即可，必須附理由；等級是建議直到人確認策略。

區分測試層級與證據：

| 承諾 | 最直接驗證層級 | 證據 |
|---|---|---|
| 模組判斷規則 | 單元／元件 | 輸入、初態、輸出與判定 |
| 指令傳遞與回應 | 整合／系統 | correlation ID、輸入、發送與接收記錄 |
| 使用者可見行為 | 系統／驗收 | 操作路徑、畫面與結果、約定環境 |
| 真實設備效果 | 實機驗收 | 校驗過的量測、時間曲線、設備工作記錄 |

不強制每項做全部層級；選能發現該風險且成本合適的證據。QA 沒有資料庫、程式或硬體權限時，建立黑箱驗證與觀測需求，不假設擁有內部能力。

本專案不是 AI 產品時，不增加模型評測、幻覺或 prompt 測試等無關要求。只有實際使用模型／agent 且影響品質目標時，才釐清資料集、評判準則、非確定性、工具權限與必要的重跑方式。

測試策略決定「為什麼、哪裡、怎麼驗證」；計畫決定「這次誰、何時、用什麼版本執行」；案例補齊「從哪個狀態、怎麼操作、何時看哪裡」。不得把案例數量當成策略品質。

## 候選情境與案例

先給風險排序及可取捨候選表，再將選定情境展開完整案例。人工已授權採用某批或某種選取規則時沿用，無須每筆重問。優先交付少量完整高價值案例，不淹沒使用者於上百個標題。

### 撰寫前列出已知條件

選定本輪範圍後、開始寫這批完整案例前，先向使用者展示 templates.md 的「案例撰寫前的已知條件摘要」。涵蓋範圍、規則與驗收條件、執行環境與前置狀態、判定方式及待確認事項，包含相關共通限制與跨功能依賴。只摘要本批相關內容，保留來源檔案、版本／條款或確認決策的定位；有可用檔案時提供連結。

- 明確區分已確認規則、需求草稿、AI 建議、現況觀察與待確認事項。操作文件可支持測試步驟；其中的建議或現行介面表現不能自動變成產品 Expected。尚未驗證的環境可用性如實標示。
- 每批開始時展示一次；同批後續僅列變動、影響及新的來源定位，無變動就沿用，不在每筆案例前重印。需要保存時在現有 session 記本批範圍、摘要所據版本及定位即可，不另建重複的規格來源或必要 JSON 欄位。
- 已有確認依據且操作資訊足夠時，在同一回覆繼續產生案例，不停在「請確認以上所有條件」。只有會改變範圍、操作或預期結果的缺口才需要釐清；不能把呈現摘要當成人已核可。
- 摘要展示不占需求決策題數；衍生的實質問題依原計數規則使用剩餘額度，到限就列待辦。未決項目只阻塞受影響案例；可完成的案例繼續產出，受阻項目保留 draft／blocked 及具體缺口，不猜操作或 Expected。

摘要供快速核對，原文仍是依據；每筆案例仍須具備自己的前置、步驟、判定方式及預期結果來源，不能只寫「同上」。四輪審查與人工核可流程不變。

### 補齊完整案例

測試資料必須能重建。共用 fixture 需獨立 reset；每案包含自行建立及確認初態，不能寫「接續 TC-02」。條件不足時明確區分：產品規則缺口、環境／權限缺口、測試工具缺口、觀測缺口。

在步驟中同時寫操作、輸入、觀察、時機、證據。可用確認過的 UI 選單、CLI 命令、API request、測試工具按鈕或硬體操作。當目前沒有操作映射文件時，提出待釐清問題，案例狀態 blocked；不得藉寫出具體假命令來假裝可執行。

## 版本、進度與變更

每次接手先確認 session、來源 hash 與 Git 狀態，再按「上下文、保存與用量」選取相關檔案及記錄；不預設重讀所有原文。來源改動不會自動採納：讀差異、分類產品規則或措辭／格式變動、記錄人的決策、更新 revision 與關聯記錄。留痕後重新核對 affected AC、cases、reviews、runs。

本工具採保守的整份設計 digest：registry、全部案例、策略、計畫或決策證據有變就需要新審查／新核可。規模很大時可拆成有明確邊界的子專案，不偷偷沿用過期核可。舊基線與執行快照維持原樣，不因更新 Expected 而回寫成通過。

session.md 保存精簡的目前狀態：已知規格概況、專案根目錄、資料夾新建／沿用狀態、版控模式與同步狀態、需求來源位置或無文件狀態、本輪焦點與預計交付、釐清時間／題數預算及來源、時間是目標或上限、已問問題的短標籤與記錄連結、已用題數與最近檢查點、是否收尾與原因、已讀來源範圍與版本、相關確認決策、待辦與 owner／時點、候選取捨、待更新案例／報告、已完成案例與審查的版本、下一個單一問題及下一步。已設用量預算與可取得的實際用量另外註明，未知不補估。原文、歷次決策及完整案例保留在原有檔案，session 用連結定位，不持續堆疊全文；使用 templates.md 的精簡欄位。server 模式另記不含憑證的網址、分支、上傳範圍及最近確認的遠端版本；詳細欄位見 git-server.md。

本輪進度與題數只寫 session，不為每次計數改 registry；真實範圍或規則有變才依原契約更新。既有專案續作時補記已知進度，無紀錄的時間或題數寫未知，不杜撰。此流程不新增必要 JSON 欄位，也不要求升級專案工具或建立計時服務。

## 執行與放行

案例設計任務不自動擴張為對產品執行。使用者要求執行後，確認環境與操作在既有授權內。無實際工具回傳的觀察就保持 NOT_RUN；只讀程式或預測結果不算執行。

RUN 必須記錄 build 或產物 hash、案例與規格快照、工具／依賴版本、環境、資料與初態、逐步實際觀察、證據、時間與執行人。環境失敗不冒充產品 FAIL；Expected 未定或證據不足記 INCONCLUSIVE／BLOCKED。

放行報告包含：本次版本與已驗範圍、未測／阻塞、未解缺陷、結果證據、剩餘風險、例外與責任人。只有人明確作出放行決策時才記錄為核准放行。基線核可與所有案例通過都不能自動代替這項決策。

## 測試設計、共用判準與探索的銜接

本輪範圍選定後，由 AI 按 [test-design.md](test-design.md) 選方法、列覆蓋項目，再補案例；沿用既有決策與提問額度，不把方法或欄位變成新問卷。寫案例前的已知條件摘要納入這些分析。部分判準未定時，先查可重用的已確認共用 AC，再依 [oracles-exploration.md](oracles-exploration.md) 交付可形成的案例或探索任務；操作依據也不足時列具體缺口。

輪末回報新增的規則、方法／覆蓋項目、實際案例內容及探索計畫，分清哪些可判定、哪些只供觀察。網頁及 test-design.md 顯示設計承接與剩餘風險，實測證據仍獨立保存；新發現不自動重設預算、擴大範圍或變成 Expected。
