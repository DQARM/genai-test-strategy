# 編號與縮寫說明

## 展示規則

編號用來穩定追蹤同一筆資料。ID 的英文是 Identifier，中文為識別碼。每則回覆、每份人閱讀的文件，都要在第一次出現某前綴時解釋其英文來源、中文意思與用途，或附涵蓋本次所有前綴的簡短圖例。表格可在欄名或表前說明，無須每列重複；不能只留裸編號，叫使用者自己查 README。

例如：`REQ-01（REQ＝Requirement，需求；01 是需求類別的流水號，用來追蹤這筆需求）`。同一回覆再引用時可寫 `REQ-01（需求）`。跨回覆或重新輸出的文件需有自己的說明。

新建資料預設採「前綴-流水號」，如 REQ-001；既有 REQ-01 保留原樣。流水號不代表優先順序、版本、已確認或已通過；修訂、狀態與風險等級分欄記錄。含日期、領域標籤或其他後綴時，另說明各段意義，不把非數字後綴稱為流水號。

## 本 Skill 的預設慣例

這是本 Skill 的命名約定，不是要求所有團隊採用的統一標準。RISK、RUN 本身是英文單字，不要捏造縮寫展開。AC 單筆用 Acceptance Criterion，複數為 Acceptance Criteria。

| 前綴 | 英文來源 | 中文意思 | 用途 |
|---|---|---|---|
| SRC | Source | 資料來源 | 追蹤文件、操作指南或其他依據 |
| REQ | Requirement | 需求 | 追蹤單一產品需求 |
| AC | Acceptance Criterion | 驗收條件 | 定義可觀測且可判定的產品條件 |
| Q | Question | 待釐清問題 | 追蹤未決事項、責任人與確認時點 |
| DEC | Decision | 決策 | 記錄人的決定與依據 |
| RISK | Risk | 風險 | 追蹤失敗情境、影響與取捨 |
| SC | Scenario | 測試情境 | 表示待選或已選的測試情境 |
| TC | Test Case | 測試案例 | 保存完整前置、步驟、判準與證據要求 |
| REV | Review | 審查紀錄 | 記錄特定版本的案例審查 |
| F | Finding | 審查發現 | 追蹤具體問題與處置 |
| APP | Approval | 核可紀錄 | 記錄人對明確內容與範圍的核可 |
| BL | Baseline | 案例基線 | 凍結已核可的案例版本 |
| RUN | Run | 測試執行紀錄 | 保存某次實際執行的觀察與證據 |

## 既有及自訂慣例

既有專案以已確認的編號字典或來源為準。未解釋的 `R-01` 不可自行猜成 Requirement、Rule 或 Risk；保留原 ID，標示「R 的英文來源與含義待確認」，需要時只問這一個問題。其他新增前綴也須同時提供全名與用途。

可在 `qa/registry.json` 的 `project.id_glossary` 記錄本專案的定義：

```json
{
  "REQ": {
    "english": "Requirement",
    "meaning": "需求",
    "purpose": "追蹤單一產品需求",
    "basis": "採用本 Skill 的編號慣例"
  }
}
```

這是字典格式示例，不是產品需求。若已存在前綴但含義尚未確認，先以同名項目及 null 欄位記錄，避免工具套用預設解釋。確認後補 english、meaning、purpose，basis 記錄實際依據；不自動改原編號。

`render` 會優先使用專案字典，未定義時才使用上述預設慣例；未知或不完整定義顯示待確認。生成 spec.md、test-cases.md、traceability.md 時各附本檔使用的前綴說明，並產生 id-glossary.md。此檢查只能協助展示，不能驗證填入的英文是否正確；AI／人仍須核對依據。

AI 撰寫的策略、計畫、決策、審查、執行報告與對話，也要自行附相應說明。機器讀取的 JSON id、引用、檔名不加入括號解釋；使用字典或文件圖例，維持追溯連結。
