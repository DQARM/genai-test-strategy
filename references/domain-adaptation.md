# 依使用者專案調整流程

## 使用方式

先從本專案資料辨識受測對象、使用情境、承諾與限制，再選擇適用的提問與驗證方法。下面是思考方向，不是預設測試範圍或已確認規則。不要因為看到某一種類型就把全部項目加進專案。

同一專案可能包含多種介面，例如 App、API 與背景工作；分清每一層能提供的證據。產品範圍與使用者能力有限時，列出觀測缺口與可行的黑箱驗證方式。

| 專案類型 | 優先理解的分歧 | 可考慮的風險 | 操作與證據來源 |
|---|---|---|---|
| Web／桌面／行動 App | 角色、主要流程、返回／取消、資料何時保存、錯誤回饋 | 流程中斷、畫面與保存值不同、狀態切換失敗 | 實際 UI 文件、畫面、事件或後端回覆；無 selector 不編造 |
| API／服務 | 輸入契約、認證狀態、錯誤語意、重複請求、完成時機 | 契約不符、狀態錯誤、重複處理、部分成功 | API 規格、實際 endpoint／方法、request／response、關聯 ID |
| 批次／資料匯入匯出 | 資料型別、空值、重複、排序、部分失敗與交易範圍 | 資料遺漏、重複寫入、錯誤回復、格式或單位誤解 | 已確認工具與參數、固定資料集、輸出檔、處理記錄及前後差異 |
| Linux／部署／網路 | 目標狀態、版本、拓樸、權限、重跑與復原 | 套用不完整、重跑改壞狀態、連線／依賴失效 | 已授權環境、設定差異、服務狀態、命令結果、實際觀測點 |
| 嵌入式／設備／IoT | 輸入訊號、狀態、單位、時序、失效與恢復 | 指令與動作不符、事件競爭、量測或設備失效 | 真實設備／模擬器介面、量測記錄、控制與回應；區分模擬與實機 |
| GenAI／agent 產品 | 任務成功定義、資料集、允許行為、工具權限、非確定性 | 輸出不符判準、來源無法支持結論、工具動作越界 | 確認過的評判準則、案例資料、模型／設定／工具版本、完整執行軌跡 |
| 業務流程／跨系統整合 | 角色責任、交接、補償、狀態對應與外部依賴 | 工作遺失、重複、上下游狀態不一致 | 業務規則、流程操作、通知／紀錄及跨系統關聯證據 |

## 逐步建立的專案背景

可將已知資訊寫入 registry.project 的下列欄位；未提供時保留 null 或列入 unknown_fields，不能把表格示例填成使用者的資料：

- purpose：產品要解決什麼問題；本輪希望得到什麼。
- product_type：使用者提供或來源明確顯示的產品類型。
- users：使用角色、責任及影響對象。
- sut：實際要驗證的產品、功能、服務或流程邊界。
- interfaces：真實可用的 UI、API、CLI、檔案或設備介面及來源。
- environment：已知平台、版本、測試環境與可用權限。
- quality_goals：可驗證的品質目標；未有門檻則記問題。
- constraints：時程、可用資料、工具、觀測與資源限制。

不把這份清單一次問完；每次只問對下一步最有影響的一項。使用者已經提供答案時直接整理並確認解讀，不重做入門問卷。

## 共用的案例設計順序

1. 找到已確認的 AC 與本輪選定風險。
2. 找出可以建立初態、施加輸入及取得觀測的實際介面。
3. 選具體資料，寫出獨立準備、操作、檢查及清理步驟。
4. 為每個產品斷言附上 AC、判定時機與證據。
5. 缺產品規則時提問；缺工具／權限／量測能力時列阻塞。
6. 跨層承諾要有各自適當證據，不能以低層通過替代端到端驗收。

這些步驟對非 AI 產品同樣適用。模型特有的評估只在本專案真的需要時加入；使用 GenAI 協助寫案例本身，不會使受測產品變成 AI 產品。
