## 評估方式

REQ 取自 Requirement（需求）；RISK 是 Risk（風險）這個單字；TC 取自 Test Case（測試案例）。例如 REQ-001、RISK-001、TC-001 的 001 都是各類流水號，不表示等級、版本或已完成。

每個已登錄、未被替代的需求都保留風險評估狀態。AI 先讀需求、適用情境、介面、品質目標、缺陷紀錄與已有評估，再提出具體「在何種條件下，哪個行為失敗，造成什麼後果」。考慮軟體、設備、資料、使用者與跨系統影響，只採本專案適用項目。沒有因果依據時不誇大危害；沒有統計時不編機率。

一個需求可有多個風險，一個共通／跨系統風險可引用多個需求，不複製成內容相同的多筆風險。直接關聯寫在 risks.requirement_ids；需求端由此反查，不再維護第二份 risk_ids 清單。風險尚不能對應需求時保留缺口；不可憑文字相似度或自動創造產品要求補齊。

先做全體已登錄需求的狀態盤點，再深入本輪範圍；未讀、未評估及不在本輪的部分明列，不讓全專案逐條確認成為交付的前提。AI 可批次完成初評，說明來源、推論與缺少的證據；只把會改變危害判斷、驗收或測試取捨的重要分歧交人決定。同一人的有效決策可涵蓋多項，不逐需求要求重新同意。

實質風險取捨問題仍計入五題批次；已選先產出、到總上限或等待續問選擇時，不以風險評估重啟訪談。交付初評與缺口，確認狀態保持 proposed／unassessed。使用者停止訪談不是接受風險。

## 分開三種判斷

| 欄位 | 要回答的事 | 依據 |
| --- | --- | --- |
| severity（危害嚴重度） | 失敗一旦發生，後果有多嚴重？ | 受影響人員／設備／資料／業務、影響範圍、可恢復性及損失 |
| likelihood（發生可能性） | 在指定使用條件下，多容易發生或曝露？ | 實際使用頻率、缺陷歷史、環境、設計變更與證據限制 |
| priority（測試優先序） | 本次應先投入哪些驗證？ | 前兩者加上不確定性、改動、現有證據、測試成本與交付目標 |

嚴重度不能由測試成本、難易度或低機率降低；高嚴重度也不自動等於某個測試優先序。不得直接把 P0/P1/P2 當危害等級。若採此命名，P 取自 Priority（優先序），數字含義由專案準則定義，不是識別碼流水號。

優先沿用專案已確認的分級、方向與依據。沒有標準時，提出精簡文字分級供採納，先標 proposed；不要強迫使用精密分數或相乘公式。可提出下列**建議草案**，實際門檻與適用性由專案確認，不寫進新專案預設資料：

| 嚴重度建議 | 後果描述草案 |
| --- | --- |
| critical／極嚴重 | 有依據的人身重大危害、不可逆重大損失或核心系統廣泛失效 |
| high／高 | 主要功能不可用、重大資料／設備／業務損害，恢復困難 |
| medium／中 | 功能受限但可恢復，影響範圍有限且存在可行替代方式 |
| low／低 | 輕微使用影響，核心結果及資料完整性不受影響 |

可能性另定自己的高／中／低與觀察條件，優先序另定處理時點；不同尺度不必使用相同級數。資料不足使用字面值 `unknown`，並在對應理由說明缺什麼，不當作最低等級或零機率。不預設取得正式安全認證，也不把這份測試風險初評冒充專案另有要求的專業危害分析。

## 資料與狀態

沿用 schema 1。新專案 project.risk_policy 是 `requirement-risk-v1`；詳細資料仍只存 qa/registry.json，qa/risks.md 與 HTML 是生成視圖。

project.risk_criteria 欄位：

- `status`：proposed／confirmed。
- `severity`、`likelihood`、`priority`：各自為「等級代碼：明確文字定義」的非空物件。可用專案既有 S1／S2 等名稱，但必須說明英文來源、數字方向及含義；`unknown` 保留給資料不足，不放入等級表。
- `source_refs`、`decision_refs`：已登錄來源／決策。confirmed 必須有確認的 normative 來源或真實人的決策；來源須實際支持本次分級準則。

每個 requirements 記錄增加 `risk_assessment`：

```json
{
  "status": "unassessed",
  "requirement_revision": 1,
  "rationale": "尚未檢視本需求的失敗情境與後果。",
  "source_refs": [],
  "decision_refs": []
}
```

- **unassessed／未評估**：還沒有完成初評。舊資料缺欄位也如此顯示，不自行當成無風險。
- **proposed／已有初評**：已有失敗情境與評估建議，但還沒有適用確認依據；可先產出案例草稿。
- **confirmed／已確認**：有正式來源或人的有效決策支持本需求的風險評估／取捨，不表示已測試或已消除風險。可確認某維度仍為 unknown，但必須記錄理由、處置及限制。
- `requirement_revision` 綁實際被評估的需求版次；`rationale` 說明檢視範圍、評估結論或仍缺的依據。confirmed 必須有 source_refs 中已確認的 normative 來源或真實 decision_refs。需求已確認不自動確認其風險評估。
- 經檢視暫未辨識風險時，可沒有 RISK 記錄，但必須寫理由與範圍，顯示「本次未辨識風險，不等於零風險」。不能為湊數新增空洞風險，也不能省略評估。

risks 保留原有 failure、impact、likelihood、uncertainty、priority、rationale、evidence_refs、disposition、owner、residual_risk，增加：

- `requirement_ids`：直接對應的需求陣列，支援多對多。
- `severity`、`severity_rationale`：嚴重度代碼及理由。
- `likelihood_rationale`：可能性判斷及證據不足之處；priority 的理由仍用原 `rationale`。
- `source_refs`、`decision_refs`：評估來源及取捨決策；原 evidence_refs 文字保留，不把舊自由文字自動改為正式來源。
- `disposition_reason`：需要暫緩時記取捨理由；暫緩採 disposition=`defer`，另記 residual_risk 與真實 decision_refs。

各維度使用已定義代碼或 `unknown`。每個有填等級／unknown 的維度都留下理由，不能由工具按空值自動給低分。風險表的評估狀態以各需求的 risk_assessment 為準；共通風險的不同關聯需求可尚未同時完成確認。

## 範圍與案例承接

保留原本的測試範圍選擇：已選風險由 selected_risk_ids 與案例 risk_ids 承接，再由人審查步驟／觀察／斷言是否真的能發現失敗。未選風險不偷偷刪除；涉及本輪需求時留下暫緩理由、剩餘風險與決策。重大疑慮可以阻塞相關核可或執行，但不把所有未選需求一律拉進本輪訪談。

需求、風險、分級準則或來源改變時，重新檢視受影響評估並標 proposed／unassessed，保留修訂與真實決策；不可只把 requirement_revision 改新而沿用舊結論。更新測試取捨與案例後以新 digest 審查。需求版次不符時工具會顯示評估過期；工具無法判斷所有自由文字的實質變更。

## 檢查與舊專案

工具 1.5.0 的 `check` 會指出未評估、初評待確認、過期、缺嚴重度或理由、缺直接需求關聯等缺口；無效引用、等級或偽稱 confirmed 卻沒有確認依據是結構錯誤。缺口可先保留草稿，不為通過檢查補造證據。

新基線須採 risk_policy，並完成**本輪選定驗收條件／案例／風險所直接涉及需求**的風險評估確認。本輪有風險時分級準則須已確認；相關風險各維度及理由完整，已選風險有案例，其他關聯風險有暫緩決策與剩餘風險。本輪外未評估需求只保留警示，不阻塞無關案例。unknown 可保留，但重大未決處置仍依 Q 的實際阻塞範圍處理；不因通過結構檢查而核准產品放行。

舊專案先保存版本，依 local-versioning.md 明確更新 qa/tools/qa_project.py；重跑 init 不會升級工具。缺 risk_policy 或新欄位時仍可 draft 檢查／render，畫面保留未評估與舊資料；新基線前按本輪範圍補欄位、準則與真實評估依據，再設 risk_policy、重審新 digest。不要從舊 priority 或 impact 直接推成已確認 severity。既有基線、核可、執行與證據快照維持原樣。
