# 通用需求與 Test Case 模板

所有欄位由當前專案的來源與決策填寫。模板的 null、空陣列與說明文字都代表尚待補足，不能當成正式規則、真實工具或已完成驗證。

## 需求釐清記錄

- 原始描述與來源定位。
- 已知：本專案資料明確支持的內容。
- 分歧：哪兩種解讀會造成不同實作或 Expected。
- 下一題：目前最有影響的一個決策問題。
- 人的回答：原意、決策人與時間；不知道就保留 open。
- 已確認規則：適用條件、操作、可觀測結果、時機／容差。
- 未決項目：Q ID、owner、確認時點、影響與阻塞階段。

## 每輪釐清短模板

沿用已提供的焦點與預算；未知產品規則不代填。以下為填寫提示，不是一張要請使用者全部回答的問卷。

**本輪安排（記入 session）：**

- 專案準備：未完成／完成、尚缺資訊；與需求釐清進度分開記錄。規格有無、資料夾、來源位置、版控及登入等初始化問題不計需求題數。
- 焦點／預計交付：一個流程、功能或重要風險，以及本輪要形成的規則／案例。
- 暫不展開：項目與回訪時點；不自動改掉已選測試範圍。
- 預算：使用者設定，否則 10–15 分鐘、最多 3 個需求決策問題；記錄時間適用於需求討論或整場，整場上限仍包含初始化。
- 進度：未開始／進行中、第一個實質需求或本輪範圍決策的起算點、已問問題的短標籤與原文連結、是否計入及已用題數；可確知的時間資訊，無法可靠計時就註明。準備完成且尚未問需求時可寫「需求釐清未開始（0／3 題）」；已問過實質決策則保留用量。
- 收尾：尚在進行／已收尾及原因；下一輪建議焦點。

**精簡續作狀態（維護同一份 session，不另建對話資料庫）：**

- 專案設定：根目錄、規格概況、來源位置／無文件、版控選擇及同步狀態。
- 相關依據：本輪規則／決策／來源 ID、確認狀態、版本與原文位置；包含共通限制及跨功能依賴。
- 待辦：未決事項、owner／時點、受阻階段；待更新案例與原因、報告是否待重產。
- 成果：已完成案例／審查的版本及檔案位置；不要把待更新版本列成可執行。
- 下一步：下一個單一問題／動作；已收尾時只列下輪建議。
- 用量：使用者有設定才記預算；實際值附統計範圍，無工具資訊則寫未知。

只替換目前狀態，不附整段歷史；完整回答、決策與案例留在原有檔案。摘要不能把建議改為已確認。同一輪續作沿用剩餘額度；若舊記錄誤計初始化，依問題記錄校正並註明原因，無依據的用量標未知。案例通常在本輪收尾集中補齊，使用者提前要求時可提前交付；每題仍立即保存回答與規則。

**每題決策卡（一次一張）：**

- 情境與依據：只引用與這一題有關的資料，保留適用的共通限制與必要依賴。
- 要決定的一件事：哪個分歧會改變預期結果或驗收。
- 選項及影響：2–3 個方向、各自代價；可回答待確認或自行補充。
- 如提供 AI 建議：清楚標示尚未確認及理由。

**收尾三句：**

1. 本輪已確認：實際取得的決策與規則。
2. 已可交付：完整案例或仍受阻的草稿；如未實測，明說尚未執行。
3. 下一個最值得決定的問題：列為下輪待辦；預算已用完就不再索答。

## 風險與範圍

每項風險寫明失敗情境、影響、可能性／曝露、不確定性、優先序與理由，再決定對應的測試層級、方法、資料和證據。選定範圍記入 scope；未選項目留下取捨理由與剩餘風險。

## 案例草稿 JSON

建立真實案例時依本專案命名 ID 與 title，將檔名設為相同 ID。這個空白草稿沒有產品判準，不具備 ready 條件：

```json
{
  "id": "TC-001",
  "title": "填入本專案要驗證的具體行為",
  "revision": 1,
  "status": "draft",
  "purpose": null,
  "ac_ids": [],
  "risk_ids": [],
  "scenario_ids": [],
  "level": null,
  "type": null,
  "environment": {
    "target": null,
    "build_binding": null,
    "tools": null,
    "binding_refs": []
  },
  "preconditions": [{"action": null, "verify": null}],
  "data": [],
  "steps": [{
    "n": 1,
    "action": null,
    "input": null,
    "observe": null,
    "when": null,
    "evidence": null,
    "checks": []
  }],
  "cleanup": [{"action": null, "verify": null}],
  "independence": null,
  "verdict_rules": {"pass": null, "fail": null, "inconclusive": null},
  "blockers": [],
  "provenance": {"author": "assistant", "model": "unknown", "context_refs": []}
}
```

存在具體缺口時建立 Q，將 Q ID 填入 blockers，並設 blocked。不能留下空 blockers 卻宣稱相關資訊完整。

## 由草稿變成完整案例

逐一確認下列資訊，以真實名稱和值取代空白：

1. 目的與依據：選定 AC、風險、情境，並確認 AC 的版本及來源。
2. 初態：如何自行建立；從哪裡確認前置成立。
3. 資料：具體值、單位、格式與取得方式；依資料型別設計適當的代表值／邊界。
4. 操作：實際 UI 路徑、request、CLI、檔案或設備動作。只有概念性操作時不能宣稱可執行。
5. 斷言：加入 `checks: [{"expected": "已確認的可觀測結果", "rule_refs": ["實際 AC ID"]}]`。每個宣稱覆蓋的 AC 都要有對應斷言。
6. 判定：何時看哪個輸出；何種證據可支持 PASS、FAIL 或無法判定。
7. 重跑：本案自己的清理、隔離、重置，不依賴另一個案例。檢查所有會影響本案的殘留狀態；只知道主要資料已清空，不能推定快取、去重記錄或待處理事件也已清空。缺少重置契約時列待確認，或使用已確認可隔離的新 fixture。

生成時 Actual 留待實測，寫入 RUN，不能填進案例設計。人工程序與自動化程序都需要以上資訊；自動化另記真實腳本、相依套件與執行方式。

如果只是先討論需求，可以用對話或 Markdown 表達草稿；確定專案資料夾後再轉入 registry 與 cases，無須為了開始對話而先假造完整 JSON。
