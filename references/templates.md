## 需求釐清記錄

- 原始描述與來源定位。
- 已知：本專案資料明確支持的內容。
- 分歧：哪兩種解讀會造成不同實作或 Expected。
- 下一題：目前最有影響的一個決策問題。
- 成對問答：依 [interview-records.md](interview-records.md) 保留原始提問、選項、原始回答；AI 解讀另列，已知回答者與時間照實記錄。
- 回答狀態：未答／已答／部分回答／不知道／暫緩／缺回答；與規則確認狀態分開，不知道就保留 open。
- 更正及關聯：保留舊問答，連到受影響決策、需求、風險與案例；缺原文標示，不補寫逐字稿。
- 已確認規則：適用條件、操作、可觀測結果、時機／容差。
- 未決項目：Q ID、owner、確認時點、影響與阻塞階段。

## 每輪釐清短模板

流程與計數依 [workflow.md](workflow.md#本輪範圍與釐清預算)。以下是 AI 從已知記錄填寫的欄位，不是逐欄訪談問卷。

**session 目前狀態：**

| 欄位 | 保存內容 |
|---|---|
| 專案準備 | 規格概況、根目錄、新建／沿用、來源位置／無文件、版控選擇與同步狀態；未知項目 |
| 本輪 | 階段、焦點、預計交付、暫不展開事項及回訪條件 |
| 限制 | 預算來源、明訂總題數／時間／費用及適用範圍；時間是目標或上限 |
| 計數 | 累計、本批起算點與已問／可問數、問題短標籤及原文連結、是否計入、最近統整 |
| 續問 | 進行中／等待選擇／已選續問／已選先產出；真實選擇、時間與原文連結 |
| 依據 | 本輪來源／規則／決策的狀態、版本、實讀範圍與定位；共通限制及跨功能依賴 |
| 待辦 | 未決項、owner／時點、受阻階段、待更新案例及原因、報告是否待重產 |
| 成果 | 已交付案例／審查的版本與實際位置、可執行性及限制 |
| 下一步 | 下一個單一問題或動作、是否收尾及原因、下輪建議 |
| 用量 | 有設定才記預算；實際值及統計範圍，無資料記未知 |

用目前狀態取代舊摘要，完整歷史保留原記錄並以連結定位。server 的帳號／網址、分支、上傳範圍及遠端版本依 [git-server.md](git-server.md) 記錄，不含憑證。

**統整時的示例文案：**

新增確認：[新增規則]。目前可形成：[實際成果，尚未寫成案例則明說]。重要缺口：[影響交付的事項]。
繼續釐清可補足：[具體缺口及用途]。

> 這一批已完成統整。接下來希望「繼續釐清」或「先產出」？
> 若繼續，我會一次問一題，每五題統整一次，再讓你選擇；也可隨時要求先產出。

僅在 workflow 指定的等待選擇情形使用；已具備交付依據或已到明訂上限時直接產出。

**單題決策卡：** 問題、必要情境／用途、適用選項及影響、自由回答／待確認；如提供建議，另標 AI 建議及理由。

**收尾三句：** 本輪新增確認；實際交付及仍缺欄位／是否實測；下一個動作與責任人。

## 風險與範圍

依 [risk-assessment.md](risk-assessment.md) 填寫本表；非需求來源的風險按其 origin 與影響另列。

| 需求與版次 | 評估狀態 | 風險／失敗情境 | 後果 | 嚴重度與理由 | 可能性與理由 | 測試優先序與理由 | 依據／缺口 | 案例或暫緩處置 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 實際需求 | 未評估／已有初評／已確認 | 直接連結，可一對多／多對多 | 具體影響對象與範圍 | 專案等級或 unknown | 專案等級或 unknown | 專案等級或 unknown | 來源／決策／尚缺資訊 | 已選案例或取捨、剩餘風險與決策 |

分級、未知及取捨的處理依 risk-assessment.md；選定範圍記入 scope。

## 案例撰寫前的已知條件摘要

策略中視需要補一張精簡表，詳見 test-design.md：

| 已選風險 | 失效機制與依據 | 方法／深度 | 要保留的項目與證據 | 時間／設備限制及未測部分 |
|---|---|---|---|---|
| 本專案實際風險 | 在什麼條件下如何失敗 | 適用技術及選擇理由 | 可觀測承諾及覆蓋項目 | 不把未測當通過，不代填風險接受 |

非需求來源的風險依 risk-assessment.md 明列 origin 及 affected_areas；不用虛構需求填滿表格。排程標籤／分鐘另放 execution-profile，不改原設計欄位。

本批選定情境／來源版本：[實際範圍與依據]。依 [展示時機](workflow.md#候選情境與案例) 使用下表；不同確認狀態分列。

| 項目 | 目前內容與狀態 | 依據與定位 | 對本批案例的影響 |
| --- | --- | --- | --- |
| 本輪範圍 | 已選流程、風險、情境及暫不處理事項 | 現有 scope／策略及人的取捨記錄 | 本批要承接哪些項目 |
| 來源閱讀 | 實際已讀範圍、僅索引／部分正文、未讀或讀取失敗 | 來源版本、閱讀紀錄序號及摘錄序號；可點閱原文定位 | 哪些引用有正文支持、哪些案例仍受阻 |
| 規則與驗收條件 | 已確認規則；草稿、建議及現況觀察分開標示 | 來源檔案、版本、條款或確認決策 | 哪些可作為 Expected，哪些仍待確認 |
| 執行條件 | 設備／軟體、權限、工具、資料、初態與重置方式；可用性未驗證時註明 | 操作文件版本與定位、環境紀錄 | 能否寫出可照做的步驟及獨立前置 |
| 判定方式 | 觀察點、判定時機、門檻／容差及所需證據；未知列缺口 | 已確認判準及觀測方法的依據 | 能判定哪些承諾、仍缺什麼觀測能力 |
| 方法與覆蓋項目 | 適用的方法、分區／邊界／組合／轉移及取捨；由 AI 分析 | 已確認 AC、選定風險與範圍 | 要由哪些具體輸入、初態與斷言承接 |
| 待確認事項 | 產品、操作或環境缺口；責任人／確認時點沿用既有記錄 | 既有問題或來源衝突的定位 | 受阻情境／案例，以及可繼續的部分 |

表格供快速核對；案例本身仍須完整且可追溯，確認與缺口處理依 workflow.md。

## 案例草稿 JSON

建立真實案例時依本專案命名 ID 與 title，將檔名設為相同 ID。這個空白草稿沒有產品判準，不具備 ready 條件：

```json
{
  "id": "TC-001",
  "title": "填入本專案要驗證的具體行為",
  "revision": 1,
  "status": "draft",
  "purpose": null,
  "ac_ids": [],
  "risk_ids": [],
  "scenario_ids": [],
  "coverage_ids": [],
  "level": null,
  "type": null,
  "environment": {
    "target": null,
    "build_binding": null,
    "tools": null,
    "binding_refs": []
  },
  "preconditions": [{"action": null, "verify": null}],
  "data": [],
  "steps": [{
    "n": 1,
    "action": null,
    "input": null,
    "observe": null,
    "when": null,
    "evidence": null,
    "checks": []
  }],
  "cleanup": [{"action": null, "verify": null}],
  "independence": null,
  "verdict_rules": {"pass": null, "fail": null, "inconclusive": null},
  "blockers": [],
  "provenance": {"author": "assistant", "model": "unknown", "context_refs": []}
}
```

存在具體缺口時建立 Q，將 Q ID 填入 blockers，並設 blocked。不能留下空 blockers 卻宣稱相關資訊完整。

## 由草稿變成完整案例

逐一確認下列資訊，以真實名稱和值取代空白：

1. 目的與依據：選定 AC、風險、情境，並確認 AC 的版本及來源。
2. 初態：如何自行建立；從哪裡確認前置成立。
3. 資料：具體值、單位、格式與取得方式；依資料型別設計適當的代表值／邊界。
4. 操作：實際 UI 路徑、request、CLI、檔案或設備動作。只有概念性操作時不能宣稱可執行。
5. 斷言：加入 `checks: [{"expected": "已確認的可觀測結果", "rule_refs": ["實際 AC ID"], "coverage_ids": ["實際 COV ID"]}]`。每個宣稱覆蓋的 AC 都要有對應斷言。
6. 判定：何時看哪個輸出；何種證據可支持 PASS、FAIL 或無法判定。
7. 重跑：本案自己的清理、隔離、重置，不依賴另一個案例。檢查所有會影響本案的殘留狀態；只知道主要資料已清空，不能推定快取、去重記錄或待處理事件也已清空。缺少重置契約時列待確認，或使用已確認可隔離的新 fixture。

生成時 Actual 留待實測，寫入 RUN，不能填進案例設計。人工程序與自動化程序都需要以上資訊；自動化另記真實腳本、相依套件與執行方式。

如果只是先討論需求，可以用對話或 Markdown 表達草稿；確定專案資料夾後再轉入 registry 與 cases，無須為了開始對話而先假造完整 JSON。


## 緊湊案例表（對話草稿選用）

多筆案例共用環境或阻塞時，先列一份「共通環境、真實操作介面、每案如何重置、觀測與證據方法、共通 Q」；下表每列為一案。只在內容能清楚閱讀時使用，不因案例數量硬套寬表。長步驟、分支、時序複雜或準備正式交接時改成逐案展開。

| TC ID／目的與狀態 | 獨立初態與資料 | 操作、觀測時點與證據 | Expected 與 AC／COV | 清理、個案阻塞與判定 |
|---|---|---|---|---|
| 既有或新流水號；draft／blocked／ready | 明示使用哪份共通前置及本案參數，如何自行建立與驗證 | 1. 具體操作與輸入；2. 在指定時機查指定觀測點；保存哪項證據 | 每項斷言引用已確認 AC 及實際覆蓋的 COV；未知保留缺口 | 如何重置及確認；引用共通與個案 Q；通過／失敗／無法判定 |

共通前置必須在同份交付中可取得；不能寫「沿用上一個 TC 的結果」。共通阻塞用 Q 引用，避免每案複製相同說明；相關案例仍標 blocked，不把概念操作包裝成可執行命令。Actual 留待實測，不因表格緊湊而填入 Expected。

首次使用 REQ／AC／COV／TC／Q 仍說明英文來源與用途。對話內容未落檔須明說。轉存正式 cases 時將共通前置／清理展開到每案既有欄位，保留原 ID 與確認狀態，不新增第二套資料格式或重啟訪談。
