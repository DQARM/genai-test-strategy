## 需求釐清記錄

- 原始描述與來源定位。
- 已知：本專案資料明確支持的內容。
- 分歧：哪兩種解讀會造成不同實作或 Expected。
- 下一題：目前最有影響的一個決策問題。
- 成對問答：依 [interview-records.md](interview-records.md) 保留原始提問、選項、原始回答；AI 解讀另列，已知回答者與時間照實記錄。
- 回答狀態：未答／已答／部分回答／不知道／暫緩／缺回答；與規則確認狀態分開，不知道就保留 open。
- 更正及關聯：保留舊問答，連到受影響決策、需求、風險與案例；缺原文標示，不補寫逐字稿。
- 已確認規則：適用條件、操作、可觀測結果、時機／容差。
- 未決項目：Q ID、owner、確認時點、影響與阻塞階段。

## 每輪釐清短模板

沿用已提供的焦點與預算；未知產品規則不代填。以下為填寫提示，不是一張要請使用者全部回答的問卷。

**本輪安排（記入 session）：**

- 專案準備：未完成／完成、尚缺資訊；與需求釐清進度分開記錄。規格有無、資料夾、來源位置、版控及登入等初始化問題不計需求題數。
- 階段／焦點／預計交付：目前處於需求釐清、範圍選取、案例設計或其他實際階段；本輪聚焦的流程、功能或風險，以及要形成的規則／案例。輪次編號不代表階段已切換。
- 暫不展開：項目與回訪時點；不自動改掉已選測試範圍。
- 預算：每批最多五題、一次一題；預設沒有十題總上限。使用者明訂總題數／時間優先，追加批次不得超過剩餘總額度。另記預算來源、10–15 分鐘進度目標或明訂時間上限及其適用範圍；整場上限包含初始化。
- 進度：累計已問、本批起算點與已問／可問數、問題短標籤及原文連結、是否計入、最近統整與可確認的時間；對外例如「累計已問 0 題；本批已問 0 題，每五題統整一次」。追加批次不清零累計；有明訂總上限時另列。
- 續問狀態：進行中／等待選擇／已選續問／已選先產出；留下真實選擇、時間與原文連結。未有明確選擇不得代填續問。初始化、統整與續問選擇不計需求題數。
- 收尾：尚在進行／已收尾及原因；下一輪建議焦點。

**精簡續作狀態（維護同一份 session，不另建對話資料庫）：**

- 專案設定：根目錄、規格概況、來源位置／無文件、版控選擇及同步狀態。
- 相關依據：本輪規則／決策／來源 ID、確認狀態、版本與原文位置；包含共通限制及跨功能依賴。
- 待辦：未決事項、owner／時點、受阻階段；待更新案例與原因、報告是否待重產。
- 成果：已完成案例／審查的版本及檔案位置；不要把待更新版本列成可執行。
- 下一步：下一個單一問題／動作；已收尾時只列下輪建議。
- 用量：使用者有設定才記預算；實際值附統計範圍，無工具資訊則寫未知。

只替換目前狀態，不附整段歷史；完整回答、決策與案例留在原有檔案。摘要不能把建議改為已確認。同一輪續作沿用累計、本批額度及續問選擇；舊預設三題／十題的續作依 workflow.md，使用者明訂的短預算不自動放寬。若誤計初始化，依問題記錄校正並註明原因，無依據的用量標未知。案例通常在本輪收尾集中補齊，使用者提前要求時可提前交付；每題仍立即保存回答與規則。

**每五題統整一次，再選擇下一步：**

新增確認：[本段新增的規則]。目前可形成：[實際完成內容，或明確標示尚待撰寫的案例／草稿]。重要缺口：[仍影響本輪交付的事項]。
資料足夠時直接產出，不必問滿；明訂總上限已到也直接產出。其餘在本批最後一答後附上以下選擇，等待回覆，不附帶下一個產品問題：

繼續釐清可補足：[具體缺口與用途]。

> 這一批已完成統整。接下來，你希望：
>
> - 繼續釐清
> - 先產出
>
> 若繼續，我會一次問一題，每五題統整一次，再讓你選擇是否繼續。你也可以隨時要求先產出；資料足夠時，我會提早整理測試策略與案例草稿。

五題是統整間隔，不估算總共還有多少問題。使用者明訂總上限時另列，例如「你設定本輪總共最多八題，目前累計五題；依此限制還可問三題，到限就產出」，不要把限制餘額寫成需求只剩三題。選續問才追加該批；選先產出就依已確認內容做策略與案例，未決部分標草稿／受阻，不再索答。摘要與選擇不占需求題數，不代表核可產品規則。可顯示「累計已問 5 題；本次統整已完成；等待選擇」，不寫成需求完成百分比。

**每題決策卡（一次一張）：**

- 單一問題：用使用者熟悉的詞說明現在要決定什麼。提問前先查既有答案及適用分支，僅詢問影響本輪交付的缺口。
- 必要情境與用途：只引用相關依據、共通限制及依賴；不明顯時簡短說明答案會改變哪個案例或判準。
- 回答方式：有明確方向才給 2–3 個中性選項及影響；允許待確認、適用時的不適用及自由回答。已有有效決策不重問；未知保留缺口。
- 如提供 AI 建議：清楚標示尚未確認及理由。

**收尾三句：**

1. 本輪新增確認：相較輪初新增的決策與規則；沒有新增就如實說明。
2. 本輪交付：實際產出的完整案例、草稿或有依據的內容，以及仍缺欄位；如未實測，明說尚未執行。
3. 下一個動作與責任人：查資料、取得介面、補案例、審查或必要決策；只有需要人的決策才列下一題，已選先產出或明訂總上限已到就只列待辦，不自動重啟訪談。

## 風險與範圍

依 [risk-assessment.md](risk-assessment.md) 維護每個需求的評估狀態。先由 AI 依資料初評，不把此表變成逐欄問卷；提問沿用本批額度與續問選擇。

| 需求與版次 | 評估狀態 | 風險／失敗情境 | 後果 | 嚴重度與理由 | 可能性與理由 | 測試優先序與理由 | 依據／缺口 | 案例或暫緩處置 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 實際需求 | 未評估／已有初評／已確認 | 直接連結，可一對多／多對多 | 具體影響對象與範圍 | 專案等級或 unknown | 專案等級或 unknown | 專案等級或 unknown | 來源／決策／尚缺資訊 | 已選案例或取捨、剩餘風險與決策 |

未評估不等於沒有風險；未辨識風險須留檢視範圍與理由。使用已確認分級準則，沒有標準先提出建議。選定範圍記入 scope，再決定測試層級、方法、資料與證據。

## 案例撰寫前的已知條件摘要

本批選定情境／來源版本：沿用目前範圍與已讀依據，未知明列，不另行猜補。以下短表先展示給使用者，再撰寫案例；每批一次，同批後續只更新變動。必要時拆列，以免把不同確認狀態混在一起。

| 項目 | 目前內容與狀態 | 依據與定位 | 對本批案例的影響 |
| --- | --- | --- | --- |
| 本輪範圍 | 已選流程、風險、情境及暫不處理事項 | 現有 scope／策略及人的取捨記錄 | 本批要承接哪些項目 |
| 來源閱讀 | 實際已讀範圍、僅索引／部分正文、未讀或讀取失敗 | 來源版本、閱讀紀錄序號及摘錄序號；可點閱原文定位 | 哪些引用有正文支持、哪些案例仍受阻 |
| 規則與驗收條件 | 已確認規則；草稿、建議及現況觀察分開標示 | 來源檔案、版本、條款或確認決策 | 哪些可作為 Expected，哪些仍待確認 |
| 執行條件 | 設備／軟體、權限、工具、資料、初態與重置方式；可用性未驗證時註明 | 操作文件版本與定位、環境紀錄 | 能否寫出可照做的步驟及獨立前置 |
| 判定方式 | 觀察點、判定時機、門檻／容差及所需證據；未知列缺口 | 已確認判準及觀測方法的依據 | 能判定哪些承諾、仍缺什麼觀測能力 |
| 方法與覆蓋項目 | 適用的方法、分區／邊界／組合／轉移及取捨；由 AI 分析 | 已確認 AC、選定風險與範圍 | 要由哪些具體輸入、初態與斷言承接 |
| 待確認事項 | 產品、操作或環境缺口；責任人／確認時點沿用既有記錄 | 既有問題或來源衝突的定位 | 受阻情境／案例，以及可繼續的部分 |

已知資訊不一律標成已確認；不要新增推測的門檻或操作。依據足夠就接續輸出完整案例；有缺口則只阻塞受影響部分。摘要不構成核可、不新增確認關卡，案例本身仍要完整且可追溯。

## 案例草稿 JSON

建立真實案例時依本專案命名 ID 與 title，將檔名設為相同 ID。這個空白草稿沒有產品判準，不具備 ready 條件：

```json
{
  "id": "TC-001",
  "title": "填入本專案要驗證的具體行為",
  "revision": 1,
  "status": "draft",
  "purpose": null,
  "ac_ids": [],
  "risk_ids": [],
  "scenario_ids": [],
  "coverage_ids": [],
  "level": null,
  "type": null,
  "environment": {
    "target": null,
    "build_binding": null,
    "tools": null,
    "binding_refs": []
  },
  "preconditions": [{"action": null, "verify": null}],
  "data": [],
  "steps": [{
    "n": 1,
    "action": null,
    "input": null,
    "observe": null,
    "when": null,
    "evidence": null,
    "checks": []
  }],
  "cleanup": [{"action": null, "verify": null}],
  "independence": null,
  "verdict_rules": {"pass": null, "fail": null, "inconclusive": null},
  "blockers": [],
  "provenance": {"author": "assistant", "model": "unknown", "context_refs": []}
}
```

存在具體缺口時建立 Q，將 Q ID 填入 blockers，並設 blocked。不能留下空 blockers 卻宣稱相關資訊完整。

## 由草稿變成完整案例

逐一確認下列資訊，以真實名稱和值取代空白：

1. 目的與依據：選定 AC、風險、情境，並確認 AC 的版本及來源。
2. 初態：如何自行建立；從哪裡確認前置成立。
3. 資料：具體值、單位、格式與取得方式；依資料型別設計適當的代表值／邊界。
4. 操作：實際 UI 路徑、request、CLI、檔案或設備動作。只有概念性操作時不能宣稱可執行。
5. 斷言：加入 `checks: [{"expected": "已確認的可觀測結果", "rule_refs": ["實際 AC ID"]}]`。每個宣稱覆蓋的 AC 都要有對應斷言。
6. 判定：何時看哪個輸出；何種證據可支持 PASS、FAIL 或無法判定。
7. 重跑：本案自己的清理、隔離、重置，不依賴另一個案例。檢查所有會影響本案的殘留狀態；只知道主要資料已清空，不能推定快取、去重記錄或待處理事件也已清空。缺少重置契約時列待確認，或使用已確認可隔離的新 fixture。

生成時 Actual 留待實測，寫入 RUN，不能填進案例設計。人工程序與自動化程序都需要以上資訊；自動化另記真實腳本、相依套件與執行方式。

如果只是先討論需求，可以用對話或 Markdown 表達草稿；確定專案資料夾後再轉入 registry 與 cases，無須為了開始對話而先假造完整 JSON。
